# v4.3 vs cuBLAS：非对齐列数的对比分析（cols=1500）

## 1. 为什么选 cols=1500

前一轮用 cols=1000 测试，发现 v4 几乎不退化。原因是 1000 < 1024，v4 主循环步进 1024 时，所有活跃线程恰好都走 float4 路径，没有 warp divergence。这其实回避了真正的"破"场景。

**cols=1500 才是真正卡在中间的尺寸**：

- v4 主循环步进 = blockSize × packSize = 256 × 4 = **1024**
- 第一轮（c = tid×4, 0..1020）：所有 256 线程都走 float4，覆盖 cols[0..1023]
- 第二轮（c = 1024 + tid×4, 1024..2044）：只有 tid=0..118 还在 cols 范围内
  - tid=0..118 走 float4 (c=1024..1496, c+3=1499<1500) ✓
  - tid=119 起（c=1500..） 跨过 cols，整个 else 分支都不走
- 结果：**第一轮所有 warp 满载，第二轮只有 4 个 warp 在工作，剩 4 个 warp 空转等同步**

这正是 v4 设计上的薄弱点。

## 2. 实测数据

### 标准基准（cols=1024，完美对齐）


| 版本     | 时延（ms） | 相对 v0 |
| ------ | ------- | ----- |
| v0     | 0.0261  | 1.00× |
| v4     | 0.0163  | 1.60× |
| cuBLAS | 0.0219  | 1.19× |




### 非对齐基准（cols=1500）


| 版本         | 时延（ms）    | 相对 v0 | 相对自身 cols=1024 |
| ---------- | ---------- | ----- | -------------- |
| **v4**     | **0.0221** | 1.18× | **+35%** 退化    |
| **v4.3**   | **0.0227** | 1.15× |（没基线，但与 v4 接近） |
| **cuBLAS** | **0.0300** | 0.87× | **+37%** 退化    |

## 3. 关键发现（与 cols=1000 完全不同的故事）



### 发现 1：v4 在 cols=1500 上退化了 35%

cols=1024 → cols=1500：v4 从 0.0163 ms 涨到 0.0221 ms。 **为什么涨这么多**？数据量只多了 46%（1500/1024 = 1.46），但时延涨了 35%。两个原因：

1. **多了一整轮循环**：第二轮的同步开销（两次 block_reduce）摊不掉
2. **第二轮 warp divergence**：tid 119 之后的线程提前退出，第二轮的归约要等"半空"的 block



### 发现 2：v4.3 在 cols=1500 上略**慢**于 v4（0.0227 vs 0.0221）

这是反直觉的——v4.3 设计上就是为非对齐场景优化的，怎么反而慢？原因：

- v4 在 cols=1500 时第一轮所有线程都走 float4（恰好整轮命中），第二轮才出现 divergence
- v4.3 把 main 循环对齐到 packSize=4 的倍数（main_cols = 1500），tail = 0
- v4.3 的 main 循环步进还是 1024，所以第二轮里 tid=0..118 走 float4，但还要走完整循环的索引计算
- 两者在 cols=1500 上跑的指令数几乎一样 -
- v4.3 多了一些"显式 tail"的索引开销，反而略慢

**这印证了一个事实：v4.3 的 main+tail 显式分离不是万能药，只有当 cols % packSize ≠ 0 时才有优势**。 cols=1500 是 4 的倍数，tail=0，所以 v4.3 没有发挥空间。

### 发现 3：cuBLAS 在 cols=1500 上退化了 37%

cuBLAS 从 0.0219 ms（cols=1024）涨到 0.0300 ms（cols=1500），退化 37%。这破除了之前的"cuBLAS 时延对 cols 无关"假设——**那个假设只在 cols<1024 时成立**。当 cols > 1024 时，cuBLAS 同样需要多跑一轮循环，同步开销同样翻倍。不同的是 cuBLAS 一直是标量路径，绝对时延更高。

### 发现 4：v4 vs cuBLAS 的优势在 cols=1500 上扩大到 +36%


| 场景            | v4 时延         | cuBLAS 时延     | v4 优势    |
| ------------- | ------------- | ------------- | -------- |
| cols=1024     | 0.0163 ms     | 0.0219 ms     | **+26%** |
| cols=1000     | 0.0166 ms     | 0.0220 ms     | **+33%** |
| **cols=1500** | **0.0221 ms** | **0.0300 ms** | **+36%** |


v4 在非对齐场景下的相对优势 **不降反升**。原因：

- v4 退化 35%（绝对值 0.0058 ms）
- cuBLAS 退化 37%（绝对值 0.0081 ms）
- cuBLAS 的标量路径在第二轮上摊更多的指令开销，绝对退化更严重

## 4. cols 维度的完整扫描

我额外跑了几个尺寸来观察规律：


| cols | v4 (ms) | v4.3 (ms) | cuBLAS (ms) | v4 vs cuBLAS | 说明                             |
| ---- | ------- | --------- | ----------- | ------------ | ------------------------------ |
| 1024 | 0.0163  |—         | 0.0220      | +35%         | 完美对齐，v4 最佳                     |
| 1000 | 0.0166  | 0.0164    | 0.0220      | +33%         | 接近对齐，v4 几乎无退化                  |
| 1500 | 0.0221  | 0.0227    | 0.0300      | +36%         | **卡在中间**，v4 多跑一轮               |
| 1536 | 0.0217  | 0.0208    | 0.0285      | +31%         | 1536=1.5×1024，对齐到 4 倍数，v4.3 最佳 |
| 2048 | 0.0300  | 0.0284    | 0.0484      | +61%         | 完美 2×1024，cuBLAS 退化最严重         |


**几个规律**：

1. **v4 在 cols ∈ (k×1024， (k+1)×1024) 中间会退化**，因为多跑一轮循环但 warp 不满载
2. **v4.3 在 cols 是 packSize 倍数时与 v4 接近**，在 cols=1536/2048 这种"对齐到大粒度"时反而比 v4 快（少一次循环开销）
3. **cuBLAS 退化最严重**：因为它的基线本来就慢，多一轮循环把劣势放大
4. **v4 vs cuBLAS 的优势在大 cols 上越来越大**（cols=2048 时 v4 快 61%）

## 5. 设计哲学总结


| 维度            | v4                                     | v4.3                | cuBLAS    |
| ------------- | -------------------------------------- | ------------------- | --------- |
| **最佳场景**      | cols = blockSize×packSize 倍数           | cols = packSize 倍数  | 无         |
| **最差场景**      | cols 卡在（k， k+1）×blockSize×packSize 中间 | 同 v4                | cols 越大越差 |
| **设计取向**      | 让常见对齐尺寸最快                              | 让任意 packSize 倍数稳定   | 让所有尺寸都能跑  |
| **代码复杂度**     | 中（循环内分支）                               | 高（main + tail 显式分离） | 低（一个标量循环） |
| **cols=1024** | **0.0163 ms** ✨                        | —                   | 0.0220 ms |
| **cols=1500** | 0.0221 ms                              | 0.0227 ms           | 0.0300 ms |
| **cols=2048** | 0.0300 ms                              | **0.0284 ms** ✨     | 0.0484 ms |

## 6. 工程教训



### 教训 1：v4.3 的优势比想象中窄

v4.3 设计上是为非对齐场景兜底，但在 cols=1500 上反而比 v4 略慢。真正能让 v4.3 发力的场景是：

- cols 不是 packSize 的倍数（如 cols=1023、1001、1499）
- 此时 v4 会触发 warp divergence，v4.3 通过 tail 分离避免
- cols=1500 是 4 的倍数，tail=0，v4.3 没机会发挥

**结论**：v4.3 是"最后一公里"的优化，要看场景的概率分布决定是否值得维护两份代码。

### 教训 2：v4 的退化点是 cols 落在 1024 倍数的中间

v4 真正的弱点不是"非对齐"，而是**循环轮数刚好需要 1.x 轮**：

- cols=1023（1 轮，少几个元素）→ 不退化
- cols=1025（2 轮，第二轮只有 1 个元素）→ 大幅退化
- cols=1500（2 轮，第二轮约一半线程工作）→ 退化 35%
- cols=2048（2 轮，第二轮全员工作）→ 退化 84% 但仍快于 cuBLAS 61%

如果业务场景的 cols 经常落在 1024 倍数的"中间"，可以考虑动态调 blockSize（如 cols=1500 用 blockSize=384）让循环正好一轮覆盖。

### 教训 3：cuBLAS 的退化幅度比 v4 大，所以非对齐场景 gap 反而扩大

这是反直觉的发现：很多人以为"通用库在所有尺寸上稳定"，但实际上：

- cuBLAS 的时延绝对值更高（标量路径）
- 多跑一轮循环对它来说绝对开销更大
- 所以非对齐时 cuBLAS 退化得更厉害，v4 的相对优势反而扩大



### 教训 4：blockSize 和 packSize 的乘积才是真正的"对齐单位"

之前以为"32 倍数"（warp size）是关键，实际上对 v4 这种 grid-stride 循环来说， **blockSize × packSize = 1024** 才是关键单位。这个数决定了：

- 每轮循环覆盖多少元素
- 什么尺寸的 cols 会让最后一轮"半空"
- warp divergence 的触发条件

---



## 7. 结论

1. **v4 在 cols=1500 上退化 35%**（0.0163 → 0.0221 ms），印证了循环轮数对齐的重要性
2. **v4.3 在 cols=1500 上不比 v4 快**（0.0227 vs 0.0221），因为 cols=1500 是 4 的倍数，v4.3 没有 tail 可优化
3. **cuBLAS 在 cols=1500 上退化 37%**（0.0219 → 0.0300 ms），比 v4 退化得稍多
4. **v4 vs cuBLAS 的优势在非对齐场景下不降反升**：cols=1024 时 +26%，cols=1500 时 +36%，cols=2048 时 +61%
5. **v4.3 真正发力的场景是 cols 不是 packSize 倍数**（cols=1023、1499 等），cols=1500 不在这个范围
6. **手写 kernel 的非对齐鲁棒性比想象中好**，cuBLAS 的"稳定通用"在大 cols 上其实退化更严重

最关键的洞察：

> **真正决定 v4 性能的不是"cols 是否对齐到 32/8"，而是"cols 是否对齐到 blockSize × packSize"。** **如果业务有固定的 cols 模式，调整 blockSize 让循环恰好一轮覆盖，比写 main+tail 分离的 v4.3 更有效**。
