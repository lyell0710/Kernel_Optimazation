# SASS 编译期证据链(与运行时计数器互补)

## 1 这条路解决什么问题

版本梯的每一级都带一句「这一级改了什么、为什么快」。这两半要的是不同的证据:
**改了什么**是编译产物里的事实,**为什么快**是运行时行为。本文管前一半。

- `docs/ncu_reading_guide.md` 讲**有了计数器该看什么**——sector、命中率、
  stall 分解、achieved occupancy,全部是运行时观测量。本仓这一半已经补上:
  各算子 `project-proof/profiling/ncu/` 下有 51 份 RTX 4090 / CUDA 12.8 的
  `.ncu-rep`,闭环记录是 `records/EXP-K07`《采集主机 NCU 计数器闭环》。
- 本文讲**编译产物里能看到什么**——SASS 是编译期事实,`cuobjdump` 不初始化 CUDA、
  不打开设备节点、不需要任何权限,在共享机器上跑它对别人零影响。

两者互补而不互相替代。SASS 在三件事上比计数器更硬:它没有采样窗口与重放误差
(同一个二进制读一万次结果相同);它能证伪源码注释(「我写了 float4」是意图,
`LDG.E.128` 出现几条是事实);它能把「这一级只改了一件事」这种控制变量声明
变成可核对的账。计数器在另外三件事上是 SASS 永远给不了的:实际执行次数、
命中与冲突、时间。本文凡是碰到后三类,一律交给 `EXP-K07` 或仓内 `.ncu-rep`(§7.2),
不在这里硬推。

本文表格中的 REG / SMEM / 各判据条数,一律由 `scripts/sass_ladder.py` 产出:

```
python3 scripts/sass_ladder.py --op gemm          # 单算子
python3 scripts/sass_ladder.py --json             # 十算子,含完整助记符直方图
python3 scripts/sass_ladder.py --op w8a8 --mnemonics
python3 scripts/sass_ladder.py --recheck-sm89     # sm_75 产物的重编等价性核验
```

正文里另有五类数**不出自该脚本**,引用时按各自的出处读:
操作数复用标志 `.reuse` 的条数、指令地址与立即数偏移(如 `+0x8300`)、
主循环体的切片条数(要按回边定位循环体,脚本只给全 kernel 总数)、
PTX 层结论(`cuobjdump -ptx`)、理论 occupancy(脚本给 REG/SMEM,换算另做,见 §7.5)。
时延、带宽、TFLOPS 一概不来自本文,指针在各 `records/EXP-*`。

## 2 三档判定

| 判定 | 含义 | 该怎么用 |
|---|---|---|
| SASS 已证实 | 声称的改动在编译产物里有对应的指令级痕迹,且方向与声称一致 | 可以从「推断」升格为「编译期事实」写进 README/讲稿,证据指针写本脚本 |
| SASS 证伪或与记载不符 | 编译产物与记载矛盾,或记载的机理在产物里查无此物 | 必须改记载。改文字还是改代码见 §6 的分类 |
| SASS 答不了 | 命题本质上是运行时量(时间、字节、命中、冲突、并发) | 见 §7 的替代办法;确实还没有数据的见 §8 |

一条贯穿全文的纪律:**指令条数不是字节账。** 一条 `LDG` 是一次 LSU 请求,
warp 内合并、L1/L2 命中都发生在这条指令之后。指令数降 32 倍不代表显存流量降
32 倍——`gemm` v0→v1 正是这个坑(§5.1)。凡是把 LDG 条数当 DRAM 字节用的地方,
本文一律降级为「指令数」并单独标出。

## 3 判据速查(修正版)

| 判据 | 读法 | 陷阱 |
|---|---|---|
| `HMMA` / `IMMA` / `OMMA` | Tensor Core 矩阵乘。非零 = 真上了 Tensor Core | 形状写在助记符里(`HMMA.16816.F32` = m16n8k16) |
| `IDP.4A` | dp4a 整数点积。**不占用 Tensor Core** | 与 IMMA 是两条不同的路 |
| `LDSM` | ldmatrix。`LDS` 是它的字符串前缀,必须分开数 | `grep -E '^LDS'` 会把它算进普通 shared load |
| `LDGSTS` / `LDGDEPBAR` / `DEPBAR` | cp.async。`grep -c LDG` 会把三者加在一起 | 见 §5.1 的口径事故 |
| `DEPBAR.LE SB0, 0xN` 的立即数 | 流水级数 = `__pipeline_wait_prior(N)` 的实参,是编译期常量,不需要任何运行时观测 | 助记符直方图会丢掉操作数,脚本另存一份立即数列表 |
| `LDG` / `STG` 的宽度后缀 | 单条访存指令覆盖的字节 | **必须含 16 位与 8 位桶**;bf16/half 算子的访存全在 `.U16` 里,只看 32/64/128 会得出「不访存」 |
| `LDS` / `STS` | shared 读写(活指令) | ptxas 会插 `@!PT LDS RZ, [RZ]` 死指令,必须排除 |
| `SHFL` | warp shuffle。`.BFLY` 是 `__shfl_xor_sync`,`.DOWN` 是 `__shfl_down_sync` | 尾部 `RET.REL.NODEC` 段里可能有变量偏移的冷桩,不在热路径 |
| `MUFU` | 特殊函数单元。子助记符区分 `EX2`/`SIN`/`COS`/`RCP`/`RSQ` | 整数除法的模拟代码也产生 `MUFU.RCP`,与算子数学无关 |
| `BAR.SYNC` | `__syncthreads` | `BSSY`/`BSYNC` 是分支重收敛,不是 barrier,必须分开 |
| `BRA` | 算法自身的循环回边与条件跳转 | `BRA.CONV`(子程序调用点的收敛跳转,与 `CALL.REL.NOINC` 成对)与 `BRA.DIV`(发散跳转)各占一个键;并进 `BRA` 会凭空造出分支,`cuda-reduce` v4 就是这么被数成 14 条的(实为 2 + 12) |
| `CS2R` | 累加器清零。`CS2R Rn, SRZ` 的条数 ≈ accumulator 寄存器组数 | 用来锁死 fragment 数比 HMMA 条数更干净 |
| `LDL` / `STL` | local memory = 寄存器溢出 | 全仓十算子此项恒为 0,没有一个 kernel 溢出 |
| `-res-usage` 的 REG / SHARED | 编译期资源,理论 occupancy 的输入 | SHARED **只算静态**;`extern __shared__` 的 kernel 这里恒为 0 |

## 4 计数口径:五个会把结论带偏的坑

1. **谓词恒假的死指令。** ptxas 在 cp.async 代码里插 `@!PT LDS RZ, [RZ]` 占位:
   `gemm` v3/v4 各 12 条、`flash-attn` v4 有 9 条。它们计入反汇编总条数但永不执行。
   本文所有判据只计活指令。这一条不执行会直接读错结论——把 `flash-attn` v4 的
   LDS 记成 70(含死指令)而不是 61(活),v3→v4 的 LDS 增量会从 +2 被放大成 +11,
   足以撑起一个「v4 自己变胖了」的错误竞争解释。
2. **名字互为子串。** `v1_kernel` ⊂ `dequant_v1_kernel` ⊂ `gemv_v1_kernel`
   同处 `w8a8_ext.so`。必须按 `Function :` 段切,且右边界要认 fatbin 段头,
   否则每个编译单元的最后一个 kernel 会把下一个 fatbin 吞进去。
3. **静态条数不是动态条数。** `#pragma unroll` 的编译期常数循环里,静态条数
   等于每次迭代的动态条数;运行时上界的循环里,静态条数只反映展开体大小。
   比较两版的「每元素成本」必须先切热循环体、再除以该循环体处理的元素数,
   直接比全 kernel 总条数会被展开度差异骗到(`gemv` v0 224 条 vs v1 153 条,
   但每元素 3.44 条 vs 4.88 条,方向相反;两组都是 sm_75 口径,见第 5 条)。
4. **总条数里混着与算子无关的固定开销。** 本仓多处 `/` 与整数除法被编成完整
   IEEE 慢路径子程序(`FCHK` + `MUFU.RCP` + `CALL.REL.NOINC` + 大量 `BRA`),
   `rope` 全梯的 `MUFU.RCP` 与 `IMAD*` 大头都来自它。把 total_inst 当
   「kernel 复杂度」用之前必须先剔掉这段。
5. **arch 会骗人。** `softmax` / `gemv` / `int8-quantize` / `cuda-reduce`
   四个二进制是 `sm_75` 编的(各自 `CMakeLists.txt` 未设 `CMAKE_CUDA_ARCHITECTURES`,
   用了 CMake 默认值);`gemm` / `flash-attn` 与四个 torch 扩展是 `sm_89`。
   sm_75 与 sm_89 跨 major 不二进制兼容,4090 上实际执行的是驱动 JIT 出来的
   sm_89 码,不是 `cuobjdump` 读到的这一份。脚本对非 sm_89 会告警。

   重编等价性核验已落盘为 `python3 scripts/sass_ladder.py --recheck-sm89`
   (抽内嵌 PTX → 改写 `.target` → 本机 `ptxas -arch=sm_89 -O3` → 逐项对比,全程静态)。
   核验结果**不是「逐项一致」**,必须分成两类看:

   - **跨 arch 稳定**:全部 `LDG`/`STG` 宽度桶、`LDS`、`STS`、`LDSM`、`SHFL`、
     `BAR.SYNC`、`BSSY`、`MUFU`、`FFMA`、`DP4A`、`LOCAL`、`BRA.CONV`——四个二进制
     34 个 kernel 无一项不同。以这些判据为论据的结论对 4090 成立。
   - **跨 arch 不稳定**:**活指令总数**(34 个 kernel 里最大相对差是 `cuda-reduce` v4 的
     112→101,−9.8%;其次 `cub:tile` 951→881、`baseline` 114→122,其余都在 5% 内)、
     **`IMAD*`**(34 个里 19 个不同,而且差得更狠:`int8-quantize` v4 52→60、
     `cuda-reduce` v4 14→9、`cub:tile` 49→24、`cuda-reduce` baseline 1→6)、
     **`BRA` / `BRA.DIV`**(只有 `softmax` v4 与 v4.3 两个,各是 66→68 / 70→72
     与 2→4)、以及**寄存器数**(34 个里 22 个不同,`softmax` v4.3/v4.4 62→40、
     `gemv` v2 66→50 是差得最大的)。

   **凡以活指令总数、`IMAD*`、`BRA`、REG 为论据的结论,下文一律标注「sm_75 口径,
   4090 上不执行这一份码」**,并在能算的地方给出 sm_89 重编值。
   重编值本身也不是「4090 上真正执行的那份」——驱动 JIT 用的是驱动内置的 ptxas,
   版本与开关未必与本机一致;它给的是「哪些判据跨 arch 稳定」这条弱一些的结论。
   一条独立佐证:仓内 4090 的 `.ncu-rep` 报的 registers-per-thread 与本机 sm_89
   重编值逐个吻合(`softmax` baseline/v0/v3/v4.3 = 39/40/36/40,与重编完全相同,
   与 sm_75 的 43/46/48/62 全都不同),说明重编这一路确实站在 sm_89 这一侧。

## 5 逐算子证据链

每节先给判据表,再逐级判定。表中 `SMEM (B)` 的 `dyn?` 表示静态 shared 为 0,
该 kernel 可能用 `extern __shared__`,真实用量在 launch 语句里、SASS 看不到。

### 5.1 gemm(fp16 4096³,sm_89)

| 版本 | REG | SMEM (B) | 活指令 | HMMA | LDSM | LDGSTS | LDGDEPBAR | LDG.128 | LDG.16 | STG.32 | LDS | STS | BAR.SYNC | FFMA | IMAD* |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| v0 朴素 | 26 | dyn? | 89 | 0 | 0 | 0 | 0 | 0 | 10 | 0 | 0 | 0 | 0 | 5 | 22 |
| v1 smem tile | 33 | 4096 | 178 | 0 | 0 | 0 | 0 | 0 | 2 | 0 | 40 | 2 | 2 | 32 | 7 |
| v2 wmma | 54 | 8192 | 215 | 16 | 8 | 0 | 0 | 2 | 0 | 16 | 0 | 2 | 2 | 0 | 44 |
| v3 cp.async 双缓冲 | 61 | 16384 | 261 | 16 | 8 | 4 | 2 | 0 | 0 | 16 | 0 | 0 | 2 | 0 | 64 |
| v4 128² tile | 92 | 32768 | 377 | 32 | 12 | 4 | 2 | 0 | 0 | 32 | 0 | 0 | 2 | 0 | 78 |

cp.async 流水级数(`DEPBAR` 立即数):v3 与 v4 都是 `SB0, 0x1` 与 `SB0, 0x0` 各一条。

**v0 → v1「32×32 smem tile」——部分证实。** smem tile 与两处 `__syncthreads` 实锤
(SHARED 0→4096 B、STS 0→2、LDS 0→40、BAR.SYNC 0→2);指令世代确未动
(HMMA/LDSM 仍为 0,算术仍是 CUDA core 的 FFMA 5→32)。
但两处必须降级:其一,每线程每 k 步的全局 load **指令数**降 32 倍
(v0 每 k 步 2 条 `LDG.E.U16`,v1 每 32 步的 K 块共 2 条),这不是字节数——
v0 的 block 是 `dim3(16,16)`,一个 warp 的 B 请求本就被合并、A 请求本就被广播。
按 tile 形状推算(非实测):v0 每个 block 每个 k 步只触及 16 个 A + 16 个 B 元素
服务 256 个输出(0.125 个不同元素/输出/k 步),v1 是 64 个服务 1024 个输出(0.0625)——
**不同元素的流量只降 2 倍**,差出来的 16 倍在 v0 里早已由 warp 合并与 L1 收敛掉;
4096³ 下 A+B 共 67.1 MB,完整驻留 4090 的 72 MB L2,两版的强制 DRAM 流量都是
A+B+C ≈ 101 MB,离带宽墙极远。其二,本级并非单变量:`gemm_v0.cu` 的 block 是
`dim3(16,16)`、`gemm_v1.cu` 是 `dim3(32,32)`,tile 形状、block 线程数(256→1024)、
理论 occupancy(100% 线程数限 → 66.7% 寄存器限,按 sm_89 的 65536 reg/SM、
1536 thr/SM、256 分配粒度算)三项同时变化。

**v1 → v2「wmma 16³ fragment」——证实。** HMMA 0→16 且全部是 `HMMA.16816.F32`,
LDSM 0→8(4 条 `M88.4` 喂 matrix_a、4 条 `MT88.4` 喂 row_major matrix_b),
CUDA core 算术彻底归零(FFMA 32→0)。但源码文件头「访存策略刻意保持与 v1 同级的
朴素,使 v1→v2 的差异只剩指令世代」被证伪:同一级里访存宽度也变了
(`LDG.E.U16` 2 B/条 → `LDG.E.128` 16 B/条,STS 同样从 `.U16` 变 `.128`),
tile 与每线程工作量也变了(32²→64²、每线程 1 个输出 → 32 个)。三者合力,
SASS 给不出指令世代单独的权重。

**v2 → v3「cp.async 双缓冲」——证实,且这一级是纯替换、没有叠加。**
`LDGSTS.E.BYPASS.128` 0→4、`LDGDEPBAR` 0→2、`DEPBAR` 0→2;更强的一条是
`LDG.128` 2→0 且 `STS` 2→0——global→寄存器→shared 的中转被整条替换掉,
不是叠加。计算段一字未改(HMMA 16、LDSM 8 与 v2 逐条相同)。
流水级数直接写在立即数里:主循环内 `DEPBAR.LE SB0, 0x1`
(等到未完成的 cp.async 组数 ≤1,即放过刚 commit 的预取),被剥离的末轮
`DEPBAR.LE SB0, 0x0`(清空),与源码 `__pipeline_wait_prior(k0+BK<K ? 1 : 0)`
的两个取值逐字对应。这条不需要任何运行时观测。

**v3 → v4「128² tile」——证实。** HMMA 16→32、LDSM 8→12、STG.32 16→32、
SHARED 16384→32768 B、REG 61→92;cp.async 调度完全继承
(LDGSTS/LDGDEPBAR/DEPBAR 保持 4/2/2,两条 DEPBAR 立即数仍是 1/0,BAR.SYNC 仍是 2)。
锁死「每 warp accumulator fragment 由 4 变 8」的是 `CS2R`(累加器清零)条数
**32 / 33 / 65**(v2/v3/v4):HMMA 条数翻倍本身也可以由 BK 翻倍产生,
CS2R 才排除掉这个替代解释。

**v3 → v4「算术强度翻倍」——需要改口径。** 按 roofline 定义,算术强度 =
FLOP / DRAM 字节;4096³ 的强制 DRAM 流量在 v2/v3/v4 恒为约 101 MB,**没有变化**。
SASS 支持的是另一句:每条 HMMA 摊到的**全局请求字节**由 128 B 降到 64 B
(每 K 块每 block 的全局字节 8192→16384 B,warp 级 HMMA 条数 64→256),
fragment 级复用同向(LDSM/HMMA 由 8/16 = 0.500 降到 12/32 = 0.375)。
这一级压的是 L2 请求速率,不是 HBM 带宽。措辞应写「每条 mma 摊到的 L2 请求字节减半」。

**v3 → v4「33% occupancy 最低却最快,靠 fragment 级 ILP」——部分证实。**
「无相互依赖」这半 SASS 证得到:v4 主循环 32 条 HMMA 的目的寄存器落在 17 个互不
重叠的组(16 条独立累加链 + 1 个换名临时),约 64 个寄存器常驻累加器,
占 92 reg 的七成;v2/v3 只有 9 个组。操作数复用标志 `.reuse` 随之增长
(v2 15 / v3 24 / v4 43)。理论 occupancy 由编译期资源算得,不需计数器:
按 sm_89 常数得 v0 100% / v1 66.7% / v2 75%(reg 限)/ v3 50%(smem 限)/
v4 33.3%(reg 限),33% 确为全梯最低。**但因果证不到**,而且有一个产生同样
SASS 与 res-usage 签名的竞争解释:128² tile 让 block 数降到四分之一,
同一份 A/B 面板被重复拉取的 block 数随之降到四分之一,L2 层面的跨 block 复用
整块改善。分离二者的实验见 §7.3。

**v4 → cuBLAS 的剩余差距——SASS 只能给一个带宽占用上界,归因要看计数器。**
bank conflict 是运行时事件,SASS 只能看到 `LDSM.16.M88.4`/`MT88.4` 与地址寄存器。
静态旁证有两条:v2/v3/v4 的 shared 地址由普通 `IMAD`/`LEA` 线性算出,未见 XOR 换算
(无 `LOP3.LUT` 参与地址),与「wmma 不暴露 smem swizzle」一致;流水级数确为 2 级
(`DEPBAR.LE SB0, 0x1`),「无 >2 级流水」属实且是编译期事实。

编译期算术能给出的只有一条**smem 带宽占用上界**:v4 每 block 每 K 块的 smem 流量
= LDSM 12 条/warp × 512 B × 8 warp + LDGSTS 16384 B = 65536 B;grid 1024 block
(4096/128 的平方)、每 block 128 个 K 块(BK = 32),合计 8.59 GB,除以
`records/EXP-K02` 的 v4 时延 1.0330 ms 得 **8.3 TB/s**,是 Ada 无冲突 smem 屋顶
(128 SM × 128 B/clk × 2.52 GHz ≈ 41.3 TB/s)的 20.1%。

**这个比值只说明「无冲突口径下 smem 带宽没有饱和」,它不约束 bank conflict 的
延迟贡献。** 冲突的代价是同一条 shared 指令被拆成多个 wavefront 串行重放,
打的是依赖链延迟与 LSU 发射位,不是带宽占用;一个带宽占用只有两成的 kernel
完全可以被冲突拖死。用带宽比值去卡冲突的延迟贡献是换错了仪器。

正确的仪器现在就在仓里。`gemm/project-proof/profiling/ncu/gemm_v4_bigtile_profile.ncu-rep`
与 `gemm_cublas_profile.ncu-rep`(RTX 4090 / CUDA 12.8,单一 grid,口径同
`records/EXP-K07` §5.1)离线读出:

| kernel | grid | shared-load wavefront | 其中冲突 wavefront | 冲突占比 |
|---|---|---|---|---|
| `gemm_v4_kernel` | (32,32,1) | 268,862,879 | 218,125,616 | **81.1%** |
| `gemm_v3_kernel` | (64,64,1) | 404,124,369 | 335,587,066 | 83.0% |
| `gemm_v2_kernel` | (64,64,1) | 404,228,981 | 335,607,866 | 83.0% |
| `ampere_fp16_s1688gemm_fp16_128x128`(真 cuBLAS) | (32,32,3) | 35,828,655 | 101,720 | **0.28%** |

读法:`ncu --import <rep> --page raw --csv`,列名
`l1tex__data_pipe_lsu_wavefronts_mem_shared_op_ld.sum` 与

**v0 基线「warp-per-row 在线 softmax」——证实。** v0 是全梯唯一零 smem、零 barrier
的 kernel;归约确为 warp shuffle(15 条 `SHFL.BFLY`,蝶式 5 个 offset × 展开份数);
K/V/Q 全部直读 global 且全是 2 字节标量(28 条 `LDG.E.U16`)。

**v0 → v1「唯一变量 = K/V 读取层级」——证伪,至少动了三件事。**
smem 化本身确证(SHARED 0→32768 B = 源码 `Ks+Vs` 各 16 KB,STS 0→2 均为 `.128`,
LDS 0→8 均为 `.64`,BAR.SYNC 0→2)。但同时改的还有:global load 宽度与发射条数
(`LDG.E.U16` 28→4,K/V 的读从每 lane 每 key 8 条 2 字节标量变成每 8 线程一条
16 字节 `LDG.E.128` + `STS.128` 中转);以及 launch 几何——`fa2_v0.cu` 是
`<<<dim3(S,Hq,B), 32>>>`(1 warp/block),`fa2_v1.cu` 是 `<<<dim3((S+3)/4,Hq,B), 128>>>`
(4 warp/block),按 sm_89 常数理论 occupancy 从 50%(受每 SM 24 block 上限)
掉到 25%(受 32 KB 静态 smem 限)。
附带一条与归因直接冲突的事实:`flash-attn/project-proof/data/derived_fa2_proto_stability.csv`
(3 轮)四个尺寸里,v1 只在 S=4096 快 9.6%,S=512/1024/2048 分别慢 11.0%/1.2%/1.1%;
而全部 8 个 kv-head 的 K+V 在 S=4096 也只有 16.8 MB,远在 72 MB L2 之内——
符号翻转与 L2 容量对不上,「L2 已扛住广播读」这条归因在自家数据上就不成立。

**v1 → v2「wmma QK^T/PV + smem 往返 softmax」——证实。**
HMMA 0→128 且与源码全展开循环逐次对得上(4×8 + 8×4 = 64 次 mma_sync × 2 条);
LDSM 0→96 = 32 条 `MT88.4`(K^T 视图)+ 64 条 `M88.4`(P 与 V);
相位链 BAR.SYNC 2→6(循环内 5 次 + 收尾 1 次),与源码「5 段相位链」精确吻合;
softmax 退回单线程扫行(SHFL 16→0);Q 常驻寄存器确证——32 条 `LDG.E` 全部落在
第一条 BAR.SYNC 之前,循环体内没有任何 Q 的 global load。REG 40→72 与源码文件头
逐字吻合。

**v2 → v3「只改并行组织」——降级为部分证实。** 每线程各判据恰好减半、线程数恰好
翻倍,block 级总量逐条相等(HMMA 128→64、LDSM 96→48、block 级 wmma 相位 smem 指令
两版都是 704 条/tile)。但这是恒等式而非判据:任何把同样总工作量摊到 2 倍线程上的
改动都自动满足它,包括同时换了一套 smem 地址映射的改动——而地址映射正是 bank conflict
的唯一决定因素。而且同一份 res-usage 里有反向信号:每线程工作量减半而
REG 72→95(+32%)、IMAD* 124→156、BRA 39→47(另新增 2 条 `BRA.DIV`)。可以写「block 级 wmma 与 smem 的
指令条数、字节数不变」,不能写「算法与 smem 布局逐字节不变」。

**v3 → v4「cp.async 与 half S/P」——证实。**
`LDGSTS.E.BYPASS.128` 0→3,目标 smem 偏移与源码常数逐字节对上
(`+0xa700` = 42752 = `OFF_K`、`+0x12700` = 75520 = `OFF_V`);`LDGDEPBAR` 0→3;
同时 `LDG.128` 2→0、`STS.128` 2→0,寄存器中转被替换而非叠加。
half S/P 也确证:S 的写侧由 `STS.64`(fp32,步长 `+0x880` = 68 float × 8 行 × 4 B)
变成 32 位 `STS`(步长 `+0x480` = 72 half × 8 行 × 2 B),读侧由 32 位 `LDS`
变成 `LDS.U16` 并新增 39 条 `HADD2.F32`;P 原位改写确证——8 条 `STS.U16` 的地址是
`[R49+0x8300..]`,`0x8300` = 33536 = 源码 `OFF_SP`,与 S 同址。

**v3 → v4「瓶颈在相位链」——部分证实,且原报告的一处数字要更正。**
SASS 支持前提:相位链一条没动(BAR.SYNC 仍是 6,HMMA 64、LDSM 48 与 v3 逐条相同)。
但反向代价被夸大过:v4 的 LDS 是 **61 条活指令**(另有 9 条 `@!PT LDS RZ, [RZ]`
死指令),v3 是 59,真实增量是 +2 而不是 +11。去掉这个虚增之后,
「v4 自己变胖了」这个竞争解释明显变弱,证据反而更支持「剩下的时间在相位链上」。

**「smem 往返是主因」这条已经不再需要靠 SASS 推,`records/EXP-K07` §5.4 / §6.5
有实测。** 该记录在 S=4096 协议点 `(64,32,1)` 上给出:v4 的 `short_scoreboard`
(shared 访问 stall)达 **50.13%**,是第二名 barrier(13.86%)的 3.6 倍;
同一个 kernel 的 `long_scoreboard`(全局访存延迟)已降到 **0.31%**。
v2→v3→v4 的 short_scoreboard 单调上升(39.95 → 45.09 → 50.13%)——每优化一版,
瓶颈就更向 smem 集中一分。**该记录同时钉死了这条结论的边界:本轮只证明了
smem 是瓶颈,没有证明 swizzle 能解决它**(`EXP-K07` §7.4 第 5 条:读侧的 578 M
bank conflict 未做 swizzle 前后对照)。对外措辞必须把这两件事分开。

编译期算术在这里只剩一个**smem 带宽占用上界**,留作交叉校验、不作归因:
v2 每 block 每 tile 的 wmma 相位 smem 流量 278528 B 加上第四段 O 的读写 65536 B,
按 causal 的 block-tile 数(每头 Σ(i+1), i=0..63 = 2080,×32 头 = 66560)展开,
除以 `derived_fa2_proto_stability.csv` 的 v2 时延 5.6354 ms,得 **4.1 TB/s**,
是无冲突 smem 屋顶 41.3 TB/s 的 9.8%。**这个比值只说明无冲突口径下带宽没饱和,
它不约束 bank conflict 的延迟贡献**——冲突的代价是 wavefront 串行重放带来的
依赖链延迟,不是带宽占用,而 v2 恰恰是 barrier 串起来的相位链,最不可能被
「带宽占用率」约束住。上面 50.13% 的 stall 与这条 9.8% 的带宽占用并不矛盾:
一个说时间花在等 shared,一个说 shared 的数据通路没被填满,合起来正是
「冲突/串行化而非带宽」的画像。红线表的措辞与解锁条件以 `LEDGER.md` 为准。

**v0 → v1「融合成单 kernel」——证实(仅对指令数)。**
符号层 2 个 entry 变 1 个;每元素全局访存指令 v0 = 5 条 `LDG.E.U16` + 2 条
`STG.E.U16`,v1 = 4 + 2,剔除跨行复用的权重后正是 5→4 次读写指令,
消失的那一条就是 `v0_rmsnorm` 第一遍的 `row[i]` 读。
这一条落到 DRAM 字节的理由不在 SASS 里而在工作集:中间 residual 张量在
T=32768/H=4096 下是 268 MB,远超 72 MB L2,且跨 kernel 边界,是真 DRAM 往返。
判据是工作集尺寸与时间距离,不是指令条数——同类指令证据在 v3→v4 上得出的是相反结论。

**v1 → v2「warp shuffle 归约」——证实。** SHFL 0→11(两次 `warp_reduce_sum`
各 5 条直线码 + 1 条发散回退子程序里的冷桩);v1 的树形归约在 SASS 里是真循环
(循环体 = 2 LDS + 1 STS + 1 BAR.SYNC,回边可见),v2 是全直线码。
按实测 blockDim=1024 展开动态条数:BAR.SYNC 12→2、LDS 21→2、STS 11→2。
静态 shared 也从 `extern` 的 4096 B 降到 128 B。访存不变亦确认(LDG.16 4 条、
STG.16 2 条,两版逐条相同)。注意源码注释按 blockDim=512 算账,而 H=4096 时
`bs` 被夹到 1024,注释里的「同步 9 次降到 2 次」按实际是 12 次降到 2 次。

**v2 → v3「16 B 向量化访存」——原为证伪;根因已定位并修复,现已兑现。**

修复前的事实是:整个 `fused_norm_ext.so` 里 `LDG.E.128` = 0、`LDG.E.64` = 0、
`STG.E.128` = 0、`STG.E.64` = 0;v3 的每个 `BF16x8` 被拆成 4 条 32 位访问
(单寄存器目的、偏移 `+0x0/+0x4/+0x8/+0xc`),计数上是 16 条 `LDG.32` + 8 条 `STG.32`。
丢失发生在 nvcc 前端而非 ptxas:PTX 里已经是 `ld.global.v2.u16` ×4 与
`st.global.u32` ×4,从未出现 `v4.u32`。工具链本身会发 128 位——同机 `gemm_bench`
里有 `LDG.E.128`,`int8-quantize` v4 也有。

**根因不是 SROA、也不是对齐证不出来。** 做过静态对照编译:同样被 SROA、同样
`alignas(16)`、同样运行期下标的 `struct{unsigned w0..w3}` 照样出 `LDG.E.128`。
判别变量是聚合体的成员类型是 `__nv_bfloat162`(一个 2×16 位向量类型),
NVVM 的 load/store vectorizer 合并到 `v2.u16`(4 B)就停了。
`alignas(16)` 只保证**地址对齐**,不强制向量化;nvcc 按成员类型逐个生成访存,
对齐属性只是让它敢于假设基址对齐,不改变它切分访存的粒度。

**修法是换载体,不动数学也不动调用点。** `fused_norm_v3.cu` / `fused_norm_v4.cu`
里的 `struct alignas(16) BF16x8` 从 `{ __nv_bfloat162 h[4]; }` 改成
`union { float4 raw; __nv_bfloat162 h[4]; }` 加显式拷贝构造与拷贝赋值
(两者都写 `raw = o.raw`),整体赋值于是走 `float4` 这条 128 位通路,
逐元素计算仍从 `h[]` 视图读。**调用点一行未改**——所有 `BF16x8 v = p[i];` /
`p[i] = v;` 保持原样。

**验证分两层,静态那层就足以判定。** 静态:重编后 v3 是 4 条 `LDG.E.128`
(其中 2 条 `.CONSTANT`)+ 2 条 `STG.E.128`,`LDG.32` 与 `STG.32` 双双归零,
恰好是「若真发 128 位应各是 4 条与 2 条」这条修复前就写死的预测值;
v4<1> 是 3 条 `LDG.E.128` + 2 条 `STG.E.128`,模板四实例的 `LDG.128` 是
3/6/12/24、`STG.128` 是 2/4/8/16,随 `MAX_WAVES` 线性展开。
全程 `cuobjdump`,不碰 GPU。运行时那层是 `EXP-K08` 的同环境 A/B(修复前后各 3 轮,
raw 在 `fused-norm/project-proof/data/20260829T0304_fused-norm_vec-{before,after}_r{1,2,3}.csv`):
L2 常驻区间 v3/v4 显著上涨、HBM 区间落在 std 内、`max_rel_err` 与修复前逐位相同,
未使用 `BF16x8` 的 v1/v2 对照组同轮次只动 +0.1%,所以增益可归因到向量化。
这些是本文管不着的量,按 §9 第 4 条交给该记录,具体数字不在此复述。

指令层的净改动因此从「访存宽度 2 B/条 → 4 B/条、每元素访存指令 6→3」
更正为:**宽度 2 B/条 → 16 B/条,每元素访存指令 6 → 0.75(8 倍,与源码承诺一致)**。
每 8 个元素 v2 要发 48 条访存指令(4 `LDG.16` + 2 `STG.16`,×8),v3 只发 6 条。

**v2 → v3 在 HBM 区间的零收益——README 的带宽墙解释成立且必要,不受修复影响。**
HBM 区间 v2/v3/v4 都卡在约 91% 峰值上,墙在那里,与访存指令宽度无关;
修复后 HBM 区间的变化落在 3 轮 std 内(`EXP-K08` §5),这条解释因此更硬而不是更软。
变的是 L2 区间:修复前这一级在 L2 区间就有台阶,修复后又涨了一截,
且 v4 由慢于 v3 变为快于 v3——「寄存器缓存消第二次读」原本被未向量化的访存开销淹没,
每省下一次读要先付 4 条 32 位访存指令的开销,现在才兑现。
这个定性反转要单独记一条:被证伪的那一级掩盖了下一级的收益,
修好之后版本梯的顺序才与设计意图一致(`EXP-K08` §6)。涨幅本身是 bench 侧的量,本文不复述。

**修复前的计数器数据必须整体标注为「修复前」。** `EXP-K07` §6.4 读出 v3/v4 的
L1TEX 全局读扇区是 v1/v2 的 4 倍(16.000/12.000×S 对 4.000×S),而 DRAM 侧恒为
2.000×S——**这批 `.ncu-rep` 采的是未向量化的 `.so`**,4 倍扇区放大正是
「向量化未兑现」在计数器上的独立复现,是那一代实现的有效历史基线,不作废、不删除;
但它**不描述当前代码**。修复后每个请求覆盖 16 B,扇区数与请求数都应当变,
具体变成什么必须重采才知道(§8 缺口表第四行)。引用这组数时一律写明
「对应修复前的版本」,不要拿它去解释现在的 `.so`。

另外这一级并非只动访存宽度:`fused_norm_v2.cu` 的 `bs` 在 H=4096 时是 1024,
`fused_norm_v3.cu` 是 512,按 sm_89 常数理论 occupancy 从 66.7% 提到 100%(§6.3)。
修复前对 HBM 区间零收益的解释是「向量化只兑现四分之一」与「occupancy 提高 1.5 倍」
两个反向变量的净结果;修复后第一个变量没有了,HBM 区间的零收益只剩带宽墙一个解释。

**v3 → v4「寄存器缓存消第二次读」——证实(仅对指令数)。**
`LDG.128` 4→3,按位置精确对上:v3 第二个循环里有 1 条 `LDG.E.128`(重读 residual)
+ 1 条 `LDG.E.128.CONSTANT`(权重),v4 只剩权重那 1 条。
(修复前同一条判据是 `LDG.32` 16→12,4 条重读 + 4 条权重减为 4 条;
向量化把每一组 4 条 32 位合并成 1 条 128 位,消掉的仍是同一次重读。)
但「字节账 5→4/元素」要降级:被消掉的地址正是本线程第一遍刚用 `STG.E` 写过的
同一个 `res[i]`,同一线程先写后读同一地址必然命中缓存,从来不到 DRAM。
这一条现在有实测:`records/EXP-K07` §5.3 / §6.3 给出 v1..v4 的 DRAM 读扇区
**恒为 2.000×S**(= 算法下界),v3/v4 之比 1.0001;**而且把机制层级钉在 L1**
——v4 的 L1 命中率 83.19%(与 1 − 2/12 = 83.33% 吻合),L2 命中率只有 0.94%。
所以措辞是「被 **L1** 接住」,不是「被 L2 接住」;后者是本仓多处旧文的说法,
`EXP-K07` §8 已列出逐个回写的位置。本文对应的措辞是
「每元素的全局访问次数 5→4(向量化之后落到指令上是每 8 元素 4 条 `LDG.128` → 3 条),
DRAM 字节不变」。

**模板常量下标防止 `cache[]` 掉进 local memory——证实,而且这一条 SASS 比 NCU 更直接。**
全 `.so` 里 `LDL`/`STL` = 0,`-res-usage` 对四个 v4 实例都给 `STACK:0 LOCAL:0`;
寄存器随模板参数单调上升(24/29/38/48),证明 `cache[]` 真在寄存器里。
源码注释说要用 ncu 看 local 计数,其实 cuobjdump 静态就能判死。

`MUFU` 分解:v0 是 5 条 `RCP`,v1/v2/v3 各 3 条 `RCP`(全部来自整数除法模拟,
与算子数学无关),v4 是 8 条 `SIN` + 8 条 `COS` + 3 条 `RCP`。

**v0 → v1「一线程一对,读 2 写 2」——证实。** 每迭代处理的元素数 1→2;
折算每元素:数据读 2→1、表读 2→1、写 1→1。就地更新也由符号确证:
v0 的 4 条 load 全带 `.CONSTANT`(只读 src),v1 的数据侧 2 条是不带 `.CONSTANT`
的 `LDG.E.U16`(与 `STG.E.U16` 同址)。
但「1.81 倍主要来自消掉临时缓冲而非少读 cos」是归因命题,SASS 判不了;
而且 v0 的那份整量 D2D 拷贝根本不在 kernel 里(是 host 侧 `cudaMemcpyAsync`),
`rope_v0.cu` 字节账里的「临时缓冲 2」在 SASS 里查无此物。

**v1 → v2「q/k 合并进一次 launch」——访存部分证实,代价的机理证伪。**
访存指令逐条相同(每迭代 2 条 `LDG.E.U16` + 2 条 `LDG.E.U16.CONSTANT` + 2 条
`STG.E.U16`),两版总条数同为 223/224。
但 `rope_v2.cu:15` 的「代价:kernel 里多了一次分支」不成立:BRA 静态条数
两版都是 6,循环体内每迭代执行的 BRA 都是 3。q/k 选择被完全谓词化成 `SEL`
(v2 循环体 SEL=5、v1=0)。结论(发散可忽略)比作者说的还强,机理写错了——
真正的代价是主循环体活指令 111→120(+8%),多出来的是 5 条 `SEL`、
2 条 `ISETP` 与若干条地址运算。

**v2 → v3「16 B 向量化」——证伪(与 fused-norm 修复前是同一个成因,此处尚未修)。**
v3 的 `LDG.E.128` = 0、`STG.E.128` = 0;4 个 16 B 块各被拆成 4 条 32 位访存。
同一 `.so` 里的对照组直接证明不是 ptxas 不会:v4 的 `const float4*` 读
确实编成了 2 条 `LDG.E.128.CONSTANT`。所以「16 B/lane 后一次请求」不成立,
实际是 4 次请求;「每线程 16 B 连续足迹」成立(地址仍是 `+0..+0xf` 连续)。
修法已在 fused-norm 上验证(§5.3 的 union 载体),搬过来即可;本节数字对应未修版本。

**v2 → v3 有一块 README 没记的收益——证实。**
按「主循环体活指令 ÷ 该循环体处理的元素数」这个口径(下同),
每元素指令数 v2 = 120/2 = 60、v3 = 201/16 = 12.6,降 4.8 倍;
而同一级的每元素访存指令只从 3 条降到 1.5 条(2 倍)。
差出来的那一大截是下标运算被摊薄——每个循环体里固定要做两次 64 位整数除法的
模拟代码(`i/hv` 与 `hp/Hh`,除数是运行期 int,ptxas 生成
`MUFU.RCP` 牛顿迭代快路径 + `CALL.REL.NOINC` 全 64 位慢路径的双路结构),
v2 把它摊到 2 个元素上,v3 摊到 16 个。
README 把这一级的收益全部归给访存宽度,SASS 显示下标运算摊薄至少同量级。
若把 `half`/`hv`/`Hh` 做成模板常量或改用 magic-number 乘法,v0-v2 应该还能再快一档——
这是一条 SASS 直接指出、README 里没有的优化方向。
不过量级上要限定:该级在 HBM 区间可供分配的因果预算本就只有约 15 个点
(v3 已达约 88% 峰值),两项加起来也只值这 15 点,谁都不是约束条件。

**v3 → v4「免表现算」——证实。** 循环体逐条对上:`LDG.E.CONSTANT` 8→0
(cos/sin 两路表访存整组消失);新增 `LDG.E.128.CONSTANT` ×2(inv_freq);
新增 `MUFU.SIN` ×8 + `MUFU.COS` ×8 = 源码说的「8 次 SFU 调用」(每次编成 2 条);
`PRMT` 32→16(表的 bf16→f32 解包消失)。工作集从 O(T·D) 塌成 O(D):
inv_freq 的地址只依赖 `vi ∈ [0,8)`、与 token 无关,整个 kernel 只触及 256 B。

**v3 → v4 在 L2 区间反而慢 22%——SASS 给不出瓶颈,原先的 SFU 吞吐解释不成立。**
按 sm_89 的 SFU 容量(128 SM × 16 lane × 约 2.52 GHz)与该尺寸的元素数折算,
每元素 1 条 MUFU 的需求只占容量约 11%,整体指令发射也只到约 17%——差近一个数量级,
SFU **吞吐**不可能是瓶颈。同样的「每 16 元素多 32 条算术指令」签名更可能由
依赖链延迟产生:v4 的关键路径是 `LDG.128` → `FMUL` → `FMUL.RZ`(×1/2π 规约)
→ 长延迟 `MUFU.SIN/COS` → `FFMA` → `F2FP` → `STG`,比 v3 长两级且多的那一级是 SFU;
L2 区间没有足够在飞访存去遮蔽它。SASS 分不开吞吐与延迟这两种机制。
一条能排除带宽解释的旁证:v4 在该区间搬的真实字节只有 v3 的一半(v3 还要读表),
流量减半而时间反增——「带宽/流量」可以从候选里划掉。

**v4 的精度边界可能比源码注释写的更紧——SASS 提示,未验证。**
`__sincosf` 的参数规约在 SASS 里就是一条 `FMUL.RZ Rx, Ry, 0.15915493667`
(×1/2π,单精度、向零舍入),之后才 `MUFU.SIN/COS`,没有 Payne-Hanek 扩展精度规约。
按此推算,T=32768 量级的角度误差与 bf16 的相对分辨率同量级,而不是注释说的「远小于」。
这一条是从规约方式推的,未做数值对拍,只作为待验证项列出。

**v0 → v1「融合」——证实,且字节账逐条对得上。**
v0 每输出元素 3 条 `LDG.E.U16` + 2 条 `STG.E.U16` = 5;v1 = 2 + 1 = 3。
5→3 精确成立,每条都是 16 位,不存在宽度差把账搅浑,与 README 的字节账 1:1 对齐。
LDS/STS/LDGSTS 全为 0,「中间值留在寄存器」是字面属实。

**v0 不是稻草人——证实。** v0_silu 与 v1 的每元素算术路径完全同构
(FFMA 都是 17、MUFU 都是 4、同样的 `MUFU.EX2` 与 `FCHK`/`CALL` 除法慢路径、
同样的 `F2FP.BF16.F32.PACK_AB`),v0 唯一多出来的就是那一对 `STG.E.U16`/`LDG.E.U16`。
加速来自消掉中间张量往返,不是来自 v0 写得烂。这个自检论证站得住。

**v1 → v2「16 B 向量化」——证伪(与 fused-norm 修复前同一成因,此处尚未修)。**
全 `.so` 里 `LDG.E.128`/`STG.E.128`/`LDG.E.64`/`STG.E.64` 均为 0;
v2 实际生成 8 条 32 位 `LDG.E.CONSTANT` + 4 条 32 位 `STG.E`。
PTX 层已经是 `ld.global.nc.v2.u16` ×4 与 `st.global.u32` ×4。
per-thread 16 B 是真的,「一次请求」不是——是 4 次。真实改动是
2 B/条 → 4 B/条、每元素访存指令 3 → 1.5、循环体每元素 39 → 26.75 条。

**「标量 bf16 时一个 warp 只覆盖 64 B,不足一个 128 B 事务,一半带宽被丢弃」——证伪。**
这条其实是编译期可判死的,不需要计数器:warp 的地址足迹由指令形态 + 源码下标
唯一确定。v1 的 `LDG.E.U16` 每 lane 2 B、lane 间连续,一条 warp 请求覆盖 64 B 连续
= 2 个满 32 B sector,利用率 100%,不存在「丢一半」。这条注释沿用了 Pascal 时代的
128 B 事务模型,在 Ada 的 32 B sector 模型下不成立。

**v2 → v3「只动输入布局」——证伪。** 打包布局本身确证:v2 的 kernel 参数区有
四个参数(out/gate/up/nv),两路读从两个独立基址起算;v3 只有三个参数
(out/gate_up/Iv),up 的基址不再是参数,而是 `LEA` 从 gate 指针算出来的。
但同一级至少还改了三件事:索引位宽(long long → int,循环判据从两条 64 位比较
变成一条 32 位)、grid 几何(1D 持久化 4096 block × 12 次 grid-stride →
2D `(6, T)` × 恰好 1 次迭代)、以及随之而来的**整张量被触达的顺序**
(全局线性 stride 横扫 → 按行分块扫)。三者对收益的分配无证据;
而且该级在 L2 区间与 HBM 区间的相对变化差了约一个数量级(见 `activation/README.md`
三列),任何单因归属都必须先绑定区间。

**「打包让寻址更简单」——证伪。** 循环体地址算术条数两版都是 20;
循环体总指令 v3 反而多 3 条,全 kernel 多 3 条,寄存器多 2 个。
v3 在循环判据上省下的两条 64 位指令,被多出来的 `LEA`/`LEA.HI.X` 指针成型吃掉了。

**「收益不在被改的地方:打包让两次 GEMM 合并」——SASS 答不了。**
这条主张全部发生在 GEMM 侧,`activation_ext.so` 里没有任何 GEMM kernel
(五个 Function 全是逐元素,HMMA/IMMA/LDGSTS 均为 0)。办法见 §7.1。

一处 README 没主张也没否定的空白:`silu(x) = x / (1 + __expf(-x))` 里的 `/`
在无 `--use_fast_math` 下编成了完整 IEEE 除法,v2/v3 循环体里可明确归给它的
至少 49 条(`FCHK` 8 + `CALL.REL.NOINC` 9 + `BSSY`/`BSYNC` 各 8 + `MUFU.RCP` 8 +
`FSETP.GEU.AND` 8),占循环体的约四分之一;exp 那边反而很干净(8 条 `MUFU.EX2`)。
HBM 区间不影响(已到约 92% 峰值),decode 区间值得试 `__fdividef`。

**量化链 v0 → v1「融合 + warp shuffle 归约」——证实。** 符号数 2→1;

这是注释与实现不符,不是 bug。

**量化链 v1 → v2「读 16 B / 写 8 B」——写侧证实,读侧证伪。**
写侧真做到了:`STG.E.U8`(1 B/条)→ `STG.E.64`(8 B/条),PTX 是 `st.global.v4.u16`。
读侧没有:`LDG.E.128` = 0,BF16x8 被拆成 4 条 32 位 `LDG.E.CONSTANT`,
两个循环共 8 条(与 fused-norm 修复前同一成因,此处尚未修)。
所以读侧措辞在改代码之前应从「读 16 B」降为「每条访存指令覆盖的元素数翻倍」。
本级对端到端的贡献有硬上界:`records/EXP-K06` §5.1 给出量化步只占整条链路 1.8%,
所以无论 v1→v2 多快,端到端贡献 ≤1.8%——不值得为它单独跑 GPU。

**反量化 v0 → v1「x_scale 只读一次 + 列向量化」——证实,但记载漏了最大的一项。**
scale 提出循环确证:`dequant_v1` 的 `LDG.E.CONSTANT` 位于循环回边之前(循环外,
每 block 一次),`dequant_v0` 的 3 条全在循环体内。读侧向量化确证
(`LDG.128` 0→2,PTX `ld.global.nc.v4.u32` 与 `v4.f32`)。
写侧则要降级:`BF16x4` 的 8 B 写被拆成 2 条 32 位 `STG.E`,没有 `STG.E.64`。
**记载完全没提的一项**:v0 每元素做 `i % O` 与 `i / O`(O 是运行期变量),
PTX 里是 `div.s64` + `div.u32`,SASS 展开成 55 条 `IMAD*` + 3 条 `I2F` + 2 条
`MUFU.RCP`;v1 用 `blockIdx.y` 直接给行号,`IMAD*` 只剩 8 条、`MUFU` 归零,
活指令 152→47。不过「消除法是主因」超出 SASS 能支持的范围:v1 每次迭代处理
4 个元素而 v0 处理 1 个,就算把除法原封不动保留,4 倍的循环体摊薄本身也会让
每元素除法成本降到四分之一——「消掉除法」与「向量化摊薄一切」在 SASS 上
产生完全相同的签名,只能并列为候选。

**INT8 GEMV 的 dp4a——证实。**
`IDP.4A.S8.S8` 各 116 条(PTX 各 20 条 `dp4a`,ptxas 又展开了一轮);
权重按 16 B 读(gv.v0 有 58 条 `LDG.E.128.CONSTANT`);
收尾是 5 条 `SHFL.BFLY`(warp 归约的 5 步蝶形)+ 1 条 `STG.E.U16`。
全 `.so` 零 HMMA/IMMA,「不占用 Tensor Core」字面成立。

**INT8 GEMV v0 → v1「激活搬进 smem」——结构证实,收益可预测为零(不必实验)。**
`LDG.E.128.CONSTANT` 58→30、`LDS.128` 0→29、`STS.128` 0→1、`BAR.SYNC` 0→1,
`IDP.4A` 两边都是 116。账目对得上:v0 的 58 = 权重 29 + 激活 29;
v1 = 权重 29 + staging 新增 1 = 30,激活那 29 条整体搬成 29 条 `LDS.128`。
零收益不需要变体实验就能预测:激活是 H×1 B = 4 KB,对 Ada 每 SM 128 KB 的 L1
是 3%,v0 里 8 个 warp 的重复读必然全是 L1 命中;显式搬 smem 只是把 28 条 LDG.128
换成 29 条 LDS.128 外加一条 barrier,净增 7 条总指令。
`records/EXP-K06` §7 的「v1 相对 v0 无收益」由此从实测巧合变成可预测结果。

**接口:x_scale 必须以设备指针传入——部分证实。** 接口形态 SASS 能确认
(gv.v0/v1 收尾各有 2 条 `LDG.E.CONSTANT` 读 `xs[0]` 与 `ws[o]`,是全局 load
而不是 kernel 参数里的标量常量)。但 `int8_gemv.cu:104-109` 里那个「decode 净亏 19%」
的数字在本仓没有对应的 raw 文件,只在源码注释里,按铁律 6 属于终端级证据。

**baseline → v0「block 并行归约」——证实(仅结构)。**
两次 shared 归约的骨架完全成形:SHARED 0→1024 B、STS 0→18、LDS 0→34、
BAR.SYNC 0→18。18 条与源码逐字对得上:每次归约 = 1 条初始 `__syncthreads`
+ log2(256) = 8 轮各 1 条,两次共 18。全局访存条数几乎不变(LDG.32 40→39),
证明搬的字节没变、变的只是谁来搬。「并行度从 1 线程升到 256 线程」不在 SASS 里
(是 host 侧 launch 配置)。

**v0 → v1 声称的三项改动,只有一项在产物里留下痕迹——两项证伪。**
把 v1 的 `LDG.E.CONSTANT.SYS` 归一化回 `LDG.E.SYS` 之后,两版 621 条指令
**逐助记符完全相同,diff 为空**。三项逐一定性:
(a)`%` 改位运算——真改动,零收益(nvcc 早已把常量 stride 的取模强度削减掉);
(b)「缓存 `row_offset`」——**假改动**,`softmax_v0.cu:62` 与 `softmax_v1.cu:61`
都是 `const int row_offset = row * cols;`,v1 只是在它上面加了一行注释;
(c)`__restrict__`——唯一真实差异,39 条全局 load 从 `LDG.E.SYS` 变成
`LDG.E.CONSTANT.SYS`(只读/non-coherent 路径)。而且归因还要再收窄:
`input` 在 v0 里就是 `const`,打开 `ld.global.nc` 的必要条件是编译器能证明
`output` 不会写到 `input`,起作用的是加在 **output** 上的 `__restrict__`。
另需注意 `.CONSTANT` 在 Turing 之后与普通 load 共用同一个 L1,指令形态变化
不等于命中率变化。

**v1 → v2「规整 shared 归约,降 bank conflict 风险」——部分证实。**
归约访存条数一条没变(LDS 34、STS 18、BAR.SYNC 18 三项与 v1 完全相同),
变的只是判据指令形态与 9 条总指令(v1 用 `LOP3.LUT` 算掩码 + `ISETP.NE` 判 0,
v2 用 `ISETP.GT`/`ISETP.LT` 直接比阈值)。bank conflict 本身在 SASS 里没有承载字段——
反证是 v0/v1(按文档说法有冲突)与 v2/v3(无冲突)的 LDS/STS/BAR.SYNC 三项完全相同。
这一档已有计数器读数:仓内 4090 报告里 v1 的读侧冲突是 36/36、v2 是 26/22
(两次 launch),方向对但绝对量级只有几十次,对同 kernel 的 393,216 条全局扇区
可以忽略。读法与全表见 §7.2。

**v2 → v3「float4 向量化」——证实,但代价 README 没记。**
`LDG.E.128.CONSTANT.SYS` 0→3、`STG.E.128.SYS` 0→1,与源码 3 处 float4 读
(max/sum/写回三阶段各一)+ 1 处 float4 写严格一一对应;每线程元素数翻 4 倍的
痕迹是 FFMA 82→166、`MUFU.EX2` 10→22。归约段一个字节没动(LDS 34、STS 18、
BAR.SYNC 18 与 v2 逐条相同),确实只改了访存。
两点与主张不符:标量路径没有被替换掉反而变多(LDG.32 39→45、STG.32 5→7,
那是循环内 `if (c+packSize-1<cols)` 的标量回退分支);主循环没被展开
(每个 float4 循环体只有 1 条 `LDG.128`)。

**v3 → v4「归约尾部 warp 化」——证实,且是整条梯上最干净的单变量改动。**
四个数同时动且全部能用源码逐字算出来:SHFL 0→11(其中 10 条是内联 `SHFL.DOWN`
= 2 次归约 × 5 步 offset,第 11 条是尾部 `RET.REL.NODEC` 段里的变量偏移冷桩);
BAR.SYNC 18→8(每次归约 4 条 × 2);STS 18→8;LDS 34→14。
访存侧完全不动:LDG.128 3、LDG.32 45、STG.128 1、STG.32 7、FFMA 166、MUFU 35
与 v3 逐条相同。这个性质本身很值钱——它让 v3/v4 的时延差可以干净地归因到归约段,
不需要任何 profiler。

**v4 → v4.2 反例「float4 → float2」——措辞证伪。**
「去掉 warp shuffle」确证(SHFL 11→0、BAR.SYNC 8→18、STS 8→18、LDS 14→34);
但 v4.2 的 `LDG.E.64` = 0、`LDG.E.128` = 0,全部 74 条全局 load 都是 32 位标量——
源码里 `if (c<cols)` 与 `if (c+1<cols)` 两个独立守卫阻止了编译器把相邻两个标量
合并成 64 位。正确说法是「float4 → 标量、每线程 2 元素」。
后果是这条反例不是单变量对照:它同时退化了向量宽度与归约结构,
把两个变量的合计收益全记在 warp shuffle 头上是过度归因。
梯子里还缺一个「标量 + warp shuffle」的第四象限变体(「float4 + 全同步」象限
已由 v4.4 占住),补上它就能用四个时延点解出两个变量的独立贡献。

**v4 → v4.3「main+tail 显式分离」——证实。**
`LDG.E.128` 3→35、`STG.E.128` 1→3、FFMA 166→250;v4 每个 float4 循环体只有 1 条
`LDG.128`(循环内的守卫挡住了展开),v4.3 的 max 阶段一次出现 11 条连续 `LDG.E.128`。
分支挪出循环 → ptxas 展开了主循环,这一条一目了然。归约段与 v4 逐条相同。

**v4.3 → v4.4「只破坏归约」——单变量隔离完美证实,机理归属证伪。**
访存与算术六项逐条相等(LDG.128 35、LDG.32 39、STG.128 3、STG.32 5、FFMA 250、
MUFU 53),变的全在归约(SHFL 11→0、BAR.SYNC 8→18、LDS 14→34、STS 8→18)。
但「bank conflict」这个具体机理 SASS 判不了,而计数器直接把它判掉了:
仓内 4090 报告里 v4.3 的读侧冲突是 30/32、v4.4 是 44/45(两次 launch),
方向确实对上了源码主张,但绝对量级只有几十次,而同一 kernel 的全局 load 扇区数是
393,216——差三到四个数量级。更硬的一条反证是全梯冲突最多的 v4(138/126)
恰恰是最快的一版。按权威数据(`records/data/exp_k04_softmax_3rounds.csv`,4090,3 轮)
v4.3 与 v4.4 的差只有个位数百分比;多出的 10 条 BAR.SYNC + 20 条 LDS + 10 条 STS
的指令账在这个量级上已经够用。**把退化整体记成 bank conflict 是过度归因**,
这一条现在有计数器背书,不再只是推断(读数与口径见 §7.2)。

**`cublas` 臂根本不是 cuBLAS——证伪,三重静态证据。**
(1)符号本身:`_ZN50_GLOBAL__N__..._17_softmax_cublas_cu_...21softmax_cublas_kernelE...`,
`_GLOBAL__N__` = 匿名 namespace、`17_softmax_cublas_cu` = 本仓源文件,
它是本仓自己写的 `__global__` kernel。(2)链接层:`nm` 查 cuBLAS 未定义符号为 0,
`ldd` 输出里只有 `libcudnn.so.9`,没有 libcublas。(3)规范层:BLAS 规范里没有 softmax。
它与 v4 的关系是同风格手写 kernel:用 10 条 `SHFL.BFLY`(`__shfl_xor_sync`)
而 v4 用 `SHFL.DOWN`,静态 shared 256 B 对 v4 的 1024 B,
全局侧只有 3 条 32 位 `LDG.E` + 2 条 `STG.E` 且无 `.CONSTANT`。
按源码这 5 个站点是「读 input 两遍 + 写 output 两遍 + 读 output 一遍」共 5 趟,
比 v4 的 4 趟多约四分之一的**片上请求量**(注意:1024×1024 fp32 工作集只有 8 MB,
远在 72 MB L2 之内,这是片上请求量之差,不是 DRAM 字节之差,措辞不能写成带宽账);
`MUFU.EX2` 只有 1 条而 v4 有 22 条——它每元素只算一次 exp、把中间值存回 global,
是典型的拿访存换算术。这个口径本仓其他四处已勘正,只有 `softmax/README.md` 漏改。

**先定瓶颈类型。** shape 4096×2048 fp32 → mat 33.6 MB < 72 MB L2,
bench 的 100 次迭代全程 L2 常驻。按 `records/data/exp_k04_gemv_3rounds.csv`
的 3 轮均值折算,v0..v4 的 L2 需求速率全部落在 HBM 峰值的约 2 至 2.6 倍这条窄带里——
**本梯量的是 L2 带宽,不是 HBM 带宽**,任何指令级或占用率机理的可归因预算合计
只有约 1.3 倍。下面每一级的判定都挂在这个前提下。

**baseline → v0「block 并行归约」——部分证实。** 归约机制确证
(STS 0→9、LDS 0→17、BAR.SYNC 0→9 = 1 次预同步 + log2(256)、静态 shared 0→1024 B)。
但主循环一个字节没变:两版都是每元素 2 条 `LDG.32`,FFMA 29→29,LDG.32 58→58,
全部是 `LDG.E.SYS`。收益完全来自 launch 几何,SASS 里看不到。

**v0 → v1「`__restrict__` + unroll2」——`__restrict__` 证实,「指令数下降」证伪。**
全局 load 助记符整体换路(v0 全是 `LDG.E.SYS`,v1 全是 `LDG.E.CONSTANT.SYS`),
与 softmax 同源,起作用的是加在 `out` 上的 `__restrict__`。
但静态总指令 224→153 是展开度变化造成的假象:切热循环体后,v0 是 55 条/16 元素
= 3.44 条/元素,v1 是 39 条/8 元素 = 4.88 条/元素,**每元素指令数上升 42%**
(**sm_75 口径**;sm_89 重编是 55/16 = 3.44 与 41/8 = 5.13,上升 49%,结论同向)——
展开度从 16 掉到 8,因为 `if (c + 1 < cols)` 守卫(SASS 里第二条 load 带 `@!P1` 谓词)
挡住了更深的展开。
`gemv_v1.cu:23` 的「步长 `blockSize*2` 让相邻线程访存地址对齐 64 位、提升 coalescing」
也证伪:`LDG.E.64` = 0,两次访问是两条独立 32 位 load。而且方向是反的,
这一条不需要计数器也能算死:v1 的循环体是 `c = tid*2`,两条 32 位 load 的 lane 间
步长 8 B,一条 warp 请求的地址足迹 32 × 8 = 256 B,除以 32 B sector = 8 个
sector/请求;v0 步长 4 B → 128 B / 32 = 4。**每请求 sector 数由 4 升到 8**,
coalescing 是变差不是变好。这条不依赖任何异机数据:结论由「SASS 指令形态 +
源码步长」的编译期算术得出,又被仓内 4090 报告逐个证实(`gemv_v0/v1/v2` 的
全局 load 扇区÷请求 = 4.00 / 8.00 / 16.00,见 §7.2)。注意
`gemv/project-proof/profiling/ncu/SUMMARY.md` 的正文仍是 4070 Laptop 一代的文字,
而同目录下的 `.ncu-rep` 已换成 4090 代——引用时以报告文件为准。
在 L2 常驻的前提下,±42% 的每元素指令数本就不该改变时延——实测两版持平与之一致。

**v1 → v2「float4 向量化」——证实,代价 README 没记。**
`LDG.E.128.CONSTANT.SYS` 0→58,展开步长 `0x1000` = 4096 B = blockSize × 4 × 4 B,
两条基址流各半;每元素总指令 1.86 条,全梯最低。但尾部标量回退路径被完整生成
(另 58 条 32 位 `LDG.E.CONSTANT.SYS` 加一个独立热循环),cols=2048 时动态执行 0 次,
却把静态指令抬到 506(全梯最高;sm_75 口径,sm_89 重编 499)、
寄存器抬到 66(sm_75)/50(sm_89)。
「更好的内存合并」不成立:每请求 sector 数从 8 升到 16(一条 `LDG.128` 覆盖
32 × 16 = 512 B),总 sector 流量恒等,省的是指令条数与在飞字节数。

**v2 → v3「一行一 warp,shuffle 归约」——证实。**
`SHFL.DOWN` 0→5(对应 offset 16/8/4/2/1),BAR.SYNC 9→0,STS 9→0,LDS 17→0,
静态 shared 1024 B→0。整个 v3 的 SASS 里没有任何一条 shared 指令、没有任何 barrier。
总指令 506→185,寄存器 66→44(sm_75)/50→38(sm_89)。
主循环 LDG 步长 `0x80` = 128 B = 32 float,确认 lane-stride 扫描。

**v3 → v4「多行共享 x-tile」——证伪,而且是真 bug。**
v4 的 vec 地址由 `IMAD.WIDE R4, R3, 0x4, R4`(R3 = `S2R SR_TID.X`)算出,
表达式里**没有 `SR_TID.Y`**;随后的 `LDG.E.CONSTANT.SYS` 与
`STS [R3.X4], R6` 都不带任何 ty 谓词。也就是说 `blockDim=(128,4)` 的全部 512 个线程
各自从 global 读同一个 `vec[c]`、再各自写同一个 shared 地址:每 block 仍然把 vec
完整读 4 遍,和 v3「4 行各读一遍」一模一样。源码 `gemv_v4.cu:36` 缺一句
`if (ty == 0)`。全局 vec 流量的减少量是**零**,不是「收益小于开销」。
但**结论不变、机理要换句**:vec = 2048 floats = 8 KB,对每 SM 128 KB 的 L1 是 6%,
v3 里 4096 行各读一遍 vec 的那些请求全部是 L1 命中;补上守卫只能把 vec 的 LDG
条数减到四分之一,减掉的全是 L1 命中,动不了 L2/DRAM 流量。所以
「多行共享 x-tile 无收益」这个结论对,「同步开销大于复用收益」这个机理不对。
回退的指令账 SASS 全部拿到:BAR.SYNC 0→18、LDS 0→20、STS 0→13、shared 0→2560 B;
每元素代价 v3 = 3.44 条/0 barrier,v4 = 13.25 条/每 4 元素夹 8 条 BAR.SYNC。
「一来一回」也被坐实:`STS [R3.X4],R6` → `BAR.SYNC` → `LDS.U R8,[R3.X4]` →
`FFMA R2,R9,R8,R2`,FFMA 读的是从 shared 取回的 R8 而不是刚存进去的 R6,
barrier 挡死了寄存器前递。
另外可以**排除占用率解释**:按 sm_89 常数,v3(128 线程、38 reg、0 smem)与
v4(512 线程、24 reg、2560 B)理论 occupancy 都是 100%,占用率不是这一级的解释变量。
计数器把这条排除做得更死:`artifacts/ncu_for_mac/manifest.csv` 的 `occ_pct` 列
(4090 报告)给 v3 achieved 62.13%、v4 achieved 92.16%——**v4 的实际占用率反而更高
却更慢**,方向与「占用率解释」相反。

**`gemv_v4.cu:16` 的 padding 注释与事实相反——证伪。**
`-res-usage` 给 SHARED:2560 = `smem_x` 512 B + `smem_partial` 2048 B,
**精确等于无 padding 的尺寸**(若真 pad 到 `[4][129]` 应为 2576);
而行步长 128 float ≡ 0 (mod 32 banks),同列不同行恰好落在同一个 bank,
注释描述的机制与实际正好相反。实际无害(归约里同 warp 的 ty 相同、tx 连续,
本来就不冲突),但注释是错的。

**v4 在 barrier 前 early-return——SASS 可见的一处 UB 隐患。**
`if (row >= rows) return;` 之后循环里有 `__syncthreads()`。rows 不是
`kRowsPerBlock=4` 的倍数时是未定义行为;当前 rows=4096 整除所以没暴露。
v0/v1/v2 有同形 return 但一个 block 只管一行、不会半个 block 退出,无碍;v3 无 barrier。

**baseline → v0「grid-stride 并行」——部分证实。**
kernel 侧结构确认:baseline 前导是 `S2UR SR_CTAID.X` + `S2R SR_TID.X` +

**v0 → v1「unroll2 + restrict」——unroll 与 restrict 都证实,「指令数下降」证伪。**
所有每元素指令精确翻倍(LDG.32 10→20、`STG.E.U8` 5→10、`FCHK` 5→10 等);
`__restrict__` 让 `LDG.E.SYS` 全部变成 `LDG.E.CONSTANT.SYS`。
但循环体内每元素成本完全没降:v0 余数循环 56 条/1 元素,v1 112 条/2 元素,
都是 56 条/元素;每元素的 `i/hw` 无符号除法依旧在跑
(`IMAD.HI.U32` 2 条/元素、`I2F.RP` 1 条/元素、`MUFU.RCP` 2 条/元素)。
按主循环体口径,每元素指令数 v0 = 210/4 = 52.5、v1 = 426/8 = 53.25,**没有下降**
(**sm_75 口径**;同一口径的 sm_89 重编值是 203/4 = 50.75 与 408/8 = 51.0,
结论「没有下降」在两个 arch 上都成立)。
真正被摊薄的是每线程的固定前导(该 shape 下三个 launcher 的 grid-stride trip 都恰好为 1,
所以每线程只跑一轮,前导占比随每线程元素数上升而下降)。
这一级同时改了 unroll 与 `__restrict__` 两件事,SASS 只能证明两者都发生了,无法归因。

**v1 → v2「unroll4」——是回退,静态指令数与实测同向;但 SASS 不预测时延。**
v2 循环体确实覆盖 4 个连续元素(输入地址 `[R2]`/`+0x4`/`+0x8`/`+0xc`,
输出是 4 条独立 `STG.E.U8` `[R14]`/`+0x1`/`+0x2`/`+0x3`)。
但编译器**没有**把 4 条相邻的 1 字节 store 合并成一条 32 位 store——
因为源码里每个元素都被 `if (i < total)` 单独守卫。每元素主循环体指令
53.25 → 220/4 = 55.0(**+3.3%,sm_75 口径,这份码在 4090 上不执行**);
同一口径的 sm_89 重编值是 51.0 → 215/4 = 53.75(+5.4%)。访存条数与整数除法一条未减。

实测按权威数据 `records/data/exp_k04_int8_quantize_3rounds.csv`(4090,3 轮):
v1 = 0.00684767 ms、v2 = 0.00717133 ms,**回退 +4.73%**。

三者的关系只能这样写:**静态每元素指令数上升(+3.3% sm_75 / +5.4% sm_89)与实测
回退 +4.73% 同向。** 不能写成「SASS 预测了这一级的回退」——静态条数不含发射率、
访存重叠与依赖链,数值接近是巧合而非推导;两个 arch 口径给出的百分比本身就差了
将近一倍,足以说明这个数不具备预测精度。SASS 在这里的作用是**排除**:
访存指令条数与整数除法一条没少,所以「减少了访存」或「省掉了除法」这两类解释
可以直接划掉,回退只能出在别处。
(本仓 `int8-quantize/project-proof/docs/why-each-version-changed.md` 那一代
时延数字是 4070 Laptop 口径、符号相反,按铁律 7 应当归档,不可再用作因果框架。)

**v0/v1/v2 三级还有一件 README 完全没提的事——每请求 sector 数在恶化。**
v1 的下标是 `i = gid*2` 后访问 `input[i]`、`input[i+1]`,v2 是 `base = gid*4`
后访问 `base+0..3`,lane 间步长分别是 8 B 与 16 B。按与 gemv 同一套编译期算术:
v0 步长 4 B → 每请求 4 个 sector;v1 → 8;v2 → 16,单请求利用率 100% → 50% → 25%
(四条相邻 load 合起来才覆满,靠 L1 兜住)。这既是「前导摊薄」收益被抵消的候选成因,
也直接给出一条 README 里没有的优化方向:把 unroll 写成 grid-stride 形式
(`i`、`i+step`、`i+2*step`…)而不是 `gid*N + 0..N-1`,可以在保住摊薄收益的同时
把每请求 sector 数拉回 4。

**v2 → v3「一 block 一 channel,scale 只读一次」——证实。**
`LDG.32` 8→2:v2 每 4 个元素读 4 次 input + 4 次 scale,v3 只剩循环外 1 条 scale
加循环内 1 条 input;`STG.8` 4→1;`MUFU` 10→3(跨 arch 稳定)。
`IMAD*` 77→21、活指令 347→147 是 sm_75 口径,sm_89 重编为 79→19 与 341→144,
量级与方向都保住,但引用时要带口径。
scale 提升出循环由地址与位置直接可判(`c = blockIdx.x`,`float s = scales[c]`
在循环之前)。

**v3 → v4「float4 读 + char4 写」——证实,而且是本仓最早兑现的一处向量化。**
`LDG.E.128` 0→1(源码用的是原生 `float4` 而不是自定义聚合体),
写侧 `char4` 编成一条 32 位 `STG.E`。这一条曾与 fused-norm / rope / activation /
w8a8 那四处「16 B 向量化」失败形成直接对照:**同一台机器、同一个工具链,
用原生向量类型就出 128 位,用 `__nv_bfloat162` 成员的聚合体就停在 32 位。**
这个对照后来直接给出了修法——`fused-norm` 把载体换成含 `float4` 的 union 之后
`LDG.E.128` 由 0 变 4(§5.3),对照因此收窄到 rope / activation / w8a8 三处。
代价是尾部标量回退路径被完整生成(LDG.32 8 + STG.8 7),
活指令 147→413、寄存器 18→33(sm_75 口径;sm_89 重编为 144→411 与 20→32)。

**两条恒等式级的证伪。**

其一,**v6 与 v7 的 SASS 逐助记符完全相同**(REG 17、SHARED 1024 B、
活指令 122、LDG.32 5、LDS 17、STS 9、BAR.SYNC 3、BRA 7、IMAD* 19,无一项不同);
sm_89 重编后两版仍逐助记符相同(REG 17、活指令 120),这条恒等式与 arch 无关。
源码 `diff src/reduce_v6.cu src/reduce_v7.cu` 的差异只有注释与 kernel 名。
也就是说**这不是版本梯的两级**。而 `README.md`、`PORTFOLIO.md`、`LEDGER.md`、
`records/EXP-K04` 都把 v7 当作顶格数字(HBM-bound 达峰值 93.9%)在用;
按 `records/data/exp_k04_cuda_reduce_3rounds.csv` 与
`records/data/exp_k04_reduce_hbmbound_3rounds.csv`(3 轮),两者的差值都落在
v6 自身的 std 内。SASS 给出的解释很干脆:它们是同一个 kernel。

其二,**自写八版全梯 `LDG.128` = 0、`SHFL` = 0**——没有一条 float4 向量化访存,
也没有一条 warp shuffle。而同一个二进制里的 CUB 三个 kernel 各有 8 条 `LDG.128`
与 30 条 `SHFL`。`PORTFOLIO.md:274` 那一行「reduce | float4 | 单看 v3 收益 12% |
加 warp shuffle 后总收益 60%」两个手法在这条梯子上都不存在。

**baseline → v0「shared 树形归约」——证实。**
SHARED 0→1024 B、STS 0→9、LDS 0→17、BAR.SYNC 0→9(1 次预同步 + log2(256) = 8 轮);
全局访存从 29 条 `LDG.32` 塌到 1 条(每线程只读一个元素)。

**v0 → v1「`%` 换 `&`」——零差异,与 softmax v0→v1 同源。**
两版 80 条指令逐助记符完全相同。nvcc 早已把常量 stride 的取模强度削减成
`LOP3.LUT`,写不写位运算对产物没有影响。README 里 v1 比 v0 慢的那个数
(`cuda-reduce/README.md` 的快照)在 SASS 层没有任何对应物,只能是测量噪声。

**v1 → v2「对半收缩消 bank conflict」——归约访存条数不变。**
LDS 17、STS 9、BAR.SYNC 9 三项与 v1 完全相同,变的只是判据形态与 10 条总指令
(`IMAD*` 7→4;这两版的 sm_89 重编差异集合为空,活指令与 `IMAD*` 都与 sm_75 相同)。与 softmax 的同名一级是同一个结论:bank conflict 在 SASS 里
不可见,这一级在指令层是零改动。

**v2 → v3「首次加载即相加」——证实。**
`LDG.32` 1→2(每线程读两个元素),`STS` 9→11,归约段不变(LDS 17、BAR.SYNC 9)。
这是这条梯上第一个真正减少了 kernel 启动轮数的改动(grid 减半)。

**v3 → v4「末 warp 用 volatile + `__syncwarp` 展开」——证实,但代价被记漏。**
BAR.SYNC 9→3、LDS 17→12,尾部同步确实少了。但同一级里新增了
**12 条 `CALL.REL.NOINC` + 12 条 `BRA.CONV`**:`WarpSharedMemReduce` 那个带
`volatile` 与 `__syncwarp()` 的 helper **没有被内联**,而是编成了 out-of-line
子程序调用(6 步 × 2 个 `__syncwarp()`)。普通 `BRA` 只从 1 涨到 2,涨的全是
`BRA.CONV`(0→12)——分开数才看得出多出来的控制流全是调用序列,不是算法分支。
活指令 71→112(+58%,sm_75 口径;sm_89 重编是 72→101,+40%,方向与量级都保住)。
v5 把这个 helper 换成不带 `__syncwarp` 的展开写法之后,活指令回到 67、
`CALL` 归零、BAR.SYNC 仍是 3——**v5 才是这一级真正想要的产物,v4 付了一笔
子程序调用税**。这条在任何文档里都没有记载。
这笔税不是 sm_75 特有的:sm_89 重编后 `CALL.REL.NOINC` 与 `BRA.CONV` 仍各 12 条。

**v4 → v5「归约全展开」——证实。**
`CALL.REL.NOINC` 12→0、`BRA.CONV` 12→0(普通 `BRA` 两版都是 2,一条没动)、
`IMAD*` 14→2、活指令 112→67(全梯最少;`IMAD*` 与活指令为 sm_75 口径,
sm_89 重编是 9→2 与 101→67,结论不变)。
LDS 12→17 是因为展开后每一步的读被显式写出。

**v5 → v6「grid-stride + two-pass」——证实。**
`LDG.32` 2→5(grid-stride 循环体 + 尾部),`IMAD*` 2→19、`BRA` 2→7、
REG 14→17、活指令 67→122;归约段完全继承(LDS 17、STS 9、BAR.SYNC 3)。
这一段的四个不稳定列在 sm_89 上原样成立:v5 与 v6 的重编差异集合为空,
活指令 67→120、REG 14→17,`IMAD*` 与 `BRA` 逐项与 sm_75 相同。

**v5/v6/v7 的末 warp 归约有一处 SASS 可见的正确性隐患。**
它们的最后一个 warp 用 `volatile float*` 逐步相加且**没有任何 `__syncwarp()`**
(v5/v6/v7 的助记符里 `WARPSYNC` = 0,而 v4 有 1 条)。
在 Volta 之后的独立线程调度下,只靠 `volatile` 不再保证 warp 内步调一致;
当前能出正确结果不等于有语言层保证。这不是性能问题,是正确性问题,值得单独登记。

**CUB 对照臂——可以逐指令对照,这是全仓独一份的机会。**
CUB 的三个 kernel 各有 8 条 `LDG.E.128`(向量化加载)、30 条 `SHFL`
(warp 归约)、静态 shared 只有 44 B(自家版是 1024 B)、REG 45/64/40。
自家八版一条 `LDG.128` 与一条 `SHFL` 都没有,shared 用量是 CUB 的 23 倍。
「CUB 在 L2 常驻区间快 33%」这个已记录的结论,在指令层有非常直接的候选解释,
而且这个对照完全静态、不需要任何权限。

### 6.1 向量化未兑现(四处;原为五处,fused-norm 已修好)

| 位置 | 记载 | SASS 事实 |
|---|---|---|
| `rope/README.md:18,40,56`、`src/rope_v3.cu:10-11` | 「16 B 向量化」;「16 B/lane 后一次请求 32×16=512 B = 4 个满事务」 | `LDG.E.128` = 0;是 4 次请求不是一次。「512 B 足迹 / 4 个满事务」对,「一次请求」错 |
| `activation/README.md:15,36`、`src/silu_and_mul_v2.cu` | 「16 B 向量化」;同上的「一次请求」措辞 | `LDG.E.128`/`STG.E.128` = 0,实际 8 条 32 位 `LDG.E.CONSTANT` + 4 条 32 位 `STG.E` |
| `w8a8/src/quant_per_token.cu:85` | 「v2 向量化(读 16 B bf16,写 8 B int8)」 | 写侧真兑现(`STG.E.U8` → `STG.E.64`);读侧 `LDG.E.128` = 0,拆成 4 条 32 位 |
| `w8a8/src/dequant.cu:44` | 「列方向向量化」的 `BF16x4` 8 B 写 | 读侧兑现(`LDG.128` 0→2);写侧拆成 2 条 32 位 `STG.E`,没有 `STG.E.64` |

四处的成因是同一个,而且不是通常猜的那个:不是 SROA、也不是对齐证不出来。
判别变量是**聚合体的成员类型是 `__nv_bfloat162`**(一个 2×16 位向量类型),
NVVM 的 load/store vectorizer 合并到 `v2.u16`(4 B)就停了。
同样被 SROA、同样 `alignas(16)`、同样运行期下标的 `struct{unsigned w0..w3}`
照样出 `LDG.E.128`;同一台机器上 `int8-quantize` v4 用原生 `float4` 也照样出。
`alignas(16)` 只管地址对齐,不改变 nvcc 按成员类型切分访存的粒度——四处记载
把对齐属性当成了向量化开关,这是同一个误解的四个实例。

**第五处(`fused-norm` v3/v4)已经按这个根因改好,所以从本表移出。**
修法:`struct alignas(16) BF16x8` 由 `{ __nv_bfloat162 h[4]; }` 换成
`union { float4 raw; __nv_bfloat162 h[4]; }` 加显式拷贝构造/赋值(都写 `raw = o.raw`),
整体赋值走 `float4` 这条 128 位通路,逐元素计算仍从 `h[]` 视图读,**调用点一行未改**。
重编后 v3 的 `LDG.E.128` 由 0 变 4、`STG.E.128` 由 0 变 2、`LDG.32` 归零,
v4<1> 是 3 + 2(§5.3);带宽侧的同环境 A/B 与归因见 `EXP-K08`。

**这个修法可以直接套用到上表四处**,因为它们用的是逐字相同的载体定义:
`rope/src/rope_v3.cu:18`、`rope/src/rope_v4.cu:30`、
`activation/src/silu_and_mul_v2.cu:16`、`activation/src/silu_and_mul_v3.cu:20`、
`w8a8/src/quant_per_token.cu:86` 五处都是 `struct alignas(16) BF16x8 { __nv_bfloat162 h[4]; };`
(注意 `rope` v4 与 `activation` v3 也带这个载体,改的时候不要漏);
`w8a8/src/dequant.cu:46` 的 `alignas(8) BF16x4 { __nv_bfloat162 h[2]; }` 是 8 B 版,
同理换 `union{float2 raw;}`。但这六个文件到现在一行未改,
所以本表的记载与 SASS 事实都仍然成立。

在改代码之前,这四处按文档问题处理,措辞降级为:「按 bf16x2 打包,
访存指令宽度 2 B → 4 B,每元素访存指令数减半」。注意 DRAM 字节数不受影响
(warp 内 4 条连续 32 位读照样合并成整 cache line),所以现有的 GB/s 数字不作废,
作废的是「16 B」这个措辞和由它推出的「1/8 指令数」预期。
改代码之后这两句都要换回来,`fused-norm` 就是先例——它证明这四条既可以按文档问题
降级措辞,也可以按代码问题真改掉,后者代价是两行定义加一次重编。

验证顺序固定:先静态、后跑数。重编后 `cuobjdump` 看 `LDG.E.128` 出没出现即可判定
修法是否生效,不碰 GPU;`fused-norm` 那次静态验收给出的 4/2 条恰好等于修复前就写死的
预测值(「若真发 128 位应各是 4 条与 2 条」),这是本文预测被后续改动验证的一例。

这一条曾由计数器侧独立复现:`records/EXP-K07` §6.4 读出 `fused-norm` v3/v4 的
L1TEX 全局读扇区是 v1/v2 的 4 倍(16.000 / 12.000×S 对 4.000×S),而 DRAM 读恒为
2.000×S——「号称向量化的版本反而多发 4 倍事务、但被 L1/L2 全部吸收」。
静态(`LDG.E.128` = 0)与运行时(扇区放大 4 倍)两条路径互证过一次,
**但这组计数器数据对应的是 `fused-norm` 修复前的版本**,现在只作历史基线用,
不描述当前的 `fused_norm_ext.so`;修复后需重采(§8 缺口表)。
rope / activation / w8a8 至今没有任何计数器报告(同表),它们这一条只有静态证据。

`project-proof/data/benchmark_results.csv` 写死成相对 cwd 的常量,不读该环境变量。

   `EXP-K07` §2)。所以拿本文 §5.7/§5.8/§5.9/§5.10 的 sm_75 判据去对这些报告时,
   只能用 §4 第 5 条判定为「跨 arch 稳定」的那些列。

三个例子:

- **softmax 的 bank conflict 在 4090 上小到可以忽略。** 从
  `softmax/project-proof/profiling/ncu/softmax_v*_profile.ncu-rep` 读
  `l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_{ld,st}.sum`(每份两次 launch,
  下表给两次的读侧值):v0 35/33、v1 36/36、v2 26/22、v3 36/64、v4 138/126、
  v4.2 57/91、v4.3 30/32、v4.4 44/45。写侧全部 ≤4。
  同一批 kernel 的全局 load 扇区数是 393,216(只有 v4.2 是 786,432 = 每请求 8 个 sector,
  正是 §5.9 那套「lane 间步长 8 B ⇒ 每请求 8 个 sector」的算术在 softmax 上的同一形态)。
  也就是说冲突次数比全局扇区数小三到四个数量级,**在这条梯子上 bank conflict
  根本不是可归因的量**。两个直接后果:v4.3→v4.4 的冲突确实涨了(30→44,+47%),
  方向支持源码主张,但绝对量级支撑不起「v4.4 的退化是 bank conflict 造成的」;
  而全梯冲突最多的 v4(138)恰恰是最快的一版,单调关系根本不存在。
- **softmax v0 vs v1 的只读通路在计数器上也是空改动。** 两版的 global load
  requests 与 sectors **完全相同**(98,304 / 393,216),

  `lts__t_sector_hit_rate` 51.94/51.35 对 51.09/51.35——全在两次 launch 自身的

  计数器再证只读通路的缓存差也为零——这一级在两个层面上都是空改动。

  2097152/524288 = **4.00**、4194304/524288 = **8.00**、2097152/131072 = **16.00**、

  显著高于 v0 的 48.28%,正是「每请求 sector 翻倍、靠 L1 兜住」的直接读数。

### 7.3 变体对照(设计纪律比结论重要)

变体对照是把混杂变量拆开的主要手段,但它本身很容易做成混杂设计。三条纪律:

1. **改一个变量,固定其余全部——包括你没打算改的那些。**
   例:要检验 `gemm` v4 的「靠 fragment 级 ILP 不靠线程数」,把 `acc[4][2]` 拆成
   两轮 `acc[2][2]` 是**坏设计**:它同时砍了 ILP、降了寄存器(92 → 60 档,
   按 sm_89 常数 2 block/SM 会变成 4 block/SM,占用率直接翻倍)、还会重发 LDSM。
   正确做法是保留 8 个 fragment,用假依赖把 16 条 HMMA 串成长链,
   或用 `__launch_bounds__`/`-maxrregcount` 把寄存器钉死;
   编出来先 `cuobjdump` 复核 REG=92、HMMA=32、LDSM=12 三项与 v4 逐项相同,再比时延。
2. **先确认变体不是恒等式。** 例:检验 `w8a8` 「激活本就 L1 常驻」时把 `WARPS`
   从 8 降到 1 是**坏设计**——那样 v0 与 v1 退化成同一个 kernel,差距为零是构造出来的。
   而且这一条根本不需要实验:激活只有 4 KB,对 128 KB/SM 的 L1 是 3%,必然命中。
3. **确认变体在物理上可实现。** 例:`gemm` 的「给 As/Bs 加 XOR swizzle」
   在 wmma API 下做不到——`wmma::load_matrix_sync` 只接受基址 + leading dimension,
   表达不了 XOR 换算过的地址;要 swizzle 就必须改 mma.sync + 手写 ldmatrix,
   那是 README backlog 里的 v5 重写,不是低成本变体。padding(`BK` 32→40,
   half 的 ldm 必须是 8 元素倍数,合法;v4 smem 32768→40960 B,仍是 2 block/SM)
   才是干净的单变量。

按这三条,本文各节里点名的可做变体是:`gemm` 的 padding 版与固定寄存器的砍 ILP 版;
剩下三个算子(rope / activation / w8a8)「16 B 向量化未兑现」的换载体版
(先静态验 `LDG.E.128` 出现;`fused-norm` 这一版已经做完,见 §5.3 与 §6.1);
`softmax` 缺的那个「标量 + warp shuffle」第四象限;`activation` 的 v3-ctrl
(必须保留 v2 的 1D 持久化 grid 与 long long 索引,否则又混进访问顺序变量);
`rope` 的「只给 cos/sin 表加 stride padding 撑出 L2、数据形状不动」版。

### 7.4 `clock64()` 分段插桩(有计数器时基本用不上,列在这里备查)

它是段内时间切分的手段,不需要 profiler。`flash-attn` 的相位链归因现在已由
`EXP-K07` §5.4 的 stall 分解答掉,不必再动它;但对**同步相关**的命题,插桩本身
就是循环测量:被测对象就是同步链本身,而分段取时钟要在段界读时钟
+ 写 per-block 全局缓冲;`clock64` 与相邻访存没有数据依赖,不加 fence 可能被调度器
搬位置,加了就等于往被测的同步链里再加同步与访存。v4 已经是 1099 条活指令 /
80 reg / 1 block per SM,插桩还会同时改寄存器与指令数。
用它的前提是:同时报告插桩版与原版的整核时延差,作为扰动上界一起记录。
对**非同步**的段(如 `rope` 的表访存段、`gemv` 的归约段)扰动小得多,可以放心用。

### 7.5 编译期算术能顶掉的四件事(不需要任何测量)

1. **每请求 sector 数。** warp 的地址足迹由 SASS 指令形态 + 源码下标唯一确定,
   除以 32 B 即得。`gemv` v0/v1/v2 = 4/8/16、`int8-quantize` v0/v1/v2 = 4/8/16。
   这条判据不依赖任何 profiler 就能算死,而仓内 4090 报告的
   扇区÷请求正好逐个吻合(4.00 / 8.00 / 16.00,见 §7.2)——编译期算术与计数器互证。
2. **理论 occupancy。** `-res-usage` 的 REG/SHARED + sm_89 常数
   (65536 reg/SM、102400 B smem/SM、1536 thr/SM、48 warp/SM、每 SM 24 block 上限、
   寄存器分配粒度 256)即可算死。本文用它做过两次关键排除:`gemv` v3 与 v4 都是
   100%,占用率不是 v4 回退的解释变量;`fused-norm` v2→v3 从 66.7% 升到 100%,
   是零收益账里的一个反向变量。
   **算出来的是理论值,不是 achieved occupancy**——后者在仓内 4090 报告里有
   (`--page details --csv` 的 Occupancy 段,如 `gemv` v3 achieved 62.1% 对理论 100%),
   两者差多少本身就是一条信息,不要混用。用 sm_75 二进制的 REG 去算 4090 的
   理论 occupancy 会算错,必须换成 sm_89 值(§4 第 5 条)。
   `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 返回的是同源的模型值,
   不是 achieved occupancy,叫它「实测」是措辞升格;而且动态 smem 超过 48 KB 的
   kernel(`flash-attn` v2/v3/v4)必须先调 `cudaFuncSetAttribute`,并且它要建 CUDA context。
3. **片上流量的带宽占用上界。** SASS 条数 × 单条字节 × grid 展开 ÷ 权威时延,
   再比 Ada 的无冲突 smem 屋顶(128 SM × 128 B/clk × 约 2.52 GHz ≈ 41.3 TB/s)。
   本文算过两条:`flash-attn` v2 是 4.1 TB/s = 屋顶的 9.8%;`gemm` v4 是
   8.3 TB/s = 20.1%。**这两个数是「无冲突口径下 smem 带宽的占用率」,
   仅此而已。** 它们**不**是 bank conflict 的延迟贡献上界,也不构成任何红线的
   解锁条件——冲突的代价是 wavefront 串行重放带来的依赖链延迟与发射位占用,
   与带宽占用不是同一个量,一个占用两成的 kernel 完全可以被冲突拖死。
   `gemm` 的实测就是这样:v4 的 shared-load wavefront 里 81.1% 是冲突 wavefront
   (§5.1),而 cuBLAS 只有 0.28%。**要判冲突就去读计数器(§7.2),不要用这个比值代替。**
   这条编译期算术真正的用处是给一个数量级校验:如果算出来已经超过屋顶,
   说明字节账本身算错了。
4. **工作集与 L2 容量的比较。** 4090 的 L2 是 72 MB,L1 是 128 KB/SM。
   `gemm` 4096³ 的 A+B = 67.1 MB、`gemv` 的 mat = 33.6 MB、`softmax` 1024² fp32 的
   工作集 = 8 MB、`w8a8` 的激活 = 4 KB、`gemv` 的 vec = 8 KB——全部远在容量之内。
   这个比较不需要任何测量,却能一次性排除掉一大批「省下了一次显存访问」的归因。

## 8 计数器侧还缺的

原来这一节列的六类问题,现在大部分已由 `records/EXP-K07`《采集主机 NCU 计数器闭环》
与仓内 51 份 4090 报告答掉。先记账,再说还缺什么。

| 原问题 | 现状 | 出处 |
|---|---|---|
| achieved occupancy(与理论值的差) | 七个算子已有 | 各 `.ncu-rep` 的 Occupancy 段;`EXP-K07` §5.5 |
| 发射效率 / 各 pipe 利用率 | `gemm` / `flash-attn` 已有分管线数 | `EXP-K07` §5.1 |
| stall 分解(含 `long_scoreboard`) | 已有;FA2 v4 的 long_sb 已降到 0.31% | `EXP-K07` §5.4 / §5.5 |
| 4090 上的 DRAM 实际字节 | `fused-norm` 已按 ×S 口径逐版给全 | `EXP-K07` §5.3 |
| 4090 上的 L1/L2 命中 | 已有,且推翻了「被 L2 接住」——实为 L1(命中率 83.2% 对 L2 0.94%) | `EXP-K07` §6.3 |
| 4090 上的 bank conflict | `gemm` / `flash-attn` / `softmax` / `gemv` 已有 | §5.1、§7.2、`EXP-K07` §5.4 |

上表 `fused-norm` 那两行(DRAM 字节、L1/L2 命中)采自向量化修复前的 `.so`,
仍是有效的历史基线,但不描述当前代码,引用时必须写明「对应修复前的版本」(§5.3、§6.1)。
带宽侧不在此列:修复前后各 3 轮的 raw 已由 `EXP-K08` 落盘,那一格不缺。

**还缺的四件**,按能不能靠现有产物解决排序:

| 缺口 | 为什么还缺 | 怎么补 |
|---|---|---|
| `rope` / `activation` / `w8a8` 三个算子一份计数器报告都没有 | 采集主机那一轮按任务书跳过了它们 | 下次采集加这三个 op;在此之前这三节的运行时命题一律标「推断」 |
| swizzle 前后对照 | 已证 smem 是 FA2 与 `gemm` 的瓶颈,**未证 swizzle 能关掉它** | 需要 v5(mma PTX + ldmatrix + 手写 swizzle)落地后再采一轮,两份对照 |
| profiler 钉住的 shape 与 bench 报数字的 shape 不是同一个 | 如 `gemv` 的 34.1% 在计数器那个点上只有 1.4%,两者不是同一测量点 | 让 profiler 钉在 bench 报出该数字的同一 size 上重采(`EXP-K07` §6.6b) |
| 向量化修好之后的计数器对照 | 现有报告采的全是**未向量化**的版本,`fused-norm` 那 6 份 `.ncu-rep` 已经不描述当前 `.so`(带宽侧已由 `EXP-K08` 的 A/B 补上,缺的只有计数器侧) | `fused-norm` 代码已修好、静态已验(§5.3),等采集主机空出来重采一轮即可;rope / activation / w8a8 还得先改代码(`EXP-K07` §7.4 第 2 条、`EXP-K08` §7) |

一条纪律:上表第二行最容易被说过头。**「smem 是瓶颈」与「swizzle 能解决它」
是两个命题**,现在只有前者有实测,对外措辞必须把两者分开(`EXP-K07` §7.4 第 5 条)。
红线表的状态与解锁条件以 `LEDGER.md` 为唯一权威,本文只提供证据,不改它。

## 9 复现与维护

```
python3 scripts/sass_ladder.py                   # 十算子全表
python3 scripts/sass_ladder.py --op gemm         # 单算子
python3 scripts/sass_ladder.py --json            # 机器可读,含完整助记符直方图
python3 scripts/sass_ladder.py --op w8a8 --mnemonics
python3 scripts/sass_ladder.py --recheck-sm89    # sm_75 产物的重编等价性核验
```

脚本纯静态,只调 `cuobjdump` 与 `ptxas`,不初始化 CUDA、不碰 GPU,
可以在别人跑训练时随便跑。产物缺失时它会打印该算子的构建命令并跳过;
二进制里出现而版本梯表里没有的 Function 会列在「未列入版本梯」一节,
不会静默消失(这是重编译改了 mangled 名时的兜底)。

维护约定四条:

1. **表格里的判据数字必须能由该脚本重放。** 新增判据请先把对应的键加进
   脚本的 `sig_of()`,再写进本文,不要在文档里手算一个脚本给不出的数。
   §1 列出的五类例外(`.reuse`、地址立即数、循环体切片、PTX 结论、occupancy 换算)
   引用时必须写清出处与命令,不能混在「脚本输出」里。
2. **改口径改一处。** 判据全部从活指令的助记符直方图派生,
   不要在文档里二次 `grep` 原始反汇编——那会造成「表里改了、正文没改」的分叉。
3. **重编译之后先跑一次脚本再改文档。** 尤其是 §6.6 那条 sm_75 的问题一旦修掉,
   四个算子的寄存器数会整体变化,所有 occupancy 论证要重算,
   §4 第 5 条那批「sm_75 口径」标注也要连带清掉。
   四个 torch 扩展(`fused-norm`/`rope`/`activation`/`w8a8`)还多一条:
   脚本读的是 `~/.cache/torch_extensions/` 里的 `.so`,**它可能落后于 `src/`**——
   做过对照实验(临时改回旧写法编一版)之后,缓存里留下的是对照组的产物,
   而源码已经改回来了,此时脚本会照着旧二进制输出一张与代码不符的表。
   取表之前先确认 `.so` 比对应的 `.cu` 新;不确定就在扩展目录里跑一次 `ninja`
   (纯编译链接,不初始化 CUDA、不碰 GPU),再取表。
4. **运行时的量一律交出去。** 时延、带宽、命中、冲突、stall、achieved occupancy
   都不在本文的能力范围内。已有实测的指向 `records/EXP-K07` 或仓内 `.ncu-rep`(§7.2),
   没有实测的按 §8 记在缺口表里,不要在本文里用静态条数替代。

与 `docs/ncu_reading_guide.md` 的关系:那篇讲「有了计数器该看什么」,本篇讲
「编译产物里能看到什么」,两篇覆盖同一批优化手法、互不重复。该篇 §4
「优先转实测的既有推断」清单里,第 1、2、5 条已由 `EXP-K07` 闭合;
剩余条目应与本文 §8 的缺口表对齐,两处不要各记一份。
