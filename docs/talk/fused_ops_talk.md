# 讲稿 · 融合逐元素算子三件套(15 分钟)

> 目标听众：面试官。目标是让对方相信我**知道优化该往哪儿使劲、也知道什么时候该停手**，而不是展示我会写 kernel。配套：深度讲义 `docs/lectures/03_memory_bound_fusion.md`，数字出处 EXP-K05《LLM 融合逐元素算子三件套》 / llm-engine#EXP-D23《融合逐元素算子接入》。

---

## 0 一句话开场

"我给 LLM 前向里三个最高频的逐元素算子写了手写 CUDA 版本梯，接进自研引擎后 decode 吞吐涨了 44%。但这个项目真正的产出不是那 44%，是搞清楚了**手写 CUDA 在什么条件下还有价值**——结论是：在这类算子上，贴上带宽墙之后它就没价值了。"

先给结论、再给证据，而且结论是"我的东西在某些场景下没用"。这比"我比 PyTorch 快 5 倍"更容易让对方往下听。

---

## 1 背景:为什么盯上这三个算子(2 分钟)

一次 Transformer 前向里，除了 GEMM 和 attention，还有一堆看起来是零头的操作： 残差加、RMSNorm、RoPE、SwiGLU 的门控乘。直觉说这些不值得管。

直觉错在把"算力占比"当成"时间占比"。这些算子的算术强度是 0.25 FLOP/B， 而 4090 的平衡点是 164 FLOP/B——它们的耗时完全由搬了多少字节决定。而 PyTorch 的原生实现搬得极多：一次 RMSNorm 要跑 add、pow、mean、rsqrt、mul、mul 六个 kernel，每个都把整个张量读进来算完再写回去。

实测：在 0.6B 上这些"零头"占前向时间约三成。

---

## 2 方法:先算账,再写代码(3 分钟)

"我不是先写 kernel 再测，是先算字节账。"

以 `silu(gate) * up` 为例：未融合要搬 5 次（读 gate、写临时、读临时、读 up、写 out），融合后 3 次。所以融合这一级的加速**上限**是 5/3 = 1.667 倍，一分不多。

实测 1.680 倍。

"这个数对上了，说明我对瓶颈的理解是对的。但更有意思的是**对不上的那几条**。"

---

## 3 主线:一个被数据推翻的预测(5 分钟,重点)

RMSNorm 需要两遍扫行：第一遍求平方和，第二遍归一化。第二遍要么重新读显存， 要么第一遍时就把整行留在寄存器里。

按字节账，寄存器缓存版应该把访存从 5 次降到 4 次，加速 25%。我写了，实测 **0%**。

"我一开始以为是实现问题，查了寄存器有没有溢出到 local memory。都没有。后来发现答案不用 profiler 就能推出来——"

**在白板上写：**

```
v2 有效带宽(按 4 次访存计) = 917 GB/s = 91.0% 峰值
若第二次读真的走 HBM(5 次访存):
    真实带宽 = 917 × 10/8 = 1146 GB/s
4090 峰值 = 1008 GB/s
1146 > 1008  →  物理上不可能
```

"所以那次重读从一开始就命中了缓存，从未到过显存。我省掉的是一次 L1 命中， 不是一次显存访问。**字节账要在 HBM 层面记，不能在指令层面记**——我写在注释里的静态计数是指令级的，它高估了可优化空间。"

讲到这里对方常追一句"你怎么知道是哪一级缓存接住的"。带宽上界只能证明"没出片"，分不出层级；层级是后来用计数器钉死的：同一 HBM 形状下，寄存器缓存版 v4 的 L1 命中率 33.19%、L2 读命中率只有 0.20%，DRAM 读扇区停在算法下界（residual 与 x 各读一遍，实测 2.001×S）——到达 L2 的扇区几乎全部 miss 到显存，收敛发生在 L1（EXP-K09《向量化修复后的扇区账复采》§5.1）。这两步要分开讲：白板反推给的是"没出片"，计数器给的是"停在哪一层"。

这一段是整个讲稿的重心。它展示的是：能从测量本身反推机制，而不是只会跑 profiler； 以及肯把自己被推翻的预测讲出来。

---

## 4 三点曲线:什么时候该用手写 CUDA(3 分钟)

"我之前两个项目已经有两个数据点，这个项目补上第三点。"

| 算子类型 | 手写 CUDA 相对最优对照 |
|---|---|
| 计算主导 GEMM | 85.6% of 真 cuBLAS |
| 融合型 attention(wmma) | 28% of 自家 Triton（跨 harness 对照，推断级） |
| **访存主导融合逐元素** | **与 Triton / torch.compile 打平（±3.3%）** |

"HBM 区间三种实现全部落在 87-92% 峰值，同一算子内两两差距最大 3.3%——出在 rope 的 torch.compile 臂，另两个算子都在 0.3% 以内。所以在这类算子上， 手写 CUDA 没有优势——inductor 自己就能融合出同样的东西。"

**但紧接着必须补两个例外，否则结论是错的：**

- L2 常驻区间：手写相对 torch.compile 快 3.25-7.41 倍
- decode 的 launch 敏感区间：手写相对 Triton 快 2.49-4.86 倍

"而推理引擎恰好常驻这两个区间——小 batch、短序列、逐 token 解码。所以'HBM 区间打平'不等于'手写没用'。**报哪个区间的数字，决定了别人对结论的理解对不对。**"

## 5 收尾:接进引擎才算数(2 分钟)

"单算子跑得快不算数。我把三个算子接进了自研引擎："

| 臂 | TTFT | TPOT | decode |
|---|---|---|---|
| PyTorch 原路径 | 36.31 ms | 32.10 ms | 31.2 tok/s |
| 手写 CUDA | 26.01 ms | 22.28 ms | 44.9 tok/s |

"TTFT -28.4%，TPOT -30.6%，贪心解码 128 个 token 与基线逐个一致。"

"注意算子级的**倍数**在端到端变成了**百分比**——因为 GEMM 仍占大头。把 5 倍说成端到端收益是不诚实的。"

"还有一件必须说的：融合**不是**无损。我用 fp32 前向做真值，bf16 基线自己的偏离是 1.63e-2，融合版是 2.10e-2——融合确实更远离真值，代价约 0.5e-2。原因是残差加与归一化的结合顺序变了，而浮点加法不满足结合律。要消除它得让残差流用 fp32 累积，但那样每元素多搬 2 字节，访存账直接变差。这是个可量化的权衡，不能两全。"

## 6 预备:常见追问

**"你这些数字有没有可能是 harness 的问题？"** "有过一次，而且我可以讲讲怎么抓出来的。Triton 臂一开始测出恰好慢 2 倍。 **恰好整数倍是 harness bug 的指纹，不是性能现象。**我先换粒度、再加连续性断言都无效，然后 dump PTX 看到发的是 `ld.global.v4.b32`，证明向量化没问题； 再单独测那个 kernel（单 kernel 微基准，EXP-K05《LLM 融合逐元素算子三件套》），907 GB/s，和手写持平。回头查 bench，发现我把 `q.clone()` 写进了被计时的闭包里，每次迭代白搬 320 MB。就地算子的 bench 特别容易在这儿翻车。"

**"为什么正确性用 token 序列判而不是 logits？"** "两个都用，但地位不同。logits 的阈值需要校准——bf16 在 28 层累积后本底偏差就有 1.6e-2，阈值稍紧必然失败，和被测对象好坏无关。我这次的门就设错了，判了 FAIL， 但我没改阈值，而是补了一条 fp32 真值臂重新校准。贪心 token 序列是端到端唯一有操作意义的判据，它直接对应用户看到的输出。"

**"下一步做什么？"** "不是继续优化这三个 kernel，它们已经在 90-92% 峰值了。是往上下游融：把 silu_and_mul 做进 down_proj 的 GEMM epilogue，把 gate/up 两次投影合并成一次 GEMM。我实测过打包布局在算子层只有 +1%——**收益不在被改的算子里，在它上下游**， 这也是 vLLM 用打包布局的真实理由。"

---

## 7 不要说的话

- 不说"比 PyTorch 快 5 倍"而不提 torch.compile 打平。
- 不说"精度无损"。
- 不说"引擎快了 30%"——要说"0.6B 上、只改了三个逐元素算子、GEMM 未动"。
- 不把 0.6B 的百分比外推到 8B。
