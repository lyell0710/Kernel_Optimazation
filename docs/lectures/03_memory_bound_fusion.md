## 1 这一篇回答什么问题

一个具体的工程问题：**LLM 前向里那些"不起眼"的逐元素算子，值不值得手写？**

在 Qwen3-0.6B 的一次前向里，除了 GEMM 和 attention，还有一大堆看起来很廉价的操作：残差加、RMSNorm、旋转位置编码、SwiGLU 的门控乘。它们每个元素只做几次乘加，算力上微不足道。直觉会说：这些都是零头，优化 GEMM 才是正事。

但把它们接进引擎实测，替换掉这些"零头"让 decode 吞吐涨了 44%。直觉错在哪？

错在把"算力占比"当成了"时间占比"。这些算子的算术强度极低——RMSNorm 每搬 8 个字节只做 2 次乘加，算术强度 0.25 FLOP/B，而 4090 的平衡点是 164 FLOP/B。它们的耗时不由算力决定，由**搬了多少字节**决定。而 PyTorch 的原生实现搬得极多： 一次 RMSNorm 要跑 add、pow、mean、rsqrt、mul、mul 六个 kernel，每个 kernel 都要把整个张量从显存读进来、算完再写回去。

于是本篇要回答的三层问题是：

1. **怎么算清一个访存主导算子的字节账**，并据此预测每一级优化的收益上限？
2. **字节账在哪一层记**？指令层面的计数会不会骗人？
3. 当带宽被吃满之后，**手写 CUDA 相对 Triton、相对 torch.compile 还剩多少优势**？

第三问是本篇的落点。本仓此前已有两个数据点：计算主导的 GEMM，手写 wmma 够到真 cuBLAS 的 85.6%（讲义 01）；融合型 attention，同一套 wmma 只够到自家 Triton 的 28%（讲义 02）。这一篇补上第三点，把"什么时候该用手写 CUDA"从两个孤立数字变成一条有形状的曲线。

## 2 直觉与第一性原理

### 2.1 一切从 roofline 的另一半开始

Roofline 模型有两条边。讲义 01 关心的是斜边右侧的水平段（算力上限），这一篇关心斜边本身（带宽上限）。

设算子处理 $N$ 个元素，每元素必须搬 $B$ 字节（**算法下界**，即无论怎么实现都省不掉的那些读和写），硬件峰值带宽 $\text{BW}_{peak}$。那么该算子的时间下界是

$$t_{\min} = \frac{N \cdot B}{\text{BW}_{peak}}$$

这个式子朴素到近乎废话，但它给了两件非常实用的东西：

- **一把尺子**：任何实现的"有效带宽" $N\cdot B / t$ 除以 $\text{BW}_{peak}$，就是它离最优有多远。90% 意味着基本到头了，50% 意味着还有一倍空间。
- **一个上限**：如果某级优化把每元素搬的字节从 $B_1$ 降到 $B_2$，那么它的加速上限就是 $B_1/B_2$，一分不多。

第二点是本篇方法论的核心：**先算字节账，再写代码**。字节账给出的比值是可证伪的预测——写完一测，对上了说明理解正确，对不上说明模型里少了什么。而"少了什么" 往往比"对上了"更有价值（§3.3 会看到一个典型例子）。

### 2.2 三个算子的字节账

**fused_add_rmsnorm**。语义是 `residual += x; out = rmsnorm(residual) * w`，两个输出都要：`residual` 给下一层当残差流，`out` 给本层分支当归一化输入。算法下界：

$$\underbrace{\text{读 } x}_{1} + \underbrace{\text{读 residual}}_{1} + \underbrace{\text{写 residual}}_{1} + \underbrace{\text{写 out}}_{1} = 4 \text{ 次} \times 2\text{B} = 8 \text{ B/元素}$$

权重 $w$ 只有 $H$ 个元素、被所有 token 复用，不计入行级账。

未融合的实现要搬多少？一个 add kernel（读 x、读 res、写 res = 3 次），再一个 rmsnorm kernel（读 res 求平方和、读 res 归一化、写 out = 3 次），合计 6 次。所以"融合"这一级的理论上限是 $6/5$ 或 $6/4$，取决于第二遍重读算不算——这个问号后面会变成本篇最有意思的一段。

**rope**。把 head_dim 的前后两半 $(x_1, x_2)$ 看成 $D/2$ 个复数的实部与虚部， 整体乘 $e^{i\theta}$：

$$\begin{aligned} \text{out}[i] &= x_1[i]\cos\theta_i - x_2[i]\sin\theta_i \\ \text{out}[i + D/2] &= x_2[i]\cos\theta_i + x_1[i]\sin\theta_i \end{aligned}$$

注意两行右边用的是**同一个** $\theta_i$。这不是巧合：cos/sin 表在生成时把 $D/2$ 个频率重复了两遍（`cat((freqs, freqs))`），就是为了让前后两半共用一组频率。这个结构决定了字节账能砍半——一个线程同时处理一对 $(i,\ i+D/2)$， 就只需要读一次 cos、一次 sin。

朴素实现（一线程一元素）：读自己 + 读配对元素 + 读 cos + 读 sin + 写回 = 5 次。配对实现：每对读 2 写 2，加 cos/sin 各 1，除以 2 个元素 = 3 次。上限 $5/3$。

**silu_and_mul**。`out = silu(gate) * up`。未融合要物化 `silu(gate)`： 读 gate、写 tmp、读 tmp、读 up、写 out = 5 次；融合后读 gate、读 up、写 out = 3 次。上限 $5/3 \approx 1.667$。这一条后面实测 1.675，是三个算子里字节账预测最准的一个。

### 2.3 为什么中间量是罪魁

上面三笔账有一个共同结构：**未融合版本多出来的字节，全部是"中间量的往返"**。 `silu(gate)` 那份临时张量、rmsnorm 前那份写完立刻读回的 residual——它们在数学上不存在，纯粹是"一个 kernel 只能做一件事"这个实现约束的产物。

这就是"融合免搬运"这句话的字面含义：融合不省任何一次乘法，它只是让中间结果留在寄存器里，不去显存转一圈。在算术强度 0.25 FLOP/B 的算子上，这一圈就是全部。

## 3 完整推导与机制

### 3.1 归约:为什么必须两级,以及 shuffle 换掉了什么

RMSNorm 需要一整行的平方和。行长 $H$ 通常是 1024–8192，而一个 block 最多 1024 个线程，所以每个线程先在寄存器里累加自己那几个元素，然后 block 内做一次归约。

朴素的 block 归约是共享内存上的树形折叠：每轮活跃线程减半，共 $\log_2(\text{blockDim})$ 轮，**每轮一次 `__syncthreads()`**。blockDim=512 时是 9 次同步、约 1000 次共享内存读改写。

两级 shuffle 归约把它压成：warp 内 5 轮 `__shfl_xor_sync`（纯寄存器，零同步）， 每个 warp 的和写进 `smem[32]`，再由第 0 个 warp 折叠一次。同步从 9 次降到 2 次， 共享内存事务从约 1000 次降到 32 次。

warp 内折叠为什么用 `xor` 而不是 `down`(`fused-norm/include/fused_norm.h:63-68`)：

```cuda
__device__ __forceinline__ float warp_reduce_sum(float v) {
#pragma unroll
    for (int off = 16; off > 0; off >>= 1)
        v += __shfl_xor_sync(0xffffffff, v, off);
    return v;
}
```

`__shfl_down_sync` 做的是单向折叠，结束后只有 lane 0 手里是全和，下游要用还得广播一次。`__shfl_xor_sync` 是蝶形交换：第 $k$ 轮每条 lane 与它异或 $2^k$ 的那条 lane 交换并相加，$\log_2 32 = 5$ 轮之后**32 条 lane 各自都持有全和**。本算子下游每个线程都要用 `rstd` 去归一化自己那几个元素，xor 版正好省掉广播。

`mask` 写死 `0xffffffff` 而不是 `__activemask()`，是有前提的：本函数只在"整个 warp 都活着"的位置调用。行长 $H$ 由循环的 stride 覆盖，不做提前 `return`——即使某个线程的循环体一次都没进，它本身仍会走到归约这一行。如果在 `if` 分支里调用这个函数，失活的 lane 不参与 shuffle，活着的 lane 会读到未定义值。这是 warp 级原语最常见的错用方式，症状是"偶发的、随 $H$ 变化的错误结果"——不崩、不 NaN，只是偶尔算错，极难定位。

### 3.2 向量化:半个事务的浪费

GPU 的全局访存以 32 字节的 sector 为最小单位，一个 warp 的 32 条请求会被合并成若干个 128 字节事务。标量 bf16 时，一个 warp 一次只覆盖 $32 \times 2 = 64$ 字节—— **恰好半个事务**。硬件仍然按整事务的粒度动作，另一半带宽被丢掉。

改成每条 lane 一次搬 16 字节（8 个 bf16）后，一个 warp 一次请求 $32 \times 16 = 512$ 字节 = 4 个满事务，事务利用率 100%。同时每元素的访存指令数降到 1/8，LSU 发射压力与 MIO 队列排队一起下来。

代价是形状约束：要求 $H \equiv 0 \pmod 8$ 且行首 16 字节对齐。torch 张量基址是 256 字节对齐，行首偏移是 $2H$ 字节，$H$ 为 8 的倍数即满足。Qwen3 的 hidden (1024/4096/8192)与 head_dim(128)全都满足。不满足时必须在入口拒绝并回落标量版本——RMSNorm 算错不会崩，只会让输出悄悄漂移，把校验交给运气是不可接受的。

还有一个容易漏的细节：承载 16 字节的结构体必须写 `alignas(16)`。少了这个属性， nvcc 会保守地把它拆成 4 条 64 位访问，向量化收益直接归零——代码看起来一模一样， 性能差一倍。

### 3.3 寄存器缓存:一个被数据推翻的预测

RMSNorm 有个绕不开的结构：平方和必须等整行扫完才知道，而 `rstd` 又是归一化的必要输入。所以第二遍必须再拿到一次行数据。要么重新从显存读（v1–v3），要么在第一遍时就把它留在寄存器里（v4）。

按字节账，v4 应该把每元素访存从 5 次降到 4 次，理论加速 $5/4 = 1.25$。实现上要点在于：每个线程为它负责的每一"波"留 4 个寄存器，而**波数必须是编译期常量**，数组下标才能被完全展开（`fused-norm/src/fused_norm_v4.cu:60-77`）：

```cuda
    for (int k = 0; k < MAX_WAVES; ++k) {
        const int i = threadIdx.x + k * blockDim.x;
        if (i < HV) {
            BF16x8 rv = res[i];
            BF16x8 av = xr[i];
            BF16x8 sv;
#pragma unroll
            for (int j = 0; j < 4; ++j) {
                float2 r = __bfloat1622float2(rv.h[j]);
                float2 a = __bfloat1622float2(av.h[j]);
                float2 s = make_float2(r.x + a.x, r.y + a.y);
                acc += s.x * s.x + s.y * s.y;
                sv.h[j] = __float22bfloat162_rn(s);
            }
            res[i]   = sv;      // 写回显存:下一层的残差流要用
            cache[k] = sv;      // 同一份值留在寄存器:第二遍不再回显存取
        }
    }
```

写成"固定波数 + 越界守卫"而不是 `while` 循环，是因为循环次数必须是编译期常量， `#pragma unroll` 才能把 `cache[k]` 的下标常量化。若写成运行期变量下标，nvcc 会把 `cache[]` 放进 local memory——那其实就是显存，优化不仅归零还会更慢。这是寄存器缓存最常见的翻车方式。

**然后实测告诉我们：v4 相对 v3 是 -0.2%。零收益。**

为什么？答案可以从测量本身反推，不需要任何 profiler：

v2 的有效带宽，按 4 次访存（8 B/元素）计，是 920 GB/s = 4090 峰值的 91.3%。假设第二遍重读真的走到了 HBM，那么真实字节数是 5 次访存 = 10 B/元素，真实带宽应为

$$920 \times \frac{10}{8} = 1150\ \text{GB/s} > 1008\ \text{GB/s}$$

**超过物理峰值，不可能。** 所以这次重读从一开始就被缓存接住，从未到过显存。**计数器已直接证实这一点，并把层级钉到了 L1**：DRAM 读扇区恒为 2.000 倍算法下界，L1 命中率 83.2%，而 L2 读命中率只有 0.94%（EXP-K07《NCU 计数器闭环》）。 v4 消掉的是一次缓存命中，不是一次显存访问。

这里有一条方法论结论，比 v4 本身重要得多：

> **字节账要在 HBM 层面记，不能在指令层面记。**

**后续（EXP-K09）：向量化修复之后，这张账的上半部分整个换了一遍，下半部分纹丝不动。**

| 层级 | 修复前 v3 / v4 | 修复后 v3 / v4 |
|---|---|---|
| L1TEX 读请求（指令层） | 16.000 / 12.000 ×S | **4.000 / 3.000 ×S** |
| L2 读 | 2.126 / 2.019 ×S | 2.044 / 2.004 ×S |
| **DRAM 读** | 2.001 / 2.000 ×S | **2.001 / 2.001 ×S** |
| L1 命中率 | 86.87% / 83.19% | 49.34% / 33.19% |

（S = 单张量一趟 = 8,388,608 sector，grid `(32768,1,1)` 的 HBM regime。）

指令层降了整整 **4.00 倍**——正是 16 B / 4 B，一条 `LDG.E.128` 取代四条 `ld.global.v2.u16`。
而 DRAM 读**一动没动**：算法要搬多少字节，不因你怎么发指令而改变。
这正是上面那句话的最强形式——**同一次修改，在指令层是 4 倍，在 HBM 层是 0**。

还有一件事只有把标量版拉进来才看得出来：v1/v2（没有 `BF16x8`）的 L1TEX 一直是 **4.000×S**。
也就是说修复前的 v3/v4（16/12×S）**比标量版还差 3–4 倍**——那个"向量化优化"在兑现之前
不是没用，是**负优化**，只不过被 L1 全部吸收，在 DRAM 侧完全看不出来。

写在 kernel 注释里的静态计数是指令级的，它把"发出一次 load 指令"等同于"搬一次显存"，于是高估了可优化空间。而对本算子，第一遍刚写完的那一行（8 KB）在第二遍读它时还热着，根本不出片。想验证这条推断的直接办法是看 `lts__t_sectors_srcunit_tex_op_read.sum` 与 `dram__sectors_read.sum` 的比值(这两个指标不在 details 页,须用 `ncu -i <rep> --page raw --csv` 读)，但本机容器没有性能计数器权限，所以它目前是一条**从带宽上界反推的推断，不是计数器实测**——这个区分必须写清楚。

### 3.4 就地更新的读写冲突:rope 的第一个坑

rope 的朴素写法是"一线程一元素"：线程 $g$ 负责输出的第 $g$ 个位置，自己去读配对元素。前半的线程要读 `t[g+half]`，后半的线程要读 `t[g-half]`——**互为对方的输入**， 而两者又都要写自己。

不同 block 之间没有任何执行顺序保证。后执行的线程会读到已经被覆盖的值。这类 bug 不崩、不 NaN、不报错，只是结果悄悄错一半，且随 block 调度顺序随机变化。

朴素版只能付出代价：先把整份输入拷到临时缓冲，kernel 从缓冲读、往原地写——多了一次全量读 + 一次全量写。

配对版让同一个线程同时持有一对元素，依赖被收进线程内部，冲突自然消失（`rope/src/rope_v1.cu:31-39`）：

```cuda
        const float c = __bfloat162float(cosb[(long long)tok * D + i]);
        const float s = __bfloat162float(sinb[(long long)tok * D + i]);
        const float x1 = __bfloat162float(t[base]);
        const float x2 = __bfloat162float(t[base + half]);

        // 复数乘法 (x1 + i*x2) * (c + i*s) 的实部与虚部。
        // 两个输出都算完再写,写的顺序无关紧要 —— 依赖已被收进寄存器。
        t[base]        = __float2bfloat16(x1 * c - x2 * s);
        t[base + half] = __float2bfloat16(x2 * c + x1 * s);
```

两个输出都在寄存器里算完再写，写的先后就无所谓了。所以 v0→v1 的 1.81 倍提速里， **大头是消掉了那份临时缓冲的往返，不只是"少读一次 cos"**——如果只看"cos/sin 读了两次变一次"，会以为收益只有 $5/4$，实际是 $7/3$（把临时缓冲的 2 次也算进去）。再一次说明：字节账要把实现被迫付出的开销算进去，不能只算算法上的。

### 3.5 免表:一个赌注,和它为什么只赢了一点

cos/sin 表要占带宽。能不能不查表，直接在 kernel 里算？

$\theta = (\text{pos\_offset} + \text{token}) \times \text{inv\_freq}[i]$，然后一次 `__sincosf` 同时出 sin 和 cos。`inv_freq` 只有 $D/2$ 个 float（head_dim=128 时 256 字节），常驻 L1。字节账从 3 降到 2(`rope/src/rope_v4.cu:73-83`)：

```cuda
        for (int j = 0; j < 4; ++j) {
            float2 x1 = __bfloat1622float2(a.h[j]);
            float2 x2 = __bfloat1622float2(b.h[j]);
            float c0, s0, c1, s1;
            __sincosf(pos * fr[2 * j],     &s0, &c0);
            __sincosf(pos * fr[2 * j + 1], &s1, &c1);
            o1.h[j] = __float22bfloat162_rn(
                make_float2(x1.x * c0 - x2.x * s0, x1.y * c1 - x2.y * s1));
            o2.h[j] = __float22bfloat162_rn(
                make_float2(x2.x * c0 + x1.x * s0, x2.y * c1 + x1.y * s1));
        }
```

跑之前写下的预测是：**v4 ≈ v3(±5%)**，理由是 cos/sin 表本身很小（head_dim=128、T=32768 时只有 8 MB），大概率整份常驻 4090 的 72 MB L2——也就是说 v3 那两路"表访存"根本没走到 HBM，v4 省掉的是 L2 命中而不是显存访问。

实测 +2.1%，落在预测区间内。假设成立。

这一级还有一个设计教训。v4 最初写成了**标量版**免表，与向量化的 v3 相比同时变了两个变量（向量化、表/现算），实测慢 9.9%，而这个数字什么也说明不了——不知道是免表不好，还是没向量化的锅。重写成"v3 + 免表"隔离出单一变量后，才拿到那个干净的 +2.1%。

> **版本梯的每一级只准改一件事，否则整条梯子讲不出因果。**

免表还有一条真实的适用边界必须说清楚：`__sincosf` 是 SFU 的硬件近似，相对误差约 $10^{-6}$，远小于 bf16 的尾数分辨率 $2^{-8} \approx 4\times10^{-3}$，精度上完全够。但它的参数规约有范围：$\theta = \text{pos} \times \text{inv\_freq}$，最低频的 `inv_freq` 接近 1，pos 可达 32K 时 $\theta$ 到 $3\times10^4$，硬件规约仍准确； 上下文再长一个量级（$>10^5$ token）就需要先做手工规约，否则精度会塌。

## 4 代码逐段走读(按执行顺序)

以 fused_add_rmsnorm 的 v1 为例，它是整条梯子的转折点——从"两个 kernel"变成 "一个 kernel"，字节账第一次下降。

### 4.1 第一遍:三件事一次读完成

(`fused-norm/src/fused_norm_v1.cu:34-42`)

```cuda
    for (int i = threadIdx.x; i < H; i += blockDim.x) {
        float s = __bfloat162float(res[i]) + __bfloat162float(xr[i]);
        res[i] = __float2bfloat16(s);   // 立刻写回:下一层要拿它当残差
        // 注意这里累加的是 fp32 的 s,而不是舍回 bf16 再读出来的值。
        // 与 vLLM 一致。若改成累加 __bfloat162float(res[i]) 的回读值,
        // 结果会多一次舍入误差,且强制了写后读依赖,编译器无法把 store
        // 与后续计算重叠 —— 正确性差异极小,性能差异可观。
        acc += s * s;
    }
```

这段循环体同时做了三件事：算加法、把结果写回显存、把平方累加到寄存器。 v0 里这三件事分属两个 kernel，中间隔着一次完整的显存往返。

有一个细节值得停一下：第 8 行累加的是 `s`（fp32 的和），不是 `res[i]`（刚写回去、舍成 bf16 的值）。两种写法在数值上差一次舍入，几乎看不出来； 但在性能上差别可观——如果读回 `res[i]`，就人为制造了一条"写后读"依赖， 编译器无法把这条 store 与后面的计算重叠，整条流水被钉住。 **"顺手回读一下"是最容易无意中插入串行依赖的写法之一。**

累加用 fp32 而不是 bf16，则是精度上的硬要求：bf16 只有 8 位尾数，$H=4096$ 个平方直接在 bf16 上累加会把和的低位全部吃掉，相对误差能到 $10^{-2}$ 量级。

### 4.2 归约与 rstd

`block_reduce_sum(acc, smem)` 之后，`rstd = rsqrtf(sumsq / H + eps)`。用 `rsqrtf` 而不是 `1.f/sqrtf`：前者是一条硬件指令（MUFU.RSQ），后者是平方根加除法两条长延迟指令。逐行只算一次，收益微乎其微，但没有理由不用。

调用点必须在所有线程都能到达的位置，不能在 `if` 分支里——理由见 §3.1。

### 4.3 第二遍:归一化与舍入顺序

```cuda
        __nv_bfloat16 n = __float2bfloat16(__bfloat162float(res[i]) * rstd);
        orow[i] = __hmul(n, w[i]);
```

这里的舍入顺序是**先把归一化结果舍到 bf16，再与 bf16 权重相乘**。顺序若反过来（在 fp32 里乘完权重再舍），数值上更准，但与 HF/vLLM 不一致——接进引擎后逐位对拍会看到末位差异。手写 kernel 要替换生产实现，就必须复刻它的舍入顺序， "更准"在这里反而是 bug。

另外 torch 的扩展编译会定义 `__CUDA_NO_BFLOAT16_CONVERSIONS__` 与 `__CUDA_NO_HALF_OPERATORS__`，所以 bf16 的隐式转换和 `operator*` 都不可用， 必须显式写 `__float2bfloat16` / `__bfloat162float` / `__hmul`。

### 4.4 向量化版的对应段落

(`fused-norm/src/fused_norm_v3.cu:53-68`)

```cuda
    for (int i = threadIdx.x; i < HV; i += blockDim.x) {
        BF16x8 rv = res[i];
        BF16x8 xv = xr[i];
        BF16x8 sv;
#pragma unroll
        for (int j = 0; j < 4; ++j) {
            // 成对转换:__bfloat1622float2 是一条指令处理两个元素,
            // 比拆成两次 __bfloat162float 少一半转换指令。
            float2 r = __bfloat1622float2(rv.h[j]);
            float2 a = __bfloat1622float2(xv.h[j]);
            float2 s = make_float2(r.x + a.x, r.y + a.y);
            acc += s.x * s.x + s.y * s.y;
            sv.h[j] = __float22bfloat162_rn(s);
        }
        res[i] = sv;                              // 一次 16B store
    }
```

结构与 v1 完全同构，只是把"一个元素"换成"一个 16 字节块"。`__bfloat1622float2` 一条指令转两个元素，比拆成两次单元素转换少一半转换指令；写回时 `__float22bfloat162_rn` 同理。`#pragma unroll` 让 4 次内层迭代完全展开， `rv.h[j]` 的下标常量化，数据留在寄存器。

### 4.5 silu 的融合体

(`activation/src/silu_and_mul_v1.cu:21-26`)

```cuda
    for (long long i = blockIdx.x * (long long)blockDim.x + threadIdx.x;
         i < n; i += (long long)gridDim.x * blockDim.x) {
        const float g = __bfloat162float(gate[i]);
        const float u = __bfloat162float(up[i]);
        out[i] = __float2bfloat16(silu(g) * u);
    }
```

`silu(g)` 的结果连一个具名变量都不需要，直接进乘法。v0 里它是一整份与 gate 等大的显存张量（$T=8192,\ I=12288$ 时是 200 MB 写 + 200 MB 读）。

`silu` 内部的 sigmoid 在 fp32 里算，与 PyTorch 对 bf16 的 opmath 一致。直接在 bf16 上算 `exp`，$|x|$ 稍大就会明显失真——bf16 只有 8 位尾数，exp 的输入误差会被指数放大成输出的相对误差。

用 grid-stride 循环而不是"一线程一元素"，是为了让同一份代码对任意规模都正确（$T \times I$ 可达 $10^8$，一次 launch 的 block 数有上限），且 block 数可以按 SM 数来调，避免尾部 wave 的负载不均。

## 5 实验数据怎么读

### 5.1 先看区间,再看数字

同一个算子在不同工作集大小下是**不同的算子**。4090 的 L2 是 72 MB；工作集小于它时，测到的是 L2 带宽（可达 3000 GB/s 量级），大于它时才是 HBM 带宽（峰值 1008 GB/s）。

本篇所有"有效带宽"都按**算法下界字节数**计算。于是有一个方便的自检： **这个数超过 1008 GB/s，就说明数据落在 L2**。它不是错误，是区间指示器。

三个算子的 HBM 区间结果（3 轮 mean，GB/s，括号内为占 1008 峰值的百分比）：

| 版本 | fused-norm | rope | activation |
|---|---|---|---|
| v0 未融合 | 581.5 (57.7%) | 430.9 (42.7%) | 540.9 (53.7%) |
| v1 融合 | 877.3 (87.0%) | 779.0 (77.3%) | 907.7 (90.1%) |
| v2 | 920.1 (91.3%) | 770.6 (76.5%) | 918.8 (91.2%) |
| v3 | 920.3 (91.3%) | 887.0 (88.0%) | **927.7 (92.0%)** |
| v4 | 918.7 (91.1%) | **905.9 (89.9%)** | — |
| PyTorch eager | 176.2 (17.5%) | 177.6 (17.6%) | 555.5 (55.1%) |
| torch.compile | 917.4 (91.0%) | 877.2 (87.0%) | 925.7 (91.8%) |
| Triton | 922.1 (91.5%) | 898.5 (89.1%) | 928.0 (92.1%) |

### 5.2 字节账预测对了几条

activation 的 v0→v1 预测 $5/3 = 1.667$，实测 **1.675**。几乎精确。

fused-norm 的 v0→v1 预测 1.20，实测 **1.509**，比预测好。原因在于 v0 的两个 kernel 之间隔了一整趟 1 GB 的写回：第二个 kernel 开始读时，第一个 kernel 写下的数据早就被挤出 L2，首次读全部 miss。静态字节账假设了"读就是读"，没有把缓存状态算进去。

fused-norm 的 v2→v3→v4 预测大幅提升，实测 0%。原因见 §3.3——带宽已经贴墙， 且被预测省掉的那次读本来就在缓存里。

**四条预测，一条精准、一条偏保守、两条被推翻。** 被推翻的两条给出的信息最多： 它们暴露了字节账模型缺了"缓存层级"这一维。一个从不出错的预测模型，通常是因为它没被认真检验过。

### 5.3 基线的自检条件

activation 的 v0 是 540.9 GB/s,PyTorch eager 是 555.5 GB/s——**基本同速**。

这不是巧合，是设计出来的自检：v0 被刻意写成"手写但不优化"，逐条复刻 eager 的执行方式（两个 kernel、一份临时显存）。如果 v0 比 eager 快很多，说明 eager 有额外开销没被复刻；如果 v0 比 eager 慢很多，说明 v0 写错了。两者同速，才能说明后面 1.675 倍的加速确实来自融合，不是来自"跟一个稻草人比"。

**做版本梯一定要给 v0 设一个外部锚点**，否则整条梯子的加速倍数都是自说自话。

fused-norm 那边 eager 只有 176.2 GB/s（比 v0 慢 3.3 倍），因为 PyTorch 的 rmsnorm 要跑六个 kernel 并物化 fp32 中间量——那是 eager 自身的实现代价，不是基线设计问题。

### 5.4 同一个改动,两个区间,四十倍的收益差

rope 的 v1→v2 是"把 q 和 k 合并进一次 launch"。

- HBM 区间（T=32768）：779.0 → 770.6，**-1.1%**，在 3 轮 std(±3.7)之内，等于没变。
- decode 区间（T=1）:10.30 → 7.21 us,**1.43 倍**。

带宽已经饱和时，省一次 launch 毫无意义；T=1 时一次 launch(3–5 us)就能主导总时间。同一个改动，收益差四十倍。

> **任何"这个优化有多少收益"的问题，不给工作区间就是没有答案的。**

### 5.5 带宽墙前的收敛

HBM 区间里，手写 CUDA 最优、Triton、torch.compile 三者的数字是：

- fused-norm:920.3 / 922.1 / 917.4
- rope:905.9 / 898.5 / 877.2
- activation:927.7 / 928.0 / 925.7

**两两差距全部小于 2%，统统落在 88–92% 峰值。** 而未融合的 PyTorch eager 落后 1.7–5.2 倍。

于是本篇的核心结论：

> **分水岭是「融不融合」（1.7–5.2 倍），不是「用什么语言写」(<2%)。**

配合讲义 01、02 的结论，得到"什么时候该用手写 CUDA"的三点曲线：

| 算子类型 | 手写 CUDA 相对最优对照 | 出处 |
|---|---|---|
| 计算主导 GEMM | 85.6% of 真 cuBLAS | 讲义 01 / EXP-K02 |
| 融合型 attention(wmma) | 28% of 自家 Triton | 讲义 02 / EXP-K03 |
| 访存主导融合逐元素 | 与 Triton / torch.compile 打平（±2%） | 本篇 / EXP-K05 |

手写 CUDA 的价值集中在**需要 mma 级寄存器控制**的场合。访存主导的算子上， 写 Triton 或直接开 torch.compile 能拿到同样的数字。

但这个结论有两个例外，而且都很实用：

- **L2 常驻区间**：手写相对 torch.compile 快 3.19–10.6 倍。
- **decode 的 launch 敏感区间**：手写相对 Triton 快 2.5–11 倍。

这两个区间恰恰是推理引擎最常落在的地方（小 batch、短序列、逐 token 解码）。所以"HBM 区间打平"不等于"手写没用"——**报哪个区间的数字，决定了别人对你结论的理解是否正确**。

### 5.6 接进引擎才算数

三个算子接进自研引擎（Qwen3-0.6B，batch=1，prompt 512，decode 128）， 相对 PyTorch 原路径：

| 臂 | TTFT (ms) | TPOT (ms) | decode (tok/s) |
|---|---|---|---|
| baseline | 36.308±0.541 | 32.103±0.302 | 31.15±0.29 |
| 手写 CUDA | 26.011±0.502 | 22.280±0.053 | 44.88±0.11 |
| Triton | 28.875±0.201 | 25.412±0.052 | 39.35±0.08 |

手写 **TTFT -28.4%、TPOT -30.6%、吞吐 +44.1%**；贪心解码 128 token 与基线逐个一致。

两点值得读：

1. **算子级的"倍数"被稀释成端到端的"百分比"。** 算子上是 1.7–5.2 倍，端到端只有 -30%，因为 GEMM 仍占大头。这个稀释率本身是信息：在 0.6B 这个尺度上， 逐元素算子占前向时间约三成。
2. **Triton 端到端只拿到手写的七成收益（-20.5% vs -28.4%），与算子级"HBM 打平" 看似矛盾，其实一致。** 引擎里 0.6B 的实际形状工作集只有几 MB，落在 L2 常驻与 launch 敏感区间——正是手写领先 3.2–10.6 倍与 2.5–11 倍的那两个区间。

## 6 误区与边界

**误区一："逐元素算子是零头，不用管。"** 算力上是零头，时间上不是。0.6B 上它们占前向约三成。

**误区二："融合是无损优化。"** 不是。融合改变了残差加与归一化的结合顺序，而浮点加法不满足结合律。以 fp32 前向为真值，bf16 基线自己的偏离是 $1.628\times10^{-2}$，融合版是 $2.103\times10^{-2}$——**融合确实更远离真值，代价约 $0.5\times10^{-2}$**，与 bf16 本底同量级但可测量。诚实的说法是"数值可信度仍在 bf16 固有噪声量级内"， 不能说"精度无损"。要消除它需要让残差流以 fp32 累积（residual 从 2 B/元素变成 4 B/元素），访存账直接变差——这是一个可量化的精度/性能权衡，不能两全。

**误区三："手写比 PyTorch 快 5 倍。"** 比 eager 快 5 倍，比 torch.compile 打平。省略后半句就是选择性报告。inductor 在这类算子上会自动做同样的融合，拿到同样的带宽。

**误区四："有效带宽超过峰值 = 测错了。"** 不是错，是数据落在 L2 的指示器。真正的错误是**只测这一个区间**就下结论。

**边界一：形状敏感。** v3/v4 要求 $H \equiv 0 \pmod 8$、rope 要求 $D \equiv 0 \pmod{16}$。不满足必须在入口拒绝并回落，不能让 kernel 越界。

**边界二：decode 时只有一个 block。** $T=1$ 时 grid 只有 1 个 block，128 个 SM 用了 1 个。此时无论怎么优化 kernel 都没用，正解是 CUDA Graph 把 launch 开销折叠掉。

**边界三：结论不外推到更大模型。** 8B 上 GEMM 占比更高，逐元素算子的收益会被进一步稀释。0.6B 的 -30% 不能直接说成"引擎快了 30%"。

**边界四："第二次读被缓存接住"已由计数器实测证实。** 原为带宽上界反推的推断，现有 4090 计数器数据：DRAM 读 2.000 倍算法下界、L1 命中率 83.2%、L2 读命中率 0.94%，接住它的是 L1 而非 L2（EXP-K07）。以下关于当时证据等级的说明保留作方法论记录——本机容器没有性能计数器权限。

**边界五：缓存命中率不是"越高越好"，它的分母会动。** 向量化修复后 `fused-norm` v4 的
L1 命中率从 **83.19% 掉到 33.19%**。这看着像退步，其实是同一件好事的另一面：
命中率精确等于 $1 - \text{DRAM} / \text{L1TEX}$，而修复把分母（总请求）缩小了 4 倍，
分子（真正出片的量）本来就该原地不动。

$$1 - \frac{2}{12} = 83.3\%\quad\longrightarrow\quad 1 - \frac{2}{3} = 33.3\%$$

实测 83.19% 与 33.19%，两边都对得上。**把命中率当成单调的好坏指标，在这里会得出完全相反的结论**——
它会告诉你"缓存变差了"，而真相是访存请求少发了 3/4、DRAM 流量一个字节没多。
命中率是个比值，读它之前先问分母是什么（EXP-K09 §6.1）。

## 7 连环追问

**Q1：为什么 RMSNorm 不能一遍算完？** 平方和要等整行扫完，而归一化又需要它。要么第二遍重读，要么把整行留在片上。唯一的"一遍"方案是 online 归一化（类似 FlashAttention 对 softmax 做的）， 但 RMSNorm 的归约是全行求和而非取最大值，重缩放公式虽然存在，收益却在这里不成立——因为第二次读本来就命中缓存，没有可省的显存访问。

**Q2：v4 的寄存器缓存零收益，那它是不是白写了？** 产出不是加速，是一个从数据反推出来的机制结论：第二次读从未到达 HBM。没有 v4，就没法确定 v3 的 91.3% 是"到顶了"还是"还差一次读"。**版本梯上一级零收益的实验，和一级大幅提速的实验，信息量是同等的。**

**Q3：为什么 warp 归约用 xor 不用 down？** down 结束后只有 lane 0 持有全和，下游要广播；xor 是蝶形交换，32 条 lane 各自都持有全和。本算子每个线程都要用 `rstd`，xor 正好省掉广播。

**Q4：`__shfl_xor_sync` 的 mask 什么时候不能写 `0xffffffff`？** 在分支内调用时。失活的 lane 不参与 shuffle，活着的 lane 会读到未定义值。症状是偶发的、随行长变化的错误结果。本实现靠"循环 stride 覆盖行长、不提前 return"保证整个 warp 都活着。

**Q5：向量化在 fused-norm 上零收益，在 activation 上有收益，为什么？** 取决于上一级离带宽墙有多远。fused-norm 的 v2 已经 91.3%，没有空间； activation 的 v1 是 90.1%，v2 拿到 +1.2%，也基本贴墙了。**同一手法在不同梯子上收益不同，不取决于手法，取决于剩余空间。**

**Q6：rope 为什么要提前到 transpose 之前调用？** 引擎原路径是先 transpose 成 [B，H，S，D] 再做 rope，那样 token 维不再连续，合并访存退化。rope 是逐（token， head） 独立的运算，提前到 [B，S，H，D] 时调用在数学上完全等价， 而此时展平成 [T，H，D] 正是 kernel 要的连续布局。

**Q7：免表版为什么只快 2%？什么情况下会快很多？** 因为 cos/sin 表只有 8 MB，常驻 L2，查表根本没走到显存。如果上下文长到让表超出 L2（head_dim=128 时约需 $T > 3\times10^5$），或者 batch 很大使表被反复挤出， 免表的收益会显著上升。

**Q8："恰好慢 2 倍"意味着什么？** 大概率是 harness bug，不是性能现象。真实的性能差异很少落在整数倍上。本项目的 Triton rope 臂就出过这个：诊断路径是换粒度（无效）→ 加连续性断言（无效）→ dump PTX 看到 `ld.global.v4.b32` 证明向量化没问题 → 单独测该 kernel 得 907 GB/s → 回头查 harness，发现 `q.clone()` 被写进了被计时的闭包里， 每次迭代白搬 320 MB。**就地算子的 bench 尤其容易在这里翻车：正确性需要干净副本， 时延不需要，两者必须分开。**

**Q9：接进引擎后端到端只快 30%，是不是说明算子优化价值不大？** 相反，这是唯一有意义的数字。算子级的倍数是上限，端到端的百分比是兑现。把 5 倍说成端到端收益是不诚实的；把 30% 说成"优化没用"则忽略了这是在只改了三个逐元素算子、完全没动 GEMM 的前提下拿到的。

**Q10：为什么正确性用贪心 token 序列判，而不用 logits？** 两个都要，但地位不同。logits 的逐元素比较需要一个校准过的阈值，而 bf16 在 28 层累积后的本底偏差就有 $1.6\times10^{-2}$，阈值稍紧就必然失败，与被测对象好坏无关。贪心 token 序列是端到端唯一有操作意义的判据——它直接对应用户看到的输出。正确做法是拿 fp32 前向做真值，看两条 bf16 路径谁离真值更远。

**Q11：torch.compile 已经能打平，还有必要手写吗？** 在 HBM 区间没有必要。在 L2 区间（快 3.2–10.6 倍）和 decode 区间（快 2.5–11 倍） 有必要，而推理引擎恰好常驻这两个区间。另外 torch.compile 需要图捕获， 动态形状会触发重编译，在服务化场景有额外约束。

**Q12：如果要再往上走一步，下一步做什么？** 不是继续优化这三个 kernel（已经 92% 峰值）。是把它们与相邻的 GEMM 融合——例如 `silu_and_mul` 与 down_proj 的 GEMM 融合成 epilogue，或者把 gate/up 两次投影合并成一次 GEMM（打包布局的真正价值所在）。收益不在被改的算子里， 在它上下游。

## 8 工业对照与延伸

### 8.1 文档/上游怎么说 vs 本项目实测

**vLLM 的 `fused_add_rms_norm`。** 上游实现同样把残差加与归一化融进一个 kernel， 并且同样采用"先把归一化结果舍到 bf16、再乘 bf16 权重"的顺序。本项目复刻了这个舍入顺序，理由不是它更准（它更不准），而是要与生产实现逐位可比。上游的 decoder layer 把残差以 `residual` 变量跨层携带、让残差加总是跟着下一个 norm 走， 本项目的引擎接入照搬了这个结构，并因此发现：循环中途的 hidden 不再是该层真实 hidden，与逐层对拍的调试路径语义冲突，必须互斥。

**vLLM 的 `silu_and_mul` 用打包布局。** 上游把 gate 与 up 放在同一张量的前后两半。本项目实测该布局在算子层只有 +1.0%——**打包的价值不在这个算子里**，在于它让 gate_proj 与 up_proj 可以合并成一次 GEMM（少一次 launch、GEMM 的 N 维翻倍、权重只读一次）。这是一个"收益不在被改的地方"的典型例子，只看算子级 benchmark 会得出"打包没用"的错误结论。

**vLLM 的 rotary embedding 命名。** 上游用 `is_neox` 区分两种布局：`true` 对应 "前后半段"（HF 的 llama/Qwen 用这种），`false` 对应 GPT-J 式的"奇偶交错"。名字容易反着记，而两种布局互换**不报错、不 NaN，只让输出变成乱码**。本项目的引擎在这一处有专门的对拍。

**CUDA 编程指南关于合并访存。** 官方表述是全局访存以 32 字节 sector 为单位、 warp 请求会被合并成尽可能少的事务。本项目在三个算子上把它具体化成一句可操作的话：标量 bf16 时一个 warp 只覆盖 64 字节 = 半个事务，改成 16 B/lane 后覆盖 4 个满事务。但要注意——**这条规则只在还没贴带宽墙时有效**；fused-norm 的 v2→v3 就是一个"规则正确、收益为零"的反例。

**Triton 的 mask 语义。** 文档保证 mask 的语义正确性（被屏蔽的 lane 不写、读到 `other`），但**不保证被屏蔽的那一路不产生实际访存事务**。本项目在 rope 上实测到：把 q/k 合进一个 kernel 用 mask 选择时，有效带宽恰好减半——两路 masked load 都发出了实际访存。最终改成单张量 kernel、q/k 分两次 launch。

### 8.2 延伸方向

- **算子与 GEMM 的融合**：把 `silu_and_mul` 做进 down_proj 的 epilogue； 把 gate/up 投影合并成一次 GEMM。这是打包布局真正的落地形态。
- **残差流 fp32 累积**：消除融合引入的精度代价，代价是 residual 的字节数翻倍。值不值得，取决于模型深度与下游任务对末位的敏感度。
- **CUDA Graph**：decode 时这三个算子都是 launch 主导，kernel 本身已无优化空间， 正解是把整段 decode 折叠成一张图。
- **计数器实测（已完成）**：本篇 §3.3 的"第二次读被缓存接住"原为带宽上界反推的推断，现已由 RTX 4090 计数器直接证实——DRAM 读扇区恒为 2.000 倍算法下界、L1 命中率 83.2%、L2 读命中率 0.94%，接住它的是 L1 而非 L2。见 EXP-K07《NCU 计数器闭环》。该批报告采自向量化修复之前的版本；修复后已重采，前后对照见 EXP-K09《向量化修复后的扇区账复采》§5.1。

### 8.3 一句话带走

> 访存主导的算子，优化的全部内容是**减少每元素搬运的字节数**； 字节账要在 **HBM 层面**记，不是指令层面； 一旦贴上带宽墙，**语言不再重要**——手写 CUDA、Triton、torch.compile 收敛到同一个数； 真正的分水岭是**融不融合**，以及**你的形状落在哪个区间**。
