## 1 这一篇回答什么问题

起点是一个被问住的面试问题：

> "你的 int8 量化算子性能怎么样？有没有放到引擎里？"

这个问题看似在问性能，实际在问三件事：

1. 你知不知道**只做量化那一步是负收益**？
2. 你知不知道收益到底来自哪一步？
3. 你有没有真的接进去过？

第一问是刀口。把量化算子插进推理路径、后面仍走 bf16 GEMM，等于量化完立刻反量化， 只多了两次显存往返—— 端到端必然更慢。所以"量化算子跑得多快"这个问题本身就问错了对象：实测它只占整条 W8A8 链路的 **1.7%**。

本篇回答的是 kernel 侧的三层问题：

- 完整链路由哪几步组成，各占多少？
- 为什么 decode 必须自己写 GEMV，而不能调库？
- 一个同时改变算力、带宽、存储层级的优化，**怎么才能量对**？

第三问是本篇真正的重心。W8A8 有一个别的优化没有的陷阱： **它把权重砍了一半，恰好可能让权重从 HBM 挪进 L2，而对照臂还在 HBM——对比的前提被优化本身破坏了。**

## 2 直觉与第一性原理

### 2.1 W8A8 到底赚在哪

完整链路是三步：

```
① 量化   x[T,H] bf16  ->  xq int8 + x_scale[T] fp32     (per-token 动态)
② GEMM   acc[T,O] int32 = xq @ wq^T                     (INT8 Tensor Core)
③ 反量化 y[t,o] = acc[t,o] * x_scale[t] * w_scale[o]     -> bf16
```

① 和 ③ 都是纯开销—— 它们不产生任何有用的算术，只是把数据搬进搬出 int8 的表示。 **全部收益在 ②**，而且 ② 的收益在 prefill 与 decode 是两件不同的事：

| 阶段 | 形态 | 瓶颈 | int8 赢在哪 |
|---|---|---|---|
| prefill | GEMM（M 是几百到几千） | 算力 | INT8 Tensor Core 的吞吐 |
| decode | GEMV(M=1) | 权重带宽 | 权重字节减半 |

把两者混为一谈，就会以为"量化能普遍提速 2 倍"。实际上它们的上限来源完全不同， 而且**在同一个模型上可以一个赢一个输**（见姊妹篇的引擎实测）。

### 2.2 per-token 与 per-channel:粒度不是越细越好

激活按 token 一行一个 scale，权重按输出通道一列一个 scale。为什么是这两个方向？

因为 INT8 GEMM 的累加是纯整数点积，scale 必须能从整数结果里**整体提出来**：

$$y_{ij} = s_x[i] \cdot s_w[j] \cdot \sum_k qx_{ik} \cdot qw_{jk}$$

scale 只能呈**行 × 列的外积形状**。激活若沿 $k$ 维（输入通道）做 per-channel， 就提不出来了—— 它会卡在求和号里面。

这一条约束的后果很重要：**LLM 激活的 outlier 恰好是沿输入通道分布的**， 而那正是唯一不能用更细粒度去救的方向。所以 outlier 只能靠"迁移"消解（SmoothQuant），不能靠"更细粒度"硬扛。这就是 SmoothQuant 存在的理由。

### 2.3 对称量化:为什么不要 zero-point

$q = \mathrm{round}(x / s)$，$s = \max|x| / 127$，零点固定为 0。

不做非对称（带 zero-point）的理由同样是"scale 要能提出来"：带 zp 的话 $y$ 里会多出一项 $\sum_k qw_{jk} \cdot zp_x$，需要额外一次沿 $k$ 的权重求和与一次广播加法。对称量化让反量化退化成两个标量相乘，可以完全塞进 epilogue。

代价是码域少用一个格子（用 $[-127,127]$ 而非 $[-128,127]$）。这 0.4% 的动态范围， 换的是整条链路的结构简单—— 划算。

## 3 完整推导与机制

### 3.1 量化这一步:结构与 RMSNorm 同型

per-token 量化要先求出整行的 $\max|x|$，再逐元素缩放—— 这是一次行归约加一次逐元素变换，与 RMSNorm 完全同型（`w8a8/src/quant_per_token.cu:68-76`）：

```cuda
    float m = 0.f;
    for (int i = threadIdx.x; i < H; i += blockDim.x)
        m = fmaxf(m, fabsf(__bfloat162float(row[i])));
    const float s = fmaxf(block_reduce_max(m, smem), 1e-12f) / 127.0f;
    if (threadIdx.x == 0) scale[blockIdx.x] = s;

    const float inv = 1.0f / s;
    for (int i = threadIdx.x; i < H; i += blockDim.x)
        q[off + i] = quant_one(__bfloat162float(row[i]), inv);
```

几处不显眼但错了就出事的地方：

- `fmaxf(..., 1e-12f)`：整行全零时 absmax 为 0，scale 变成 0，后面除法出 inf/nan。兜底成极小正数后量化结果仍是全 0，语义正确。
- `const float inv = 1.0f / s`：取一次倒数，循环内用乘法。除法在 GPU 上是多指令序列，逐元素做会很贵。
- 归约用 `block_reduce_max` 而非求和版—— 结构相同，只换算子；补边界时补 0 而不是 $-\infty$，因为归约的是绝对值，恒非负。若换成一般的 max 归约（可能有负数），这里必须补 $-\infty$。

**舍入方式是量化实现里最隐蔽的一个坑**(`w8a8/include/w8a8.h:87-92`)：

```cuda
__device__ __forceinline__ int8_t quant_one(float x, float inv_scale) {
    float q = rintf(x * inv_scale);
    // 饱和到 [-127, 127] 而非 [-128, 127]:留出对称区间,避免 -128 无对应正值
    // 造成的轻微不对称(与 vLLM / SmoothQuant 的常规做法一致)。
    q = fminf(fmaxf(q, -127.0f), 127.0f);
    return (int8_t)q;
```

`rintf` 是"四舍六入五成双"(banker's rounding)，与 PyTorch 的 `round` 一致。若用 `truncf`（向零截断），量化误差就不再是零均值，而是带一个系统性的向零偏置——单层看不出来，逐层累积后表现为 logits 整体偏移。**这类 bug 不会崩、不会 NaN， 只会让模型悄悄变笨**，而且从任何单点数值上都看不出问题。

### 3.2 布局:一次 `.contiguous()` 值 3.0 倍

这是本项目最反直觉、也最实用的发现。

INT8 Tensor Core(IMMA)要求 B 矩阵是**列主序**（所谓 NT 布局）。实测同一份 int8 权重，只因为 stride 不同：

| 权重布局 | INT8 GEMM 单步 | 完整链路 |
|---|---|---|
| 列主序（`wq.t()` 的自然形态） | 0.48081 ms(2.74x bf16) | **2.167x** |
| 行主序（被 `.contiguous()` 整理过） | 1.74606 ms(**0.756x** bf16) | **0.726x** |

3.6 倍的差距不涉及任何计算改动，全部来自 stride。而且行主序那一档**比 bf16 还慢**——量化非但没赚，还亏了 27%。

好消息是正确布局本来是免费的：`F.linear(x, w)` 算的是 $x W^\top$，`w` 是 `[O,H]` 行主序，那么 `w.t()` 就是 `[H,O]` 列主序—— 天生就对。 **你唯一要做的是别去"整理"它。**

`.contiguous()` 在别处通常无害（顶多多一次拷贝），在这里是 3.0 倍的性能损失。这条经验可以推广：**当一个库对输入布局有硬性偏好时，"顺手规整一下"是危险动作。**

### 3.3 decode 为什么必须自己写:M>16 是硬约束

`torch._int_mm` 在 $M=1$ 时直接报错：

```
RuntimeError: self.size(0) needs to be greater than 16, but got 1
```

这不是"慢一点"，是"跑不了"。而 decode 恰恰恒定是 $M=1$（batch=1 时一次一个 token）。

于是必须自己写 int8 GEMV。它是纯访存算子：每个输出通道要把整行权重读一遍， $O \times H$ 字节；bf16 版要读 $2OH$。**上限就是 2 倍，与 int8 的算力毫无关系。**

实现用 `__dp4a`（一条指令做 4 个 int8 乘加并累进 int32），一个 warp 负责一个输出通道（`w8a8/src/int8_gemv.cu:49-62`）：

```cuda
    int acc = 0;
    for (int i = lane; i < HV; i += 32) {
        int4 wv = w4[i];
        int4 xv = x4[i];        // 激活只有 H 字节,被同 block 的所有 warp 复用,
                                // 几乎必然命中 L1;v1 会把它显式搬进 smem
        // 每个 int 装 4 个 int8:一条 dp4a 完成 4 次乘加并累进 int32
        acc = __dp4a(wv.x, xv.x, acc);
        acc = __dp4a(wv.y, xv.y, acc);
        acc = __dp4a(wv.z, xv.z, acc);
        acc = __dp4a(wv.w, xv.w, acc);
    }
    acc = warp_reduce_sum_i32(acc);
    if (lane == 0)
        y[o] = __float2bfloat16((float)acc * xs[0] * ws[o]);
```

用 `__dp4a` 主要不是为了算力（GEMV 根本用不满算力），是为了让每条访存指令对应更多有效计算，避免发射瓶颈。每条 lane 一次读 16 字节（`int4`）= 16 个 int8， 正好 4 次 `__dp4a`。

**`xs[0]` 而不是一个主机传进来的标量**，这一处不是风格问题：量化 kernel 刚把 scale 算在显存里，若在主机侧 `.item()` 取回再当参数传，每次调用都要插一次设备到主机的隐式同步——decode 时每层每个线性层各同步一次（8B 模型上是 36 层 × 7 个线性层 = 252 次/token），整条流水被切碎。代价记在 `w8a8/src/int8_gemv.cu` 中 `int8_gemv_v0` 上方的注释里：让 decode 从应赢约 2x 变成净亏 19%——**这是实现期的终端级证据**，bench 里没有主机标量对照臂，所以它不进本篇任何一张表，也不作可外推的结论。

### 3.4 反量化:一个本不该单独存在的 kernel

cuBLASLt 的 INT8 matmul 输出 int32 累加值，scale 只有调用方知道，所以必须有一步把它变回 bf16。实测这一步占整条链路 **26.7%**。

它本可以完全消失—— 如果由 GEMM kernel 在结果还留在寄存器/共享内存里时就地完成， 这一遍 int32 读 + bf16 写就不存在。用 cuBLASLt 的现成接口拿不到那个位置。

**这就是"为什么生产框架要自己写 GEMM"的定量答案：26.7%。** vLLM 的 W8A8 基于 CUTLASS 自写 GEMM，省的主要就是这一遍。

还有一个精度上限值得知道：`acc` 是 int32，最大可到 $127 \times 127 \times H$， $H=4096$ 时约 $6.6 \times 10^7$；而单精度尾数只有 24 位，只能精确表示到 $1.6\times10^7$。所以 `(float)acc` 本身就带舍入误差。这是 int8 GEMM 的固有精度上限，不是 kernel 的问题；要更准需要 fp64 或分段累加，代价远大于收益。

## 4 代码逐段走读(按执行顺序)

一次 prefill 的 W8A8 linear，按时间顺序发生这些事：

### 4.1 量化(1.7%)

见 §3.1。一个 block 一行，行归约 + 逐元素缩放。向量化版每线程读 16 字节 bf16、写 8 字节 int8—— **读写宽度不对称是量化算子的固有形态**：输出本来就窄一半。

### 4.2 INT8 GEMM(79.0%)

`torch._int_mm(xq, wq.t())`。这一步不自己写是**有意的**：本项目要回答的是 "整条链路能不能兑现收益"，不是"我能不能写过 cuBLASLt"。用现成库做最重的那一步， 量化与反量化两步的真实代价才能被单独量出来—— 1.7% 与 26.7% 这两个数字本身就是结论。

唯一要做对的是别碰 `wq.t()` 的布局（§3.2）。

### 4.3 反量化(26.7%)

一行一 block，`x_scale` 每行只读一次而不是每元素读一次：

```
o.h[0] = __float22bfloat162_rn(make_float2((float)a.v[0] * sx * w.x, ...));
```

`sx` 提到循环外后，行内所有元素共用一个寄存器。v0 里 `xs[t]` 虽然会命中 L1， 但仍占一条 LSU 指令—— 在纯访存 kernel 上，省一条指令就是省一条。

### 4.4 decode 分支

不走上面三步的中间那步，而是 §3.3 的 GEMV。量化仍要做，反量化被折进 GEMV 的尾巴（`(float)acc * xs[0] * ws[o]`，就在寄存器里完成）—— **decode 路径上反量化是免费的**， 因为 GEMV 是自己写的，能拿到那个位置。这从反面印证了 §3.4:26.7% 的代价纯粹来自 "用了别人的 GEMM"。

## 5 实验数据怎么读

### 5.1 prefill:2.1 倍,但要看清是跟谁比

| 形状（H=4096） | bf16 cuBLAS | W8A8 | 加速 |
|---|---|---|---|
| T=512, O=4096 | 0.10953±0.00008 ms | 0.05716±0.00012 ms | 1.916x |
| T=512, O=12288 | 0.34189±0.00086 ms | 0.17534±0.00107 ms | 1.950x |
| T=2048, O=12288 | 1.31949±0.00200 ms | 0.60875±0.00013 ms | **2.167x** |
| T=8192, O=12288 | 5.20636±0.01344 ms | 2.46936±0.00166 ms | 2.109x |

对照物是真实的 `F.linear`（走 cuBLAS），不是自写的 bf16 GEMM。

### 5.2 decode:三个答案,只有一个能用

同一对 kernel，三个输出宽度给出三个截然不同的加速比：

| 形状 | int8 权重 | bf16 权重 | 加速 | 存储层级 |
|---|---|---|---|---|
| O=4096 | 17 MB | 34 MB | 4.43x | 两边都在 L2 |
| O=12288 | 50 MB | 101 MB | **8.69x** | **int8 在 L2、bf16 在 HBM** |
| O=32768 | 134 MB | 268 MB | **1.972x** | 两边都在 HBM |

4090 的 L2 是 72 MB。中间那一档，**int8 权重恰好塞得进 L2 而 bf16 塞不进**——两条臂根本不在同一个存储层级上比，8.69x 是一个无效数字。

只有 O=32768 那一档可外推：两条臂的等效权重带宽分别是 951.8 与 938.5 GB/s， 双双贴到 94.4% / 93.1% 峰值—— **都在带宽墙上，2 倍完全来自权重字节减半，与理论预测精确吻合**。

这个陷阱是量化特有的。别的优化（向量化、融合、流水）不改变数据总量， 所以对照臂和被测臂始终在同一层级；**量化把数据砍了一半，砍的动作本身可能跨过 L2 的边界**。判定量化的加速比之前，必须先分别算两边的工作集落在哪。

这是 EXP-K04《标准库基准补齐与两区间重测》"测量效度先算账"的重演，而且更隐蔽： 上次是"忘了测 HBM 区间"，这次是"优化本身把被测对象搬走了"。

### 5.3 三步分解:告诉你下一步该优化哪儿

T=2048/O=12288：量化 0.01024 ms(1.7%)、GEMM 0.48081 ms(79.0%)、反量化 0.16272 ms(26.7%)。

三个数字各有各的用途：

- **1.7%** 是对"量化算子性能怎么样"的直接回答：单独优化它没有意义。
- **79.0%** 说明主战场在 GEMM，而 GEMM 已经是库了—— 想再快只能自己写。
- **26.7%** 是自己写 GEMM 的**具体动机**：融进 epilogue 就能省掉。

**分解计时之和对不上总时间，是存在多余搬运的信号。** 本项目实现过程中据此查出一句多余的 `acc.copy_(torch._int_mm(...))`—— 白搬一遍 $T \times O$ 的 int32， $T=2048/O=12288$ 时是 100 MB 读 + 100 MB 写，占整条链路近四分之一。

## 6 误区与边界

**误区一："量化就是把量化算子写快。"** 它占 1.7%。

**误区二："int8 GEMV 快 8.7 倍。"** 那是跨存储层级的无效对比。只准说 1.97 倍。

**误区三："量化普遍提速 2 倍。"** prefill 与 decode 的收益来源不同（算力 vs 带宽）， 在同一个模型上可以一个赢一个输。

**误区四："用库就够了。"** decode 的 $M=1$ 库直接跑不了；反量化融不进 epilogue 还要多付 26.7%。这两条合起来就是生产框架自写 CUTLASS GEMM 的全部理由。

**边界一：形状约束。** 向量化要求 $H \bmod 8 = 0$；GEMV 要求 $H \bmod 16 = 0$。不满足必须在入口拒绝。

**边界二：int32 累加的精度上限。** $(float)acc$ 在 $H$ 大时本身就有舍入误差。

**边界三：算子级误差不能外推到模型级。** 本项目的量化误差 1.06e-2 至 1.39e-2 在 int8 的合理界内，但逐层累积后的表现完全是另一回事—— 见姊妹篇：不做 SmoothQuant 时 Qwen3-8B 的贪心输出直接发散。

## 7 连环追问

**Q1：为什么激活用 per-token 动态、权重用 per-channel 静态？** 权重是静态的，scale 一次算好存下来，不进热路径；激活每次前向都不同，只能在线算。方向上都受"scale 必须呈行×列外积"这一条约束（§2.2）。

**Q2：能不能给激活也做 per-channel（沿输入通道）？** 不能。那个方向的 scale 卡在求和号里面，提不出来。而 LLM 的 outlier 恰好就在这个方向—— 这正是 SmoothQuant 必须存在的原因：outlier 只能迁移，不能靠细粒度硬扛。

**Q3：为什么不用非对称量化多榨一点动态范围？** 带 zero-point 会多出一项 $\sum_k qw \cdot zp$，需要额外的权重求和与广播加法。省下的 0.4% 码域换不回这个结构复杂度。

**Q4：`rintf` 和 `truncf` 差在哪？** `truncf` 让量化误差带向零的系统性偏置，均值不为 0，逐层累积成 logits 整体偏移。不崩不 NaN，只是模型悄悄变笨。

**Q5：布局那 3.6 倍到底是什么造成的？** IMMA 要求 B 列主序。行主序时库要么走转置路径、要么落到非 Tensor Core 的慢路径。关键是：正确布局本来免费（`w.t()` 天生列主序），是"顺手 `.contiguous()`"把它毁了。

**Q6:8.69x 那个数错在哪？能不能通过多测几轮修正？** 不能。它不是噪声，是系统性的口径错误：两条臂的数据分别在 L2 与 HBM。再测一百轮还是 8.69x，而且每轮都很稳—— **稳定的错误比不稳定的错误更危险**。唯一的修法是换形状，让两边落在同一层级。

**Q7：为什么 GEMV 的 smem 版没有收益？** 激活只有 $H$ 字节（4096 时 4 KB），本就常驻 L1。显式搬进 shared memory 没有省下任何东西。这一级是负结果，保留在版本梯里作为"缓存已经做掉的事不必手工再做一遍" 的样本。

**Q8：反量化融进 epilogue 能省 26.7%，为什么不做？** 要做就得自己写 INT8 GEMM（CUTLASS 级）。本项目有意不写，是为了把 ①③ 两步的代价单独量出来。26.7% 这个数字本身就是"值不值得自己写 GEMM"的决策依据——先量清代价，再决定要不要付出实现成本。

**Q9：decode 的 GEMV 上限为什么是 2 倍而不是更多？** 因为它是纯访存的：权重字节从 $2OH$ 降到 $OH$，一半就是一半。int8 的算力优势在 GEMV 上完全用不上—— $M=1$ 时算力空转，时间全花在等权重。

**Q10：接进引擎后会怎样？** 见姊妹篇。简短版：显存 −36.9% 是无条件的真收益；prefill 赢 14.8%； decode 反而亏—— 因为 kernel 只占四成，六成花在把 kernel 送上去。

## 8 工业对照与延伸

### 8.1 文档/上游怎么说 vs 本项目实测

**关于 IMMA 的布局要求。** cuBLAS 文档说明 INT8 的 `cublasLtMatmul` 对布局有偏好， 不满足时会走较慢的路径。本项目把"较慢"量化成了具体数字：**2.74x 变 0.756x， 即从超过 bf16 变成不如 bf16**。这不是"稍慢"，是方向反转。

**关于 `torch._int_mm` 的最小 M。** PyTorch 的实现对 `M<=16` 直接抛异常。本项目把它记录为**硬约束而非性能问题**—— 它决定了 decode 路径必须自己写。该下界的确切来源（cuBLASLt heuristic 还是 torch 侧硬编码）未查，只按现象记录。

**关于 vLLM 的 W8A8。** 上游基于 CUTLASS 自写 GEMM 而不调 cuBLASLt， 本项目给出了这个选择的两条定量理由：① decode 的 $M=1$ 库跑不了； ② 反量化融不进 epilogue 要多付 26.7%。

**关于 SmoothQuant 论文的粒度论证。** 论文指出激活 outlier 沿通道分布、而 GEMM 的 scale 必须可分解为行列外积，因此 per-channel 激活量化不可行。本项目在实现层复现了这条约束（§2.2），并在姊妹篇给出了不迁移时的后果： Qwen3-8B 贪心输出直接发散。

### 8.2 延伸方向

- **自写 INT8 GEMM（CUTLASS 级）**：把反量化融进 epilogue，吃掉那 26.7%。
- **W4A16 / W8A8 的选择**：decode 是权重带宽主导，权重位宽才是杠杆； 4 bit 权重的上限是 4 倍而不是 2 倍。
- **KV cache 量化**：本项目只动了线性层。长上下文下 KV cache 才是显存大头。

### 8.3 一句话带走

> 量化不是一个算子，是一条链路：**量化 1.7% / GEMM 79.0% / 反量化 26.7%**； 收益全在 GEMM，而 GEMM 在 prefill 赢算力、在 decode 赢带宽，两者不是一回事； **布局值 3.6 倍，一次 `.contiguous()` 就能让量化从赚变亏**； 最后—— 量化会把被测对象搬到另一个存储层级，**判加速比之前先算两边的工作集**。
