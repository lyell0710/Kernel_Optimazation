# W8A8 项目介绍

## 为什么会有这个项目

这个子项目的起点是一个被问住的面试问题：

> "你的 int8 量化算子性能怎么样？有没有放到引擎里？"

当时的状态是：本仓已经有一个 int8 量化算子（`int8-quantize/`），单测很快； 自研推理引擎也在跑。但两者从未接上。

问题的杀伤力不在"没接"，在于**如果按当时的理解去接，一定是负收益**——把量化算子插进推理路径、后面仍走 bf16 GEMM，等于量化完立刻反量化， 只多了两次显存往返。真正能带来收益的是 GEMM 那一步：INT8 Tensor Core 的算力， 以及权重字节减半带来的带宽。

所以这个子项目做的不是"再优化一遍量化算子"，而是补齐**整条 W8A8 linear 链路**， 并且必须给出三件证据：性能、显存、精度。少任何一件，结论都不成立。

## 三件必须同时给的证据

| 证据 | 为什么不能少 |
|---|---|
| 性能 | 量化的直接目的 |
| 显存 | 权重减半是无条件的真收益，而且往往比速度更值钱（换 KV cache 余量） |
| 精度 | 量化是有损的。不给精度证据的加速比，等于没有结论 |

## 版本化方法论

本项目**有意不自己写 INT8 GEMM**，直接用 `torch._int_mm`（底层 cuBLASLt IMMA）。理由是要回答的问题是"整条链路能不能兑现收益"，不是"我能不能写过 cuBLASLt"。用现成库做最重的那一步，量化与反量化两步的真实代价才能被单独量出来——实测结果是 1.7% 与 26.7%（T=2048/O=12288，EXP-K06《W8A8 linear 完整链路》，`project-proof/data/derived_w8a8_vec-after_stability.csv`），这两个数字本身就是结论。

手写的是三样库给不了的东西：

| 组件 | 为什么必须自己写 |
|---|---|
| per-token 动态量化 | 语义特定，库里没有 |
| 反量化 epilogue | cuBLASLt 输出 int32，scale 只有调用方知道 |
| int8 GEMV | **`torch._int_mm` 硬性要求 M>16，decode 的 M=1 直接不可用** |

最后一条是整个项目最有价值的发现之一：它不是"库慢一点"，是"库跑不了"。这解释了为什么 vLLM 这类框架的 W8A8 必须基于 CUTLASS 自己写 GEMM/GEMV。

## 两个把结论推翻过的坑

**一次 `.contiguous()` 值 3.0 倍。** INT8 Tensor Core 要求 B 矩阵列主序； `w.t()` 天然就是列主序，是免费的正确布局。中间"顺手整理"一下， 整条链路从快 2.17 倍变成慢 1.38 倍。

**量化把被测对象搬到了另一个存储层级。** O=12288 时 int8 权重 50 MB 落进 L2、 bf16 权重 101 MB 还在 HBM，量出来 8.69 倍—— 一个无效数字。这个陷阱是量化特有的：砍半的动作恰好可能跨过 L2 的边界， 对比的前提被量化本身破坏了。必须补一档两边都超 L2 的形状才拿到真数（1.97 倍）。

## 与其他项目的关系

- 量化算法（SmoothQuant / GPTQ / AWQ 的从零实现与 α 扫描）在 [LLM_Quantization](https://github.com/lyell0710/LLM_Quantization)； 本项目做的是它的**部署形态**。
- 接进自研推理引擎的端到端结果（Qwen3-8B：线性层权重 13.9 GB → 8.8 GB、 prefill TTFT −14.8%、贪心输出逐 token 一致）见 llm-engine 的 llm-engine#EXP-D24。
- 量化这一步的版本梯与 [int8-quantize](../int8-quantize/) 同源， 但结论相反：那边它是主角，这里它只占 1.7%。
