# EXP-K09 · 向量化修复后的扇区账复采：守卫验证与「浪费比」判据

> **一句话结论**：向量化兑现后 L1TEX 请求精确降为原来的 **1/4**（16→4、12→3 ×S，正好等于 16 B/4 B），
> 而 DRAM 读**纹丝不动停在 2.000×S 的算法下界**——守卫通过；
> 对比修复前 v3/v4 的 16/12×S 与标量版 v1/v2 的 4×S，可知那个"向量化优化"在兑现之前是**负优化**，
> 只是被 L1 全部吸收才在 DRAM 侧看不出来；并由 `L1TEX/DRAM` 浪费比给出「向量化有没有收益」的必要条件。

## 1 目的与假设

EXP-K08 在主力机上把 `BF16x8` 的 16 B 向量化真正兑现（SASS 五处 `LDG.E.128` 由 0 转正），
但主力机没有计数器权限，无法验证访存账本的变化。本轮回到采集主机重采四个 torch 算子。

- **H1（守卫）**：向量化只改变**指令层**的访存方式，不改变**算法需要搬多少字节**。
  故 L1TEX 请求应大幅下降，而 DRAM 读**必须仍为 2.000×S**。偏离即说明修复引入了新问题。
- **H2（收敛幅度）**：一条 128 位 load 取代四条 32 位，L1TEX 请求应降为 1/4。
- **H3（收益分化的机理）**：EXP-K08 观察到"SASS 四个算子全兑现，性能只有两个翻正"。
  假设该分化可由访存账本解释，而非偶然。

## 6 分析与结论

### 6.1 H1、H2 成立，且吻合到理论值

L1TEX 请求降幅**精确等于 4.00×**（16→4、12→3），正是 16 B / 4 B ——
一条 `LDG.E.128` 取代四条 `ld.global.v2.u16` 的理论值。

DRAM 读在四个版本上都停在 **2.000×S**（residual + x 各读一遍的算法下界），
与修复前完全一致。**向量化改变的是指令怎么发，不是算法要搬多少字节**，这条在计数器上得到干净印证。

L1 命中率的下降完全可由 `1 − DRAM/L1TEX` 解释：

| 版本 | 实测 L1 命中 | `1 − DRAM/L1TEX` |
|---|---|---|
| v4 修复后 | 33.19% | 1 − 2/3 = 33.33% |
| v3 修复后 | 49.34% | 1 − 2/4 = 50.00% |
| v4 修复前 | 83.19% | 1 − 2/12 = 83.33% |

**命中率下降不是变差**：分母（总请求）缩小了 4 倍，而被过滤掉的绝对量本就该同步减少。
把命中率当成"越高越好"的指标在这里会得出完全相反的结论。

### 6.2 计划外发现：修复前的"向量化"是负优化

把标量版本放进来对比，账就变得刺眼：

| | L1TEX/S |
|---|---|
| v1 / v2（标量，无 `BF16x8`） | 4.000 |
| v3 / v4（修复前，假向量化） | **16.000 / 12.000** |
| v3 / v4（修复后，真向量化） | 4.000 / 3.000 |

**修复前 v3/v4 的访存事务比标量版本还多 3–4 倍。** 那个 `alignas(16)` 的"优化"不只是没兑现，
它让每条 4 B load 按 16 B stride 散着取——一条指令 touch 16 个 sector 却只用掉 4 个，
sector 利用率 25%。修复后 v4 = 3.000×S 才**首次低于**标量的 4.000×S。

这也解释了 EXP-K08 记录的那个反转（v4 原本慢于 v3、修复后反超）：
v4 的设计意图是"用寄存器省掉一次重读"，省下的 1×S 在假向量化的 4× 放大下被完全淹没——
**那个优化此前一直是净亏的**，直到向量化兑现才显出正收益。

### 6.3 H3 成立：浪费比是收益的**必要非充分**条件

`activation` 是最干净的一例：向量化后 **L1TEX = L2 = DRAM = 12.58 M**，比值 **1.00×**，
每个 sector 恰好被 touch 一次——**完美合并，sector 层面零改善空间**。
它的向量化只减少了指令条数，一个访存事务都没省下。EXP-K08 观察到的"兑现了但没收益"，
机理就在这里，不是偶然。

**但反例同样重要**：`w8a8 quant_v2` 的浪费比是 2.00×（有改善空间）却仍然 ≈ 0 收益。
EXP-K08 已给出原因——量化只占端到端链路的 1.8%，属 Amdahl 上限，与访存账本无关。

故正确表述是：

- **浪费比 ≈ 1.0 → 必然无收益**（没有可回收的事务）
- **浪费比 > 1 → 不保证有收益**（还要看该 kernel 在链路中的占比）

这比"SASS 判据"前进了一步：`LDG.E.128 > 0` 只说明**兑现**，浪费比说明**有没有可回收的量**，
而端到端占比决定**回收了值不值**。三者缺一不可——EXP-K08 §6"兑现≠收益"由此获得可计算的判据。

## 7 异常、偏差与开放问题

### 7.1 修掉一个会丢数据的 bug：空报告拦截从未真正生效

`scripts/ncu_profile_lib.inc.sh` 的空报告拦截，注释写明"**不该中止整轮采集**——机器在计费，
不能因为一个臂没抓到就丢掉其余几十份"，`PROFILING_HOST_TASKS.md` §5 也声称"已拦截并删除，不中止整轮"。
**实际从未生效**。本轮 w8a8 因此只采到 2/8 就整轮退出。

三个缺陷叠加：

1. **形态判断错**：regex 无匹配时 ncu **根本不生成报告文件**（只在 stdout 打 `No kernels were profiled`），
   而原实现假设"文件存在但零实例"。
2. **判空恒不成立**：`ncu -i <不存在的文件>` 把错误打在 **stdout**（`2>/dev/null` 挡不住），
   于是 `| sed 1d | wc -l` 得到 **1** 而不是 0。
3. **pipefail 直接中止**：`set -euo pipefail` 下该管道返回非零，赋值语句即触发 `set -e`，
   连后面的判空分支都没走到。

修法：先判文件（`[ ! -s ... ]`）再判内容，并给管道加 `|| true` 兜底。
修复后 w8a8 的 v1 被正常跳过（`!! 空报告…已跳过`），其余 7 个臂全部采到。

**这个 bug 对所有算子生效**：任何一个 regex 抓不到的臂都会让整轮采集提前终止。
第一轮未暴露，是因为第一轮采的算子恰好每个 regex 都命中。

### 7.2 w8a8 `quant_v1` 采不到：`PROFILE_TARGETS` 引用了 bench 不跑的臂

`v1_kernel` 在源码里存在（`w8a8/src/quant_per_token.cu:58`）且被编译，
但 `bench.py` 只调用 `quant_v0` / `quant_v2` / `dequant_v0` / `dequant_v1` / `gemv_v0` / `gemv_v1`，
**从未调用 `quant_v1`**，故 ncu 的 Available Kernels 里没有它。

这不是 EXP-K08 引入的（`bc18547` 只改了 `quant_per_token.cu` 11 行，未动 bench.py），
而是既有的不一致；第一轮因 w8a8 未采集而没暴露。

**已决定：采 (a)，从 `PROFILE_TARGETS` 删除 `quant_v1`，不给 bench 补臂。**

理由是量级不对称：quant 在整条 W8A8 链路只占 **1.8%**（EXP-K06 §5.1 实测），
补一条 v1 臂改变不了任何结论，却要付「改 benchmark 口径 + 重跑 3 轮 + 核对既有 CSV」的代价。
为一个占 1.8% 的中间版本动 benchmark 口径不划算。

删除时在 `w8a8/project-proof/scripts/profile_ncu.sh` 的原位置写明了缘由，
让读脚本的人当场知道"为什么 targets 里没有 v1"，而不是再查一遍。

**一处仍待处理**：原计划同时在 `w8a8/src/quant_per_token.cu` 的 `v1_kernel`（第 58 行）
上方加注释，让源码自己解释"它为何在此却无人调用"。**本轮未做**，因为该文件被按行号引用三处：

在第 58 行上方插入注释会让这三处全部偏移，而 `verify_lectures.py` **不在采集主机上**，
无法自动重定位；且 `sass_evidence_ladder.md` 正在主力机侧修订中，同时改会撞车。

### 7.3 其余开放问题

1. rope / activation / w8a8 **没有修复前的 NCU 基线**（第一轮按指示跳过了这三个），
   故 §5.4 中它们只有修复后的浪费比，不能像 fused-norm 那样做前后差分。

   **已决定不补。** fused-norm 的完整前后差分已经把机制结论立住
