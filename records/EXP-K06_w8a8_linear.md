## 1 目的与假设

本仓早已有一个 int8 量化算子(`int8-quantize/`,EXP-K01),但它只是**量化这一步**。
一个反复出现的质疑是:量化算子跑得快有什么用?——**只把量化算子插进引擎、
后面仍走 bf16 GEMM,等于量化完立刻反量化,只多了两次显存往返,端到端必然更慢。**
W8A8 的收益全部来自 GEMM 那一步。本实验补齐完整链路并测它。

跑前锁定的可证伪预测:

| 编号 | 预测 | 依据 |
|---|---|---|
| H1 | 完整链路(量化+INT8 GEMM+反量化)相对 bf16 cuBLAS 有 1.5–2.5x | Ada 的 INT8 Tensor Core 吞吐约为 bf16 的 2x |
| H2 | 反量化 epilogue 占整条链路 15–30% | 它是纯访存的一遍读写,理应可观 |
| H3 | 量化步占比 <5% | 它只搬 3 B/元素,且被 GEMM 的 O(MNK) 摊薄 |
| H4 | decode(M=1)无法走库路径,需自写 GEMV | cuBLASLt 的 IMMA 有最小 M 限制 |
| H5 | 自写 int8 GEMV 在 HBM 受限尺寸下约 2x | 纯访存,权重字节减半;与 int8 算力无关 |

判定阈值:正确性 max_rel_err < 1e-1(int8 量化误差的合理界);性能结论 3 轮 mean±std。

## 2 环境与配置

- 手写 kernel:per-token 动态量化(v0 两 kernel / v1 融合 / v2 向量化)、
  反量化 epilogue(v0 / v1)、int8 GEMV(v0 / v1 smem)。
- **INT8 GEMM 直接用 `torch._int_mm`(底层 cuBLASLt IMMA),不自己写**——
  本实验要回答的是"整条链路能不能兑现收益",不是"我能不能写过 cuBLASLt"。
  用现成库做 GEMM,才能把量化/反量化两步的真实代价单独量出来。
- 形状取 Qwen3-8B 的线性层(H=4096,O=4096/12288),按 prefill 的 token 数分档;
  decode(T=1)单列。
- 三步分解各自单独计时,用于回答"下一步该优化哪儿"。

## 5 结果

### 5.1 prefill:完整链路 vs bf16 cuBLAS(3 轮 mean±std)

| 形状 | bf16 cuBLAS | W8A8 最优 | 加速 | W8A8(权重行主序) |
|---|---|---|---|---|
| T=512, O=4096 | 0.10931±0.00017 ms | 0.05738±0.00012 ms | **1.905x** | 0.14008 ms(**0.780x**) |
| T=512, O=12288 | 0.33909±0.00137 ms | 0.17301±0.00162 ms | **1.960x** | 0.44564 ms(0.761x) |
| T=2048, O=12288 | 1.31551±0.00958 ms | 0.60811±0.00103 ms | **2.161x** | 1.79197 ms(0.734x) |
| T=8192, O=12288 | 5.16058±0.01485 ms | 2.46020±0.00368 ms | **2.098x** | 7.31056 ms(0.706x) |

三步分解(T=2048/O=12288):量化 0.01066 ms(1.8%)、INT8 GEMM 0.47755 ms(78.5%)、
反量化 0.16265 ms(26.7%)。

### 5.2 decode(T=1):库路径不可用,自写 GEMV

`torch._int_mm` 在 M=1 时直接报错:`self.size(0) needs to be greater than 16`。

| 形状(权重体量) | bf16 cuBLAS GEMV | int8 GEMV | 加速 | 区间 |
|---|---|---|---|---|
| O=4096(int8 17 MB / bf16 34 MB) | 0.03834 ms | 0.00723 ms | 5.30x | 两边都在 L2 |
| O=12288(int8 50 MB / bf16 101 MB) | 0.10734 ms | 0.01218 ms | 8.82x | **int8 在 L2、bf16 在 HBM** |
| O=32768(int8 134 MB / bf16 268 MB) | 0.28203±0.00001 ms | 0.14300±0.00009 ms | **1.972x** | 两边都在 HBM |

HBM 区间两条臂的等效权重带宽分别是 946.9 与 935.2 GB/s(93% 峰值)。

## 6 分析与结论

**H1 成立(2.10–2.16x,略超预测上界)。**

**H2 成立,且这是"为什么生产框架要自己写 GEMM"的定量论据。** 反量化 epilogue
占整条链路 26.7%。它本可以完全消失——如果由 GEMM kernel 在结果还留在寄存器
/共享内存里时就地完成。用 cuBLASLt 的现成接口拿不到那个位置,所以必须多一遍
全量的 int32 读 + bf16 写。vLLM 这类框架基于 CUTLASS 自写 W8A8 GEMM,
省的主要就是这 26.7%。

**H3 成立(1.8%)。** 量化这一步便宜到几乎不用管——这恰恰说明
**单独优化量化算子对 W8A8 的端到端毫无意义**:它只占 2%。
这是对"int8 量化算子性能怎么样"这个问题最直接的回答:问错了对象。

**H4 成立,且是硬约束不是性能问题。** `torch._int_mm` 要求 M>16,decode 的 M=1
直接不可用。这不是"慢一点",是"跑不了"。它解释了为什么 vLLM 的 W8A8 必须
基于 CUTLASS 自己写 GEMM/GEMV 而不能调库。

**H5 成立(1.972x),但只有在正确的工作区间里成立 —— 这是本实验最重要的方法学结果。**

同一对 kernel,三个 O 值给出 5.30x / 8.82x / 1.972x 三个完全不同的答案:

- O=4096:int8 与 bf16 权重都塞得进 4090 的 72 MB L2 → 两边都在测 L2 带宽。
- **O=12288:int8 权重 50 MB 落在 L2,bf16 权重 101 MB 落在 HBM。
  两条臂根本不在同一个存储层级上比,8.82x 是一个无效数字。**
  这个陷阱是 int8 特有的:量化把权重砍半,恰好可能把它从 HBM 挪进 L2,
  而对照臂还在 HBM —— 对比的前提被量化本身破坏了。
- O=32768:两边都超 L2 → 1.972x,两条臂都贴到 93% 峰值。**只有这一档可外推。**

这是 EXP-K04「测量效度先算账」在量化算子上的重演,而且更隐蔽:那次是
"忘了测 HBM 区间",这次是"量化把被测对象搬到了另一个存储层级"。

**权重布局的影响比任何一级 kernel 优化都大。** 同一份 int8 权重,只是多做了一次
`.contiguous()`,整条链路从 2.16x 变成 0.734x:

| | INT8 GEMM 单步 | 完整链路 |
|---|---|---|
| 权重列主序(NT,`wq.t()` 的自然形态) | 0.47755 ms(2.75x bf16) | 2.161x |
| 权重行主序(被 `.contiguous()` 整理过) | 1.73726 ms(0.756x bf16) | 0.734x |

3.6 倍的差距全部来自 stride。INT8 Tensor Core 要求 B 矩阵是列主序(NT 布局);
而 `F.linear(x, w)` 算的是 `x @ w.T`,`w` 是 `[O,H]` 行主序,`w.t()` 天然就是
`[H,O]` 列主序 —— **这个正确布局是免费的,前提是别在中间"顺手整理"一下**。
`.contiguous()` 在别处通常无害,在这里是 2.9 倍的性能损失。

## 7 异常、偏差与开放问题

- int8 GEMV 的 smem 版(v1)相对 v0 没有收益(1.972x vs 1.970x,噪声内)。
  激活只有 H 字节(4096 时 4 KB),本就常驻 L1,显式搬进 smem 没有省下任何东西。
  这一级是负结果,保留在版本梯里作为"缓存已经做掉的事,不必再手工做一遍"的样本。
- 三步分解之和曾对不上总时间(差约 25%),查出是 bench 里写了一句多余的
  `acc.copy_(torch._int_mm(...))`,白搬一遍 T×O 的 int32。
  **分解计时之和对不上总时间,就是这类多余搬运的信号。**
- 未做 NCU 采集(容器无计数器权限)。"反量化本可融进 GEMM epilogue"是结构性
  推断,其代价(26.7%)是实测。
- `torch._int_mm` 的 M>16 下界未查其确切来源(cuBLASLt heuristic 还是 torch 侧
  的硬编码),只按现象记录。
- 量化误差 1.06e-2 至 1.39e-2,在 int8 的合理界内;但**算子级的误差不能外推到
  模型级** —— 逐层累积后的表现见 llm-engine#EXP-D24。

## 8 下游影响

- 已接入 llm-engine(EXP-D24):Qwen3-8B 上线性层权重 -36.9%、prefill TTFT -14.8%,
  配合 SmoothQuant 后贪心输出 64/64 逐 token 一致。
- 本仓算子数增至十个;PORTFOLIO 的"赢的形态"新增一条:**布局适配**
  (不改一行计算,只让数据以硬件想要的 stride 到达)。
- 对外表述红线:①"int8 GEMV 快 8.8x"是无效数字(存储层级不同),
  只准引用 HBM 区间的 **1.97x**;②"W8A8 快 2 倍"必须限定 prefill 形状,
  decode 与端到端另有结论;③量化算子单步只占链路 1.8%,不得单独作为卖点。
