# silu_and_mul 项目介绍

## 为什么会有这个项目

SwiGLU 的逐元素部分 `silu(gate) * up` 是 LLM 前向里**张量最大**的逐元素算子。 intermediate_size 通常是 hidden 的 2.5–4 倍（Qwen3-8B：4096 → 12288）， 所以它单次调用要搬的字节数比 RMSNorm 还多。

而 PyTorch 的写法 `F.silu(g) * u` 会物化一份与 gate 等大的中间张量： $T=8192$、$I=12288$ 时，那是 200 MB 写进显存、再 200 MB 读回来， 只为了传递一个立刻就要被消费掉的中间结果。

这个子项目就是把这份往返消掉，并借它验证一件事：**字节账能不能精确预测收益**。

## 版本化方法论

| 版本 | 只改的那一件事 | 想验证的假设 |
|---|---|---|
| v0 |（基线）两个 kernel，物化 `silu(gate)` | 与 PyTorch eager 同速，证明基线不是稻草人 |
| v1 | 融合成单 kernel | 字节账 5→3，加速应为 5/3 = 1.667 倍 |
| v2 | 16 B 向量化 | 事务利用率补满 |
| v3 | 打包布局（gate/up 在同一张量前后两半） | 算子层零收益（±3%） |

**v1 那条预测实测 1.675 倍，与 5/3 几乎精确吻合**——这是三个算子里字节账预测得最准的一条，也是"先算账再写代码"这套方法最好的背书。

**v0 与 eager 同速（540.9 vs 555.5 GB/s）是这条梯子的自检条件。** v0 被刻意写成 "手写但不优化"，逐条复刻 eager 的执行方式；如果两者差距很大，说明基线写错了， 后面的加速倍数就都是跟稻草人比出来的。

## v3 想说的话:收益不在被改的地方

打包布局是 vLLM 的做法。本项目实测它在算子层只有 +1.0%——因为打包与分离在 HBM 层面搬的字节数完全一样。

那 vLLM 为什么用它？因为打包意味着 gate_proj 与 up_proj 可以合并成一次 gate_up_proj GEMM：少一次 launch、GEMM 的 N 维翻倍从而 tile 利用率更高、权重只需读一次。**这些收益全部发生在 GEMM 那一侧，算子级 benchmark 看不到。**

只看算子级数字会得出"打包没用"的结论。这是一个关于**基准测量边界**的教训： 测量对象选错了，再精确的数字也回答不了问题。

## 工程结构

- `include/activation.h`— 共用声明，文件头写清两种布局的区别与各自的动机
- `src/silu_and_mul_v0.cu ~ v3.cu`— 四级版本梯
- `src/binding.cpp`— torch 绑定，分离与打包两种入口
- `bench.py`— 七条臂、四个工作区间

## 一个形状上的注意点

本算子每 token 的工作集是 $3I$，而不是 RMSNorm 的 $4H$。所以同样叫 "prefill" 的形状，在这里已经落在 HBM 区间了。**每个算子都要单独判定工作区间，不能套用别的算子的结论**——这是本仓 EXP-K04《标准库基准补齐与两区间重测》关于 L2 与 HBM 两区间的教训在本算子上的延续。
