# RoPE 项目介绍

## 为什么会有这个项目

RoPE 是 llama 系模型里最容易写错、又最不容易发现写错的一个算子。

它的两种主流布局——"前后半段"与"奇偶交错"——在张量形状上完全一样,互换**不会报错、
不会 NaN、不会崩**,只会让模型输出变成语法通顺但语义乱掉的文字。我在写自研引擎时
就在这里被卡过一次,最后靠逐层对拍才定位到。

所以这个子项目有两个目标,顺序不能反:**先把它写对,再把它写快**。

## 这个算子是什么

把 head_dim 的前后两半 $(x_1, x_2)$ 看成 $D/2$ 个复数的实部与虚部,整体乘 $e^{i\theta}$:

$$\text{out}[i] = x_1[i]\cos\theta_i - x_2[i]\sin\theta_i,\quad
\text{out}[i{+}D/2] = x_2[i]\cos\theta_i + x_1[i]\sin\theta_i$$

关键结构:两行右边用的是**同一个** $\theta_i$。cos/sin 表在生成时把 $D/2$ 个频率
重复了两遍,就是为了让前后两半共用一组频率。**这个结构决定了字节账能砍半**——
一个线程同时处理一对,cos/sin 就只读一次。

## 版本化方法论

| 版本 | 只改的那一件事 | 想验证的假设 |
|---|---|---|
| v0 | (基线)一线程一元素 | 就地更新会撞上读写冲突,需要临时缓冲 |
| v1 | 一线程一对,读 2 写 2 | 依赖收进线程内,冲突消失且 cos/sin 只读一次 |
| v2 | q 与 k 合并进一次 launch | prefill 接近零收益,decode 接近 2 倍 |
| v3 | 16 B 向量化 | 事务利用率从半个提到满 |
| v4 | 免表,`__sincosf` 现算 | 表只有 8 MB 常驻 L2,免表只有边际收益(±5%) |

v2 那条预测是这个子项目最想验证的东西:**同一个改动在两个工作区间的收益能差多少倍**。
实测 HBM 区间 -1.1%(噪声内),decode 区间 1.43 倍——差四十倍。

v4 还留下一个方法论教训:它最初写成了标量版免表,与向量化的 v3 相比同时变了两个变量,
测出来的数字什么也说明不了。重写成"v3 + 免表"隔离出单一变量后,才拿到干净的 +2.1%。

## 工程结构

- `include/rope.h` — 共用声明,文件头写清两种布局的命名陷阱
- `src/rope_v0.cu ~ v4.cu` — 五级版本梯
- `src/binding.cpp` — torch 绑定;`D % 16 != 0` 时在入口拒绝而不是让 kernel 越界
- `bench.py` — 八条臂、四个工作区间

## 一个必须记住的坑

就地算子的 benchmark 里,**clone 必须写在计时闭包之外**。正确性需要干净副本,
时延不需要。把 clone 写进被计时的函数,该臂每次迭代会白搬一遍整个张量,
表现为"恰好慢 2 倍"——而**恰好整数倍是 harness bug 的指纹,不是性能现象**。
这个坑在本子项目的 Triton 对照臂上实际发生过,诊断过程记在 EXP-K05 §6。
